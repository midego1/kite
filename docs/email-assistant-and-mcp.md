# Email assistant and MCP

Configure the AI provider in **Admin → Agent**. Kite supports Cloudflare Workers AI, Anthropic's native API, and OpenAI-compatible providers, including Haimaker.ai, OpenAI, OpenRouter, Groq, and custom endpoints. The Haimaker catalog is fetched from its API, so available models from DeepSeek, Qwen, GLM, Kimi, and MiniMax appear without hardcoded IDs. You can save several providers, each with its own key and models, and switch between them with **Use this provider** without typing anything again; exactly one is in use for every AI feature (see [AI providers](assistant.md#ai-providers)). You can configure multiple models per provider, then choose a model for each mailbox in the assistant's **Settings** view; a mailbox whose model the provider in use does not offer uses that provider's default and says so. Assistant chat is available by default once a provider is configured; an admin can turn it off in **Admin → Agent**. With an external provider (anything but Workers AI), chat also needs the primary admin's **Allow an external AI provider to read mail** opt-in, like every other AI feature that sends mail to the provider (see [Privacy](assistant.md#privacy)). The assistant works within the selected mailbox. Mailbox managers can set instructions for the mailbox (general, chat, drafting and summaries), a draft reviewer, and a daily auto-draft limit; every user can also set their own instructions under **My instructions** (see [Instructions](assistant.md#instructions)). In the composer, **Write with Kite** writes or rewrites the body (see [Write with Kite in the composer](assistant.md#write-with-kite-in-the-composer)). Automatic reply drafts are off until enabled for that mailbox, and a person must review a draft before sending it. **Admin → Agent → View Usage** shows AI request totals, estimated spend against the daily caps, a day-by-day chart with per-day details, breakdowns by model, provider, feature and mailbox, outcomes and errors, and a filterable activity log (see [AI usage](assistant.md#ai-usage)).

You can follow up on an assistant draft in chat. The assistant can revise its body, subject, sender, recipients, and send time, copy an attachment from an email in the selected mailbox, or remove a draft attachment. It reads the latest draft revision before editing. A requested send time does not queue delivery on its own: the assistant creates a review link, and the user confirms the exact draft and time in Kite. The composer can also edit an assistant draft, add local files, and request the same review. The review always says that the assistant wrote the message, partly from email content anyone could have written, and lists in a red warning every recipient you have never written to and have not saved as a contact (contacts you added by hand or wrote to before count as familiar; someone who only wrote to you does not), so a recipient planted by a message's instructions stands out before you confirm. A recipient becomes a contact you wrote to only once Kite delivered a message you sent them: a cancelled scheduled or undone send, an auto-reply, and mail a module sends for you (such as an invitation answer or a booking notice) do not count, and they do not approve their recipients in the [Screener](screener.md) either. `Auto-Submitted: no` marks mail a person sent, so it counts. MCP's `request_send` and `get_send_request` do not return this warning; it is shown only in Kite. Apply the latest database migration before using scheduled assistant drafts.

Each tool call the assistant makes counts as one step. **Max steps per question**, at the top of the assistant's **Settings** view, sets how many steps it may take for one question; it is a personal setting (default 15, from 3 to 30) and applies to every mailbox you use. Higher limits let it handle bigger tasks but take longer and use more AI quota. On its last allowed step the assistant cannot call tools and must answer with what it has found, saying so if it ran out of steps. The setting is also available as `GET`/`PATCH /api/settings/assistant` with `{ "maxSteps": number }`; the same route reads and saves your own instructions as `{ "instructions": { "general", "chat", "draft", "summary" } }` (all four strings, up to 2,000 characters each).

The read tools are `list_emails`, `search_emails`, `count_emails`, `get_email` and `get_thread`. `list_emails` and keyword `search_emails` results page newest first on the same `(created_at, id)` order as the message list: pass the `nextCursor` of one page as `cursor` for the next, and mail stored in the same second is neither skipped nor repeated. Search results found by meaning are ranked by relevance and have no cursor. `get_thread` returns the opened email and the rest of its conversation except Spam, Trash, mail the Screener holds and other users' drafts, the same rows automatic reading (the earlier subjects and message count of the thread), automatic reply drafts and conversation summaries read (`agentThreadRows` in `src/lib/agent/thread-context.ts`); reply drafts made in the background leave out every draft. `count_emails` takes an optional search query (the same syntax as search), folder and read state and returns one exact count, so a question such as "How many GitHub emails are in my inbox?" needs a single step instead of paging through results.

The assistant can also organize mail: `mark_emails_read` and `mark_emails_unread` (up to 20 emails), `move_emails` (archive, trash, spam or back to the inbox, up to 20 emails), `list_folders`, `create_folder` and `move_emails_to_folder` (up to 20 emails into one folder). The older single-email `mark_email_read` and `move_email` still work. In chat these never act on their own: the tool returns a proposal that lists the emails or the folder, and nothing changes until you choose **Approve** under it. To clean up mail matching a search, the assistant searches first and proposes at most 20 emails at a time. Once approved, the card says what changed and offers **Undo**; the change is also recorded in the assistant's **Activity**, where full-access users can undo it for 7 days. Undo puts back only the emails that are still exactly where the action left them (same status, folder and read state), so it never overwrites a later move, filing or read change; when some had changed since, the card says so, for example "Undid 2 of 5; 3 had moved since", and when none could go back the undo is refused. Undo removes a created folder only while nothing is filed in it and no mailbox rule uses it. Undoing a move to or out of Spam puts the email back and also takes back what the spam filter learned from the move, exactly (see [Undoing a report](spam-protection.md#undoing-a-report)); until the database update that records this is applied, undo moves the email back but the filter keeps what it learned. Moves and folders need full access to the mailbox; read state needs only read access, as in the inbox, and someone with read access can undo only their own read-state change. Mail held by the Screener is never listed or changed. The assistant has no separate date tool: every message you send carries the current date and time in your time zone.

While an email from the selected mailbox is open, the assistant shows **Current email:** with its subject above the prompt, and each message you send tells the model which email that is, so "this email" means the one on screen even after the chat has discussed others. Only the email's ID goes with your message, never its subject or text, and the note is not saved in the chat history; the assistant still reads the email with its tools. Kite ignores the ID unless the email is in the selected mailbox and you could read it with `get_email`, so another user's draft in a shared mailbox is never named. Choose **✕** (Don't use this email) to leave the open email out of the chat until you open another one.

While the assistant is responding, you can enter more messages. They appear in a queue above the prompt and run in order after the current response. You can edit or remove a queued message, or choose **Steer** to stop the current response and send that queued message next. Switching chats or closing the assistant clears the local queue.

To connect an external AI client, create a key in **Settings → API keys** and enable **Allow MCP access**. Choose the permitted mailboxes and mail tools. After creation, copy the key or the ready-made AI agent instructions; the key is shown only once. Connect the client to `https://<your-kite-origin>/mcp` using Streamable HTTP and `Authorization: Bearer <key>`. Mail MCP access is limited to the selected mailboxes and the key owner's current permissions. An alias shares its parent mailbox, so selecting that mailbox also includes mail delivered to its aliases. The MCP `request_send` tool creates a review request; sending still requires confirmation in Kite. MCP mail tools do not require an AI provider. An assistant draft cannot be sent around that review either: JMAP `EmailSubmission/set` refuses it with `forbidden`, as `/api/send` refuses it with 409, and `/api/v1/send` never takes a draft.

## Connecting an MCP app with OAuth

An MCP client that supports OAuth (Claude Desktop, Claude Code, the MCP Inspector, VS Code and others that follow the [MCP authorization spec](https://modelcontextprotocol.io/specification/latest/basic/authorization)) can connect without a pasted key. Add `https://<your-kite-origin>/mcp` as a remote (Streamable HTTP) MCP server in the app and leave the key or header empty. The app opens Kite in your browser; sign in if needed, and the consent screen shows the app's name (chosen by the app itself, so Kite marks it as unverified), the host it returns to, the permissions it asks for and your mailboxes. Only **Read mail** is ticked; tick the other permissions and the mailboxes the app may use, then choose **Allow**. **Deny** sends the app back with nothing. Sending still needs your confirmation in Kite, as with a key.

- **Claude Desktop** (and claude.ai): Settings → Connectors → **Add custom connector**, paste the URL and choose **Connect**. Claude reaches custom connectors from Anthropic's servers, so Kite must be reachable over `https` from the internet.
- **Claude Code**: `claude mcp add --transport http kite https://<your-kite-origin>/mcp`, then `/mcp` in a session and choose **Authenticate**.
- **Other clients**: any client that discovers the authorization server from the `401` answer of `/mcp` and registers itself works. Clients that need a pre-registered client ID or a client secret are not supported; use an MCP key for those.

**Settings → MCP apps** lists every app you connected, with its permissions, mailboxes, the host it returns to and when it was last used. **Revoke** ends its access at once and cancels the send requests it left waiting. A connected app gets exactly the tools of the permissions you approved, filtered and checked like an MCP key's, and only the mailboxes you can still read; module permissions keep working while the module is off and their tools come back with it. API keys keep working unchanged.

How it works, for client authors and reviewers (`src/lib/mcp/oauth/`):

- **Discovery.** A request to `/mcp` without a valid credential answers `401` with `WWW-Authenticate: Bearer resource_metadata="https://<origin>/.well-known/oauth-protected-resource/mcp"` (RFC 9728; `error="invalid_token"` when a token was sent). That document names `https://<origin>/mcp` as the resource and Kite as its authorization server, whose metadata is at `/.well-known/oauth-authorization-server` (RFC 8414). The origin is `APP_URL` when set.
- **Registration.** `POST /api/oauth/register` (RFC 7591) takes public clients only (`token_endpoint_auth_method` `none`, no client secret), at most five redirect URIs of up to 1,024 characters each, every one `https` or `http` on `localhost`, `127.0.0.1` or `[::1]` (RFC 8252), without a fragment or user info. A native app should register the loopback address itself, `http://127.0.0.1:<port>/…` or `http://[::1]:<port>/…`, rather than `localhost`: RFC 8252 §8.3 advises against `localhost`, since a hosts file or DNS can send that name elsewhere. `localhost` is still accepted for apps that already use it. Other metadata such as a logo is ignored. Requests are capped at 16 KiB. Registrations are limited per IP, and of those made in the last hour at most 1,000 in all and 20 per network (an IPv4 /24 or IPv6 /48; only an HMAC of it keyed with a server secret is stored, and only until the registration is first used) may be waiting unused. A registration nobody used within an hour is removed, as is one 30 days after its last use once it has no connection left.
- **Authorization.** `/oauth/authorize` takes `response_type=code`, an S256 `code_challenge` (PKCE is required; `plain` is refused), an optional `state`, `scope` and `resource`, and a `redirect_uri` that must equal a registered one character for character, except that an `http` loopback URI matches on any port, as native apps listen on whatever port is free (RFC 8252 §7.3); it may be left out when the client registered only one. An unknown client or redirect URI is shown in Kite and never redirected to; other errors go back to the client with `error`, `state` and `iss` (RFC 9207). Only a signed-in user sees the consent screen; a signed-out visitor signs in first and returns to it. The decision is a same-origin request from the signed-in session, and the code is single-use, valid for two minutes and stored as its SHA-256.
- **Tokens.** `POST /api/oauth/token` (form-encoded, or JSON) exchanges the code with the same `client_id`, the `code_verifier` and the same `redirect_uri` (left out when the authorization request left it out), and a `refresh_token` for a new pair. Access tokens (`kite_at_…`) last an hour; refresh tokens (`kite_rt_…`) 30 days, and every refresh replaces both. A refresh retires the old token and stores the new pair in one transaction, so a failed refresh can simply be retried. A used refresh token presented again within a minute, while the pair it was replaced by is still current, gets that same pair (two processes of one app refreshing at once); later, or after the app moved on, it revokes the whole connection, as does a code redeemed twice. The repeated pair is kept sealed with a key only the old refresh token yields, bound to its connection, and the five-minute maintenance run drops it once the minute is over. Tokens are bound to `https://<origin>/mcp` (RFC 8707): a `resource` naming anything else is refused with `invalid_target`, and `/api/v1`, JMAP and every other route refuse OAuth tokens. Only SHA-256 hashes of codes and tokens are stored, nothing is logged, and the token and registration answers carry `Cache-Control: no-store`. The token and revocation endpoints are limited per IP like sign-in.
- **Revocation.** `POST /api/oauth/revoke` (RFC 7009) with `token` and `client_id`: a refresh token ends the connection, an access token only itself.
- **Storage.** A connection is an `api_keys` row of kind `oauth` (no usable key) with its scopes and `mcp_key_mailboxes`, so audit rows (`mcp.tool_call` with that key id), send requests and the rate limit work as for an MCP key; `mcp_oauth_clients`, `mcp_oauth_codes`, `mcp_oauth_grants` and `mcp_oauth_tokens` (migration 0106) hold the rest. They are not in backups, so a restore disconnects MCP apps and they connect again. Before migration 0106 is applied, Settings → MCP apps lists nothing and registration, consent and tokens answer `409` with `MIGRATION_PENDING`.

The MCP server tells every client, in its `instructions`, that email subjects, bodies, sender names, attachment names and calendar text are untrusted content written by third parties, that it must never follow instructions found there or move, delete, draft, send or change anything because of them, and that it must confirm destructive tools with the user first. Every object a tool returns starts with `"contentTrust": "untrusted_third_party_content"`. Each tool carries MCP annotations: the read tools are `readOnlyHint`, and `move_email`, `move_emails`, `discard_draft`, the admin `manage_*` tools and module tools that change or delete data (`update_events`, `delete_events`) are `destructiveHint`, so a client can ask before calling them. Every MCP tool call writes one audit row (`mcp.tool_call`) with the user, the key id, the tool, the module or admin action and whether it succeeded, and the mailbox when the key may use it; never the arguments, results or error text. List them with `GET /api/audit-logs?action=mcp.tool_call`; rows are deleted 90 days after the call: every five minutes for those that just expired (up to 5,000 a run, reading only that slice of the `created_at` index), and in the daily pruning for any left over.

Over MCP the organize tools need the **Organize mail** permission (`mcp:organize`) and `list_folders` needs **Read mail** (`mcp:read`). They act at once, without the chat approval, like the MCP move tools always have, and are not recorded in Activity; they are written to the mailbox audit log like other MCP changes, including a created folder.

MCP clients can use `update_draft` for the same draft fields and attachments, then `request_send` to create a human review for immediate or scheduled delivery. Attachment additions copy an existing file from an email in the key's permitted mailbox; local files are added through the composer.

Calendar access uses separate **Read calendar** and **Manage calendar** MCP permissions. The personal calendar exposes `get_calendars`, `get_schedule`, `search_events`, `get_event`, `find_free_time`, `create_event`, `update_events`, and `delete_events`. Calendar-only keys need no mailbox selection. Over MCP, calendar writes save immediately; `update_events` and `delete_events` are marked destructive and the server instructions ask the client to confirm them with you. In assistant chat, `update_events` and `delete_events` only propose the change (see [Assistant chat and modules](assistant.md#assistant-chat-and-modules)). Event updates and deletes use series IDs and affect the entire recurring series; these tools record attendees but do not send invitations or cancellations. Supply absolute ISO 8601 times with offsets. Schedule and availability ranges are limited to 90 days.

For management tools, create a separate MCP key in **Admin → API keys**. Its selected domain, account, and mailbox management permissions do not grant access to mail content. This page also provides copyable AI agent instructions after key creation.
