# Releasing

Kite uses calendar versions, `YYYY.MM.DD.N`: the UTC date a release was prepared, then a counter for that day's releases starting at 0. The first release on 9 October 2026 is `2026.10.09.0`, a second one that day is `2026.10.09.1`.

Every merge to `main` deploys production through the Cloudflare Git integration, but not every merge is a named release. Pull requests describe their changes in changelog fragments (`changelog.d/`) and leave the version alone, so open pull requests never conflict on release files. A release pull request, kept up to date by a workflow, folds the fragments into `CHANGELOG.md` and bumps the version; merging it is the release, and the GitHub release is published automatically once its production deploy has succeeded.

## Version numbers

- `VERSION` holds the current release. Builds embed it with the short Git revision (`scripts/build-version.mjs`), so the sidebar and the database card show `Kite v2026.10.09.0 (985434d)`. MCP reports the same version and the OpenAPI document (`docs/openapi.json`) carries it as `info.version`.
- `package.json` and the root of `package-lock.json` carry the npm form: the first three parts without leading zeros (`2026.10.9`), because npm accepts neither four parts nor leading zeros. `npm run quality:check` fails when they disagree with `VERSION`.
- Deploys between two releases keep the last release's version; the revision tells them apart, as it does for a preview of a pull request.
- The number says when a release was made, not what changed in it. `CHANGELOG.md` says what needs attention, such as database migrations to apply from the admin overview, or a new variable or binding.
- The email relay (`deploy/cloudflare-email-relay`) keeps its own version.

## Changelog fragments

A pull request with a user-visible change adds a file to `changelog.d/`, named after the change: `changelog.d/<short-slug>.md` in lowercase letters, digits, `.`, `_` or `-`. It holds one or more `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed` or `### Security` headings, each followed by entries written as in `CHANGELOG.md`; no other heading level and no text before the first heading. Code blocks (```` ``` ```` or `~~~`) may hold lines that look like headings, except `## ` lines, and an entry may start with an issue number such as `#123`. [`changelog.d/README.md`](../changelog.d/README.md) has an example.

- Name every migration and every setting an operator has to add or change. When a note introduces or changes something a user can set, link to the page it lives on with an app path, for example `[Settings → Notifications](/settings/notifications)`: the **What's new in Kite** dialog opens such links in the app, while `https://` links open in a new tab and any other link stays plain text.
- A user-visible UI change adds a screenshot to the fragment ([below](#screenshots-in-the-changelog)).
- A change nobody can notice (CI, tests, refactoring) needs no fragment: label the pull request `no-changelog`.
- Do not edit `VERSION`, the package versions, `docs/openapi.json`'s version or the "Unreleased" section of `CHANGELOG.md`; only release pull requests do.
- Fragments ship with every deploy: the **What's new in Kite** dialog lists them under "Unreleased changes" (`scripts/generate-changelog-bundle.mjs`) until a release names them.

The "Release version" job in `.github/workflows/ci.yml` runs `npm run release:check -- <base commit>` (`scripts/release-check.mjs`, Node built-ins only). For an ordinary pull request it fails when no fragment was added or edited and the `no-changelog` label is missing, when any fragment in `changelog.d/` is malformed, when `VERSION` differs from the base's or when `CHANGELOG.md` has entries under "Unreleased". A pull request from a `release/*` branch must instead be a complete release: `VERSION` a calendar version newer than the base's, a `CHANGELOG.md` heading for it, nothing under "Unreleased" and no fragments left. On a pull request it compares with the first parent of GitHub's merge commit, the base the branch was merged onto. It reads the labels when it runs, and adding a label starts no CI run, so after adding `no-changelog` rerun the failed job (or push again). Run `npm run release:check -- origin/main` locally for the same answer (it uses the current branch name; set `PR_LABELS='["no-changelog"]'` to mimic the label).

### Screenshots in the changelog

A pull request that changes what people see (a new or redesigned page, dialog, menu or setting) adds a screenshot of it to its changelog fragment, under the bullet it belongs to:

```markdown
### Changed

- The command center in the empty reading pane is laid out as cards.
  ![The command center with unread, Accounts, Quick actions and Today cards](/changelog/2026-11-01-command-center-light.webp)
```

- **Where.** The file is `public/changelog/<name>.webp`, named like a fragment in lowercase with the date first (`2026-11-01-command-center-light.webp`), and the path in the markdown is `/changelog/<name>.webp`. It is a static asset: it never counts toward the JavaScript, the page loads it lazily (`loading="lazy"`, only when the **What's new in Kite** dialog or the "Kite was updated" reader draws it) and the Content-Security-Policy stays as strict as before, because nothing is fetched from another origin.
- **Limits.** WebP only, at most 1600 px wide and 200 KB, with alt text that says what the picture shows (an empty alt text is refused). Only `/changelog/<name>.webp` paths are accepted: no remote URLs, no other folders. `npm run release:check` (the CI "Release version" job) and `npm run release:prepare` fail on a missing file, a file over a limit, a missing alt text or any other path, and `tests/changelog-images.test.mjs` fails on a file in `public/changelog/` that no release note uses.
- **Demo data only.** A screenshot never shows real mail, names, addresses, domains, keys or tokens: use the seeded demo data and read the picture once before committing. Crop to the relevant part; show light and dark when the change is about looks (two images under one bullet, the viewer steps between them).
- **How to take it.** `npm run changelog:screenshot` runs `scripts/screenshots/changelog.capture.ts` against the isolated, seeded e2e server (the same one `npm run screenshots` uses, with the invented demo data of `scripts/screenshots/demo-data.ts`), screenshots an element or the page and writes a size-capped WebP to `public/changelog/`. Add an entry to `SHOTS` in that file: a `name`, an optional `theme` and `viewport`, and an `open(page)` that navigates to the change and returns the locator to capture. Plain `npm run screenshots` skips it, so published images are never rewritten by accident. Pictures from another source (a designer's PNG, a run's output) work too if they are converted with the same limits, for example with `sharp`.
- **What people see.** In the dialog every screenshot is a small thumbnail under its bullet; clicking it opens a larger view (Escape closes it and the focus goes back to the thumbnail, the left and right arrow keys step between the release's images, **Actual size** shows the pixels). **Show images** in the dialog header turns the thumbnails off in this browser (stored as `kite-changelog-images`, on by default); the "Kite was updated" reader honours the same choice. An image with a remote URL, a path outside `/changelog/` or no alt text is not an image: it shows as literal text.
- **GitHub releases.** The published release rewrites `/changelog/x.webp` to `https://raw.githubusercontent.com/midego1/kite/main/public/changelog/x.webp` (`absoluteImageUrls` in `scripts/changelog-images.mjs`, used by `scripts/deploy/release-publish-utils.mjs`), so the pictures render on GitHub. To paste a release's notes by hand, `npm run release:notes -- <version>` (a calendar version such as `2026.11.02.0`) prints that version's `CHANGELOG.md` section with the same rewrite.

## Releasing

After every push to `main` that leaves fragments in `changelog.d/` (or entries under "Unreleased" in `CHANGELOG.md`), `.github/workflows/release-pr.yml` prepares the next release on top of `main` and opens or updates one pull request, "Release `<version>`", from the branch `release/next`:

1. A read-only job checks that it is looking at the tip of `main` (a re-run of an older push does nothing, so `release/next` is never rewound) and runs `npm run release:prepare`, which writes the next version into `VERSION`, `package.json`, `package-lock.json` and `docs/openapi.json`, folds the fragments (and anything still under "Unreleased") into a new `CHANGELOG.md` section with one heading per group, and deletes the fragments. It refuses malformed fragments and a `VERSION` dated after today, and it commits, tags and pushes nothing itself.
2. A second job, the only one with a write token and one that runs no npm or repository scripts, commits the prepared files as `chore(release): <version>` with `main` as the first parent and the previous `release/next` as the second, so the commit's own diff is exactly the release and the branch only moves forward without force pushes. It never pushes to `main`, then opens or updates the pull request.
3. When `npm run release:prepare` fails on `main` (a malformed fragment that slipped through), the run fails and the workflow opens an issue "Release PR could not be prepared" with the error, or comments on the open one; the next successful run closes it. Fix the fragment in a pull request. The workflow can also be run by hand from the Actions tab ("Release pull request", **Run workflow**); it always prepares the tip of `main`.
4. Pushes made with the workflow's `GITHUB_TOKEN` start no workflow runs (a GitHub rule), but `workflow_dispatch` is exempt. So after pushing, the second job dispatches `ci.yml`, `docs.yml` and `security.yml` on `release/next` (`gh workflow run --ref release/next`; the job holds `actions: write` for this). Their check runs attach to the branch's tip and carry the same job names as on a pull request, so the required checks (Mission validation, Node build, docs, Gitleaks history scan, Offline source security rules) count. The jobs that only make sense on a pull request ("Release version", the PR report) are skipped on dispatch; the prepare job already validated the release.
5. Unless the release is on hold, the second job then enables auto-merge (squash) on the pull request (`gh pr merge --auto --squash`), so it merges, and releases, as soon as every required check is green. Nothing is closed, reopened or approved by hand. Every other branch protection requirement still applies: a required check set from outside the workflows, or a ruleset that asks for a review, keeps the merge waiting until it is met. In this repository the Foreman posts the required `paseo/independent-review` check on each release head. The step is idempotent: a rerun that pushed nothing dispatches the checks again only when the head lacks a successful required check, and enables auto-merge only when it is not enabled yet; a failure to enable it only warns.
6. **Holding a release.** Put the label `release-hold` on the pull request (create the label once), or set the repository variable `RELEASE_HOLD` to `1`, and the workflow does not enable auto-merge and says so at the end of the pull request body. Auto-merge that was enabled earlier is switched off by the next run (or use **Disable auto-merge** on the pull request at once). To release later, remove the label (or the variable) and run **Release pull request** from the Actions tab again; closing the pull request does not hold a release, because the next push to `main` opens it again.
7. **Pushes by the bot start no workflows.** A pull request merged by auto-merge is merged as `github-actions[bot]`, and GitHub starts no workflow runs for events caused by `GITHUB_TOKEN`. So a release merge starts none of the `push` workflows on `main` (CI, Documentation contract, Security scans, Release pull request); the checks that ran on `release/next` are the ones that gated it. The production deploy and the Release publish workflow still run, because they start from Cloudflare's `check_run` events, which are not `GITHUB_TOKEN` events. Merge the pull request by hand if you want those push workflows to run on the release commit.

`npm run release:prepare` also deletes the bundle growth allowances in `bundle-growth.d/` (see [Quality](quality.md#coverage-and-performance-scope)): they only matter to the pull request that added them, and like fragments they are unique files, so open pull requests never conflict on the bundle budgets.

`release/next` is prepared again after every push to `main` while fragments remain, so edits made on that branch by hand are lost at the next push; edit the notes just before merging. When `main` moves on, the release pull request shows conflicts or is behind until that next push refreshes it (or until someone runs the workflow by hand); the run pushes a new commit and dispatches the checks again. The "Release version" check only runs on `pull_request` events, so it is not among the dispatched checks (the prepare job validates the release instead); it runs if someone closes and reopens the pull request. Merge it whenever you want a named release. `npm run release:notes -- <previous tag>` lists the commit subjects since the last release to compare against. GitHub deletes `release/next` after the merge, and the next fragment starts a new one.

To release by hand instead, run `npm run release:prepare` on a branch named `release/<anything>` made from an up-to-date `main`, commit as `chore(release): <version>` and open a pull request.

### Migrating an open PR

Pull requests opened before fragments ended with a `chore(release)` commit. To move one over:

1. Save the pull request's own changelog entries (the section its release commit added, or its lines under "Unreleased"); step 3 needs them.
2. Run `git fetch origin`, then bring the branch up to date with `origin/main` (merge or rebase); wherever Git reports a conflict in `VERSION`, `package.json`, `package-lock.json`, `docs/openapi.json` or `CHANGELOG.md`, take `main`'s side. Then put the release files back to `main`'s: `git checkout origin/main -- VERSION CHANGELOG.md`, the same for `package.json` and `package-lock.json` unless the pull request changes dependencies (then only their `version` fields go back to `main`'s), and `npm run docs:generate` to rewrite `docs/openapi.json` with `main`'s version (it also rewrites `docs/api-inventory.md` and `src/lib/metrics-routes.generated.json`; keep those changes only when the pull request changes routes).
3. Put the saved entries into a fragment, `changelog.d/<short-slug>.md`, keeping their `###` headings.
4. Commit, push and check with `npm run release:check -- origin/main`.

## After the merge

Merging to `main` deploys the Worker through Cloudflare Workers Builds. When the `Workers Builds: kite` production check run succeeds, two workflows run:

- `.github/workflows/deploy-record.yml` records a GitHub deployment for the commit ([Operations](operations.md#after-a-deploy)).
- `.github/workflows/release-publish.yml` runs `scripts/deploy/release-publish.mjs` from the default branch. It reads `VERSION` at the deployed commit and creates the lightweight tag `v<version>` on that commit if it does not exist yet, then publishes the GitHub release "Kite `<version>`", marked as the latest only when no higher published calendar version exists (drafts and prereleases do not count). Its notes are the version's section of `CHANGELOG.md` followed by the commits since the previous `v*` tag, grouped into features, fixes and maintenance. A draft for the same tag is filled in and published instead of adding a second release; an already published release is never edited.

When the tag already exists on a different commit, the deploy did not bump `VERSION`: an ordinary merge between two releases. The workflow then makes no tag or release and says so in its log; the next release pull request publishes the changes.

Tags created by the workflow do not trigger other workflows. The Release draft workflow (`.github/workflows/release.yml`) is kept for manual use: run it from the Actions tab, or push a `v*` tag yourself, to get a draft release with notes grouped from the commit subjects. It leaves an already published release untouched and finishes successfully.

A release prepared on one day and merged on a later one keeps its version: the date is when it was prepared (the release workflow prepares it again, with the current date, after every push to `main` with fragments). Don't reuse or move a tag once the release is published; prepare a new release instead.
