# Assistant: automatic reading

Besides chat, drafting and MCP (see [Email assistant and MCP](email-assistant-and-mcp.md)), Kite can read new mail for you and put what it finds in front of you as suggestions. This page covers what it does, where your mail goes, what it costs and how to stop it.

## Kite reads for you

Automatic reading is a per-mailbox setting under assistant settings, **Automatic reading**. It has four autonomy levels:

| Level            | Status        | What it does                                                                  |
| ---------------- | ------------- | ----------------------------------------------------------------------------- |
| Off              | Available     | Default. Kite does not read new mail. The older auto-draft setting still works. |
| Suggest only     | Available     | Kite reads new mail and offers suggestions. Nothing happens until you accept. |
| Act with undo    | Not available yet | Reserved. You cannot select it.                                           |
| Full auto        | Not available yet | Reserved. You cannot select it.                                           |

Automatic reading also needs the email assistant to be on and the install-wide **Enable automatic reading** switch (primary admin) to be on. The settings section names the AI provider that will read the mail.

Suggestions come in these kinds when Kite finds something worth raising: a calendar invitation, a reply to review, a summary of a long thread, a possible phishing warning, and a subscription found in a receipt or invoice (Money Watch, see [Subscriptions](#subscriptions-money-watch)). Other kinds are reserved. A suggestion expires after 14 days.

Suggestions are shown to people with full access to the mailbox only. Other users cannot tell the mailbox has any. They appear as a badge on the message row, as a card in the reader, and together on the **For you** page, grouped by kind with the most important first. Accepting or dismissing a suggestion shows a toast with Undo.

Kite never sends mail on its own at Suggest only. A reply suggestion creates a draft in the reviewer's Drafts, private to the reviewer. You review it and send it from the composer. In the assistant panel a draft the assistant wrote appears as a card with **Edit draft** and **Approve to send**; once the draft is sent or scheduled, the card shows **Sent**, **Scheduled for** the time, **Sending…** while delivery is under way (it checks again by itself) or **Sending failed** instead, and a draft that was deleted or whose send you undid shows that it is no longer available.

## Deterministic first

Most mail never reaches a model. Kite first skips messages that are not in the Inbox, come from your own addresses or from bounce senders, or are auto-submitted. For the rest it reads facts it can compute itself: sender authentication results, bulk and no-reply headers, whether the sender is a known contact, an attached calendar invite, thread length and phishing signals. It asks the model only for mail that is not bulk, automatic, no-reply or spam, from a sender you have not muted, and only when a reply, summary or phishing capability is on. Calendar invites are parsed from the attached ICS file, not by the model, and a message that needs no model costs nothing. The one exception is receipt-like mail that Money Watch could not read completely on its own: see [Subscriptions](#subscriptions-money-watch).

When Kite does call the model, the call has no tools. The model reads the message and returns a structured answer. It cannot search, send, move or delete anything. Kite checks the answer, and a reply draft is checked against the conversation so that it cannot introduce an address or link that was not already in it.

**Output budget and thinking.** Automatic requests have a small output budget (`src/lib/agent/output-budget-utils.ts`): automatic reading 400 tokens for its answer, plus up to 200 for module extensions and 60 for the one-line summary; agent drafts 900; a one-line summary on its own 80. Thinking counts against the same budget, and Claude 5 models think by default when a request does not say otherwise, so with Anthropic Kite switches thinking off for automatic requests and Write with Kite unless a reasoning effort is saved for the model. A model that cannot stop thinking (Claude Opus 5.5, Fable, Mythos) gets effort low instead, with 1,100 tokens of room. A saved effort is sent as is with the same 1,100 tokens of room; **minimal** means as little thinking as the model allows. An automatic-reading answer that is cut off anyway is asked once more with double the budget (reserved against the spend caps like any request) before it fails with `cut_off`.

## Privacy

Message content goes to the AI provider in use for the assistant (see [AI providers](#ai-providers)).

- **Workers AI** (Cloudflare). The content is processed on Cloudflare, which already hosts your Kite install. It is not sent anywhere else.
- **External providers.** Anthropic receives content through its native API. Haimaker, OpenAI, OpenRouter, Groq and custom endpoints use an OpenAI-compatible API. The content is sent to the configured provider, outside your install. Automatic reading with an external provider needs a separate opt-in from the primary admin (**Allow an external AI provider for automatic reading and the composer** in the install-wide automatic reading settings). Without it, Kite skips the message and says why, and Write with Kite is not offered in the composer. Some providers may retain what you send or train on it. Read your provider's terms, or use a provider you run yourself.

What is sent: the message's sender, subject and text, the facts Kite computed and the mailbox's own instructions. When a module asks for a few extra fields (Money Watch's vendor, amount, cycle and dates), the same request also carries that module's fixed instructions; nothing else from the message is added, and PDF text is never sent. Prompts and responses are not stored by Kite. It stores the suggestions and the audit log of what was done, plus token counts and cost for each request. Conversation summaries made with **Summarize** are the exception: they are stored, see [Summaries in the reader](#summaries-in-the-reader). The provider may store more under its own policy.

Message text is treated as untrusted. A message that tries to give the model orders cannot make Kite act: the model has no tools, its answer is validated, and anything that changes something needs your click at Suggest only.

## AI providers

The primary admin chooses the provider in [Admin → Agent](/agent) and can save several: Workers AI, Anthropic, Haimaker, OpenAI, OpenRouter, Groq or a custom OpenAI-compatible endpoint, each with a name, its base URL, its API key and its models with their rates. **Saved providers** lists them; the one marked **In use** is the only one used, and every AI feature (chat, Write with Kite, automatic reading, summaries, agent drafts, spend and the model choices in each mailbox) uses that one, as before with the single provider. **Use this provider** switches to another in one click, without typing its key or models again, and a request that starts afterwards uses it. The external-provider opt-in still applies to whichever provider is in use, so while it is on, switching to another external vendor first asks you to confirm that the permission now applies to that vendor.

- **Adding and editing.** **Add provider** opens an empty form; the provider is saved without being used unless you tick **Use this provider now**. Only when no provider is set up at all (none saved, none from before 0077 and none from the environment) is the new one used at once, so adding a provider never switches away from one that works; the message after saving says which happened. **Edit** opens a saved provider. The model list loads with the key you typed or, when you leave the key empty, with that provider's own saved key, never another provider's. A blank name becomes the provider's name, such as "Haimaker.ai".
- **Keys.** Each key is stored on the server, sealed with `APP_ENCRYPTION_KEY` when it is set (as the single key always was), and is never sent back to the browser: the page only shows whether one is saved. A custom endpoint whose base URL is `AI_BASE_URL` may leave the key empty and uses `AI_API_KEY`, which stays in the environment and is never copied into the database.
- **Unreadable keys.** A key sealed under another `APP_ENCRYPTION_KEY` (a backup restored into another install, a changed key) cannot be opened. Admin → Agent still loads and switching still works; the provider shows "key unreadable, enter it again", and AI requests with it fail with `provider_key_unreadable` until the key is entered again.
- **Deleting.** The provider in use cannot be deleted (409 `ACTIVE_PROVIDER`); switch to another first. Deleting removes its key and models.
- **Mailbox model choices.** A mailbox's chat or triage model that the provider in use does not offer falls back to the provider's default model (triage: chosen automatically), and the mailbox's assistant settings say which model was saved and which one is used. Switching back to the provider that offers it uses the saved choice again, unless the settings were saved in between.
- **Audit.** Adding, editing (including whether the API key was replaced), switching and deleting a provider are written to the audit log (`agent.provider_added`, `agent.provider_updated`, `agent.provider_switched`, `agent.provider_deleted`, with names and ids only, never a key) and listed on [Activity](/activity).
- **Migration 0077.** Saved providers need database migration 0077, which copies the provider configured until then into the first saved provider, in use. Until it is applied, Admin → Agent keeps the single provider form and says so, and everything reads and saves the provider in the earlier `app_settings` columns, which the migration leaves in place. The same columns are read while no saved provider is in use, for example after restoring a backup made before 0077. Once a saved provider is in use (saved, switched to, or after deleting the copied one), those columns are cleared, key included, so a deleted provider's key is gone and backups carry no stale copy. Backups include the saved providers (`agent_providers`, in the app settings group), with their keys sealed as stored.

## Instructions

The assistant's **Settings** view has two sets of instruction fields. They add preferences; they never replace Kite's own rules, which the settings show read-only under **What Kite always tells the AI**.

- **Instructions for this mailbox** (users who can manage the mailbox): **General instructions (all tasks)**, up to 4,000 characters, used by chat, reply drafts and automatic reading as before; **Chat**, used only in chat; **Drafting and composer**, used for the body of drafts chat writes, for the reply drafts Kite writes on its own (the legacy auto-draft and reply suggestions) and for Write with Kite in the composer; and **Summaries**, saved now for thread summaries, which are not available yet. Each task field holds up to 2,000 characters. Automatic reading itself keeps using only the general field.
- **My instructions** (every user, for themselves): the same four fields, up to 2,000 characters each. They apply in every mailbox you work in, and nobody else can read them, admins included. Chat uses the chatting user's, and automatic reply drafts use the mailbox reviewer's.

Where they go: always in the system prompt, after Kite's rules, each under its own heading that says it cannot override them, in this order: mailbox general, mailbox task, your general, your task. A shared mailbox's house style therefore comes before one person's taste. They are never placed in the user turn or inside the block that holds the email. Kite removes anything that could pass for that block's delimiters, control characters (C0 except the newline, DEL and C1), bidi controls, zero-width and other hidden characters (line and paragraph separators, soft hyphens, variation selectors), and cuts each field to its limit, counting characters as the settings' counter does (an emoji is one); the API refuses longer text. Every line of a task or personal field is quoted with `> `, so none of it can pass for one of Kite's headings; in the general field, which keeps its existing layout, only a line that imitates such a heading is quoted. Empty fields add nothing, so the prompts stay exactly as they were. An instruction such as "ignore the rules above" can make answers worse but cannot make Kite act: automatic paths have no tools, chat actions still need your approval and drafts still need your review.

The fields need migration 0069. Until it is applied, only the mailbox's general field can be saved and the others say so. A save that sets one of the new fields then answers 409 `MIGRATION_PENDING` and saves nothing, including the other fields in the same request, so a save is never half applied (the design spec said the other fields would be saved; Kite refuses the whole save instead). The same goes for **My instructions** and for the token allowances in Admin → Agent.

## Costs and caps

Every automatic request, and every step of a chat answer, is checked against these limits before it runs. Cheaper checks come first.

- **Deterministic filters.** The checks above run first and cost nothing. Per mailbox you can also turn off the calendar, reply, summary and phishing capabilities, each enabled module's own step (one switch per step, listed under the core ones), and mute senders. Muted and trusted senders are listed in the same settings, where you can remove or add them (see [Phishing warnings](#phishing-warnings)).
- **Daily limit per mailbox.** The number of messages Kite reads per UTC day. Default 200, range 1 to 1000.
- **Rate limit per mailbox.** A short burst limit. Mail over it is skipped as "rate limited".
- **Spend cap per mailbox.** An optional daily cap in USD. Empty means no per-mailbox cap.
- **Spend cap for the install.** A daily cap in USD for all mailboxes together, set by the primary admin. Default $2.00 per day. Admin → Agent shows what was spent today next to it.
- **Model rates.** Kite counts dollars with each model's rate in USD per million input and output tokens, taken from the first of these that has one:
  1. the rate the primary admin entered under **Estimated cost rates** in [Admin → Agent](/agent);
  2. the rate the provider publishes in its model list (OpenRouter, and Workers AI when Cloudflare API credentials are set), saved with the models;
  3. Kite's own price list (`src/lib/agent/model-prices.json`), with the official prices of well-known models: Anthropic Claude (dated ids such as `claude-haiku-4-5-20251001` included), OpenAI, Google Gemini, Workers AI's text models, Groq and DeepSeek (counted at DeepSeek's peak rate, the higher of its two). Each entry names the provider's pricing page and the date it was read, shown as "From Kite's price list (as of …) · source"; **Override** replaces it with your own rate, and **Use Kite's price** goes back. A model id matches exactly, by a listed alias, and for Anthropic also with a dated suffix. With a router provider (OpenRouter, Haimaker or a custom API), a `vendor/model` id (`anthropic/claude-opus-5-5`, `deepseek/deepseek-v4.1-flash`) that is not listed itself gets that vendor's own price, which routers pass on; OpenRouter's dotted Claude versions (`claude-sonnet-4.5`) match too. A direct provider's ids (Anthropic, OpenAI, Groq, Workers AI) never take another vendor's price. Where a provider charges more for long prompts (Claude Haiku 5.5 over 100,000 input tokens, Gemini 2.5 Pro and 3.1 Pro over 200,000, the larger OpenAI models over 272,000), that request is counted at the higher rate, and a price change the provider has announced with a date applies from that date. The list is updated with Kite releases, so a price the provider changes afterwards is out of date until then; override it if it matters to you. Batch, cache, fast-mode and regional surcharges are not counted.
- **When model rates are unknown.** If none of these has a rate for the model, Kite cannot count dollars. It then counts input tokens instead, with two daily allowances for the install: one for automatic reading and one for chat and Write with Kite together, 2,000,000 input tokens each by default, so neither can use up the other's. The primary admin changes them under **Daily token allowances without model prices** in Admin → Agent (1,000 to 1,000,000,000 tokens). Enter rates for your model to get a dollar cap instead.

A model that gets a rate, for example from a Kite update that adds it to the price list, moves from the token allowances to the dollar caps at once. With an expensive model the default $2.00 a day can be reached sooner than the token allowances were, so check the cap in Admin → Agent after an update. Without a triage model chosen for the mailbox, automatic reading picks the cheapest configured model among the rates entered or published in Admin → Agent; rates from Kite's price list never change which model it uses.

Kite reserves the estimated cost before each call and settles it with the real usage afterwards, so parallel jobs are counted against the cap before they run. Once reserved and settled spend reaches the cap, Kite starts no new calls: the model is skipped as "daily spend cap reached" until 00:00 UTC.

Chat counts against the same mailbox and install dollar caps, and without rates against its own token allowance. Each step of an answer (each tool call is one) reserves its estimate first, with up to 1,200 output tokens, and is settled with the step's usage. A step that would pass a cap is not sent: the answer ends with a message that names the cap (the mailbox's or the install's daily dollar cap, or chat's token allowance), says that it resets at 00:00 UTC and where it can be changed, and the steps already taken stay in the conversation. A step that is stopped before the provider reports its usage keeps its estimate. The cap is not a guaranteed billing ceiling. Estimates are not exact, so what your provider bills can slightly exceed it.

## AI usage

**Admin → Agent → View Usage** ([AI usage](/ai-usage), primary admin only) shows the AI requests of the last 7, 30 or 90 days in your time zone:

- **Totals:** tokens (input and output), requests (succeeded and failed), estimated spend and the average tokens per request.
- **Usage by day:** a chart of tokens, cost or requests. Hover over or focus a bar (arrow keys move between days, Escape closes) for the day's tokens, requests, failures, estimated cost, requests without a rate and a breakdown by model and by feature.
- **Estimated costs:** a request stores the cost of the usage the provider reported when its model has a rate. Three kinds of cost are marked estimated instead: a request that ended before the provider reported its usage (stopped, failed mid-stream or interrupted) keeps the estimate Kite reserved before the call, at the rate it was priced at; a request still running shows its reservation; and older requests that stored no cost (from before a rate was set or before Kite's price list knew the model) are priced at today's rate. Models with no rate at all are listed with a link to set one.
- **Today's spend and caps:** spend since 00:00 UTC against the install's cap and each mailbox's own cap (for mailboxes you can open), and the token allowances.
- **Outcomes:** succeeded, failed, stopped (the person stopped it, or the stream ended before the provider reported usage), running and interrupted requests, with the most common error codes. A request still open 15 minutes after it started is shown as interrupted: no model call takes that long, so its worker stopped before settling it.
- **Breakdowns** by model, provider, feature and mailbox, with requests, tokens, cost and share. Mailboxes you cannot open are counted together as "Other mailboxes".
- **Activity:** every request, newest first, filtered by model, provider, feature or status. Opening a row shows its feature, mailbox, status or error, duration, finish reason, cost and the rate it was counted at.

A **cut-off** answer (`cut_off`: it hit the output limit; tokens still counted) is recorded as **failed** in every feature, because every feature discards or flags such an answer: Write with Kite and automatic drafts insert none of it, chat marks the reply as cut off, and automatic reading, summaries and one-line summaries retry or give up. Its tokens and cost still count toward the spend and the caps. Write with Kite's answers that fail Kite's checks are failed with `unusable_answer`. The legacy automatic draft job (autonomy off with auto-drafting on) records its outcome too, but is not reserved against the daily caps, as before.

Status, error code, duration, finish reason, rate and whether the cost is an estimate are recorded from migration 0078 on; earlier requests show them as not recorded. Usage rows hold counts, costs and codes only, never prompts or answers.

## Writing style

Off by default. In the assistant's **Settings**, next to **My instructions**, **Learn my writing style from mail I send** lets Kite learn how you write, per mailbox you send from, so that the drafts it writes for you sound like you.

- **What it learns from.** Only mail you send from the composer yourself: not mail sent through the API, MCP, JMAP or by the assistant, not automatic replies, not mail sent before migration 0070, and not a message Write with Kite inserted text into, also when you reopen that draft later. Kite strips the quoted message, your signature and forwarded mail, and skips messages under five words or over 20,000 characters.
- **What it keeps.** Statistics only, computed in code without a model: how long your messages are, your sentences and paragraphs, how often you ask questions or use exclamation marks, emoji and lists, how formally you address people (Dutch, German, French and Spanish), and up to eight greeting and sign-off forms, each rebuilt only from a fixed list of greeting and sign-off phrases plus `{name}` (`hi {name},`, `gr, {name}`); a greeting or sign-off line with anything else on it is not kept at all. A one-line message counts toward neither. Recent mail counts more: after 300 messages each new one weighs 1/300. No text is kept. The formality measure is a hint: French "vous" and Spanish "ustedes" are also the plural "you", so writing to groups reads as more formal, and it is only named at 70% formal or 30% or less.
- **What the AI sees.** From ten sent messages on, at most 500 characters such as *Writes in Dutch. Usually 40 to 110 words in 2 to 3 paragraphs, with short sentences (about 11 words). Opens with "hoi {name}," and closes with "groet,". Addresses people informally (je).* It is added last to the system prompt, after Kite's rules and every instruction, as a hint the instructions and your own request override: in chat (for the drafts chat writes, using the profile of the chatting user), in Write with Kite (not for **Fix spelling and grammar** or **Translate**, which keep your text's voice; without the formality line for **More formal** and **More casual**) and in the reply drafts Kite writes on its own (using the mailbox reviewer's profile). With the switch off, no profile or fewer than ten messages, every prompt is exactly what it was.
- **Mail you already sent.** Turning it on asks whether Kite should also learn from the last 200 messages you sent from the composer in each mailbox; a background job rebuilds the profile from them, without a model or any spend. Resetting or turning it off while that job runs ends it.
- **Seeing and deleting it.** Per mailbox the settings show how many messages Kite learnt from and exactly the text it gives the AI, with **Reset** to delete that profile. Turning the switch off deletes every profile at once. Nobody else can see your profiles, admins included.

The profile needs migration 0070; until it is applied the switch is hidden and sends are not recorded.

## Write with Kite in the composer

The composer toolbar has a **Write with Kite** button (the sparkles, or ⌘J on a Mac and Ctrl+J elsewhere in the message body). It shows only when the assistant is on, a provider is configured, an external provider is allowed by the primary admin (see [Privacy](#privacy); Workers AI needs no opt-in) and you can send from the selected mailbox.

- **Write.** In an empty message, say what the email should say (up to 2,000 characters) and choose **Write**. In a reply, Kite reads the email you are answering itself, from the mailbox; it never uses the quoted copy in the composer.
- **Rewrite.** With text selected, or with text in the body and nothing selected (then the whole body counts), choose **Shorter**, **Longer**, **More formal**, **More casual**, **Fix spelling and grammar**, **Translate to** a language (your browser's, English, Dutch, German, French, Spanish, or any other up to 40 characters) or a **Custom** instruction (up to 300 characters). A translation replaces the text and keeps the original below it in a quote block, so the recipient can read both.
- **Preview first.** The answer streams into a preview in the panel. Nothing enters your message until you choose **Insert** or **Replace**; **Try again** asks again and **Discard** or Esc stops and closes. After an insert, **Undo** restores the message as it was before; if you edited the message after inserting, the panel says that Undo drops those edits too. If the selected text, or the message, changed while Kite was writing, its text is added below instead, so nothing you typed is lost, and a new email never replaces an image already in the body. Bold, links and images inside a rewritten selection are lost, so the panel says so and offers **Insert below**.
- **What stays untouched.** The quoted message is outside the editable text and is never sent or changed. The signature block is never sent to the provider and always stays at the end.
- **What is sent.** Your request or the text being rewritten, the subject, the display names of the recipients (for the greeting), for a reply the email being answered (from, subject, date and text, up to 8,000 characters, with its links marked as untrusted), and the mailbox's general and **Drafting and composer** instructions and your own. The subject and names, your text and the email are placed in nonce-delimited blocks the model is told to treat as data. The email being answered is found by the reply's Message-ID (the received copy when there are two) or else the newest received message of the conversation; mail the Screener holds, spam, trash and other users' drafts are never used. There are no tools: the model can only return text.
- **Checks.** An answer that ran out of room ("cut off") is refused, so a half sentence is never inserted. Email addresses and links come first: one that is not in your text or your request is removed and the panel says so, including bare domains such as `example.com/pay` and addresses spelled out as `name (at) example (dot) com`; one that only the email being answered contains is kept, with a warning to check it. Then Markdown is turned into plain text, unless your own text used Markdown. An answer that is a note about the text ("Here is…", "Sure, …") is refused with **Try again**, unless the text being rewritten starts that way itself. A rewrite may be at most three times as long as the original and a new email 12,000 characters; the output budget is 900 tokens for a new email or Shorter and up to 3,000 for the other rewrites.
- **Limits and spend.** Each request counts against the same mailbox and install caps as chat and automatic reading, and without model prices against the token allowance chat and Write with Kite share. It reserves its estimate first, so a request over a cap is refused before the provider is called, with a message that names the cap. There is also a per-user rate limit (429 when exceeded). Only the token counts and cost are stored (`ai_usage`, source `compose`); the request and the answer are not, and failures are logged with a code but no content. A request you stop keeps its estimated cost as the recorded spend.
- **Accessibility.** The panel is a modal dialog: focus moves into it, Tab stays inside it, Esc closes it (not the composer) and focus returns to the message body. A screen reader hears that the text is ready once it is done, not every streamed word.

## Summaries in the reader

The reader's toolbar has a **Summarize** button (the sparkles). It summarises the whole conversation; **Summarize this message** in the message's **More** menu summarises the open message alone. The button shows only when the assistant is on, a provider is configured, an external provider is allowed by the primary admin (see [Privacy](#privacy)) and the message can be summarised: never for a message in Spam, in Trash or held by the Screener, or for a draft.

- **The card.** The summary is a card at the top of the reader: one or two sentences, then up to five short points under **Asks**, **Decisions**, **Dates** and **Next steps**. It is plain text, says which model wrote it ("Written by AI (model), may be wrong") and has **Copy** and **Hide**. While a summary is shown, the automatic-reading summary line in Kite's suggestion card is hidden, so the reader never shows two; the suggestion itself stays and For you still lists it.
- **Cached and shared.** A summary is made once and then opens instantly for everyone who can read the mailbox, with no new model call. When the conversation changes (a message arrives or is sent, or is moved to Spam or Trash) the card shows the old text greyed with "New messages since this summary" and **Summarize again**; Kite never makes a new one on its own. Someone with personal **Summaries** instructions (Settings → Assistant, **My instructions**) gets a summary of their own, written with those instructions; everyone else shares one.
- **Language.** The summary is written in the language of the conversation. When that differs from your browser's language, the card offers **Translate to** your language. The translation is made only when you ask, from the summary alone (the mail is not sent again), and is kept next to the summary until the summary is made again.
- **What is sent.** The newest 20 summarised messages of the conversation in full (sender, date, subject and text, without quoted replies, up to 2,500 characters each and 24,000 together) and up to 30 earlier ones as one line each (date, sender, subject), each in a nonce-delimited block the model is told to treat as data, with links marked as untrusted. Only received, sent and archived mail is used; drafts, Spam, Trash, the Screener's held mail and mail judged spam never are. The system prompt carries the mailbox's general and **Summaries** instructions and your own. There are no tools.
- **Checks.** The answer must be the expected JSON; Markdown is turned into plain text, the overview is cut at 400 characters and each point at 200, and a link or email address that the conversation does not contain is removed (a point naming one is dropped). An empty answer or a note about the summary ("Here is a summary…") gets one more try, then an error that says what was wrong. The answer may use up to 1,600 output tokens (plus a reasoning model's headroom): enough for the longest summary the checks keep, in any script.
- **Who and cost.** Anyone who can read the mailbox may make or translate a summary, read-only users of a shared mailbox included, since it shows nothing they cannot read. Each request counts against the mailbox's and the install's spend caps like chat (`ai_usage` source `summary` or `summary_translation`) and, without model prices, against the token allowance chat and Write with Kite share. A request over a cap, or over the per-user rate limit, is refused before the provider is called, and the button is disabled with the reason.
- **Stored.** Unlike chat, summaries are stored (table `ai_summaries`, migration 0072): the text, its language, which model wrote it, who asked, and a digest of the messages it covers. They are deleted with their messages: deleting a message, or moving one to Spam or Trash, deletes its conversation's summaries, and a summary is saved only if every message it covers still exists. Conversation summaries that have been out of date for 30 days are deleted. Summaries are not in backups; after a restore, **Summarize** makes them again.
- **The assistant chat** reads a current conversation summary when it opens a thread (`get_thread`), so it can answer from it.

## One-line summaries in the message list

Optional, per mailbox, and off by default: under **Summaries** in the assistant settings, people who manage the mailbox turn on **One-line summaries in the message list**, choose whether to **Include newsletters and notifications** (off by default) and set a **daily limit** (100 by default, 1 to 1,000 per UTC day). The limit counts requests that ask for a line, not lines shown: a request whose answer had no usable line counts too (as does a repair turn), so the limit bounds what one-line summaries can spend. New mail that qualifies then shows a summary of at most 140 characters, with a small sparkles mark, instead of the first words of the email; the preview is in its tooltip. In conversation view a row shows the line of its newest message that has one. The line arrives a few seconds after the message, without a reload. Each browser can turn the display off under Settings → Appearance (**Show AI summaries instead of previews**) without touching the mailbox setting.

- **Which mail.** Only new mail in the Inbox or a folder: delivered less than 30 minutes ago, or released by a Screener approval (the newest 25 per approval, as for automatic reading); there is no backfill. It must be judged clean by the spam filter, have no phishing warning or phishing sign found by Kite's own checks (also when automatic reading is off), come from a sender that is neither muted nor one of the mailbox's own addresses, have at least 280 characters of text, and not be a newsletter, notification or no-reply mail unless the mailbox includes them. Spam, Trash, the Screener's held mail and drafts never reach the model for a line.
- **One request per message, never two.** When automatic reading already asks the model about the message, the line comes from that same request: it carries one more optional key (`oneLine`) and 60 more output tokens, and without the setting the request is exactly as before. A line that is missing or unusable in that answer is not asked for again. When automatic reading is off or settles the message without the model (a newsletter with **Include newsletters** on, for example), a small request of its own reads the subject and up to 4,000 characters of the latest message, in a nonce-delimited block, with the mailbox's triage model.
- **Gates and spend.** Lines are background work and follow automatic reading's rules: the assistant and the install-wide automatic reading switch, the external-provider opt-in, a paused mailbox, the per-mailbox burst limit, and the mailbox and install spend caps (`ai_usage` source `line_summary`, or `auto_triage_line` when it rides on triage; without model prices, automatic reading's token allowance). A refused line is skipped with the reason, and the row keeps its preview.
- **Checks.** A line is one line of plain text: Markdown and quotes are removed, it is cut at 140 characters, and one with a link or an email address, or one that talks about the email ("Here is…"), is dropped. Mail the model flags as suspicious gets no line, so a confident summary never dresses up a phishing message.
- **Stored.** A line is stored like a conversation summary (`ai_summaries`, kind `line`), shown to everyone who can read the mailbox, and deleted when its message is deleted or moved to Spam or Trash.

## When an AI request fails

Chat, Write with Kite, summaries and their translations, automatic reading and agent drafts share one list of failures (`src/lib/agent/ai-error-utils.ts`). Each has a stable code and a sentence that says what happened and what to do; the provider's own error text is never shown, logged or stored, because it can echo the email.

| Code | What you see |
| --- | --- |
| `timeout` | The AI took too long (60 s). Try again, or pick a faster model in Admin → Agent. |
| `cut_off` | The answer was cut off before it was finished (the provider stopped at the output budget). |
| `provider_rejected`, `provider_auth` | The provider refused the request, or did not accept the API key, with its HTTP status. |
| `provider_unavailable`, `provider_error`, `provider_rate_limited` | The provider had a problem on its side, returned an error without a status, or was busy (HTTP 429). |
| `model_unavailable`, `context_too_long` | The model is not available at the provider, or the email is too long for it. |
| `unusable_answer` | The answer did not pass Kite's checks, with the reason in plain words (for example "it was not in the format Kite asked for"). |
| `spend_cap`, `rate_limited` | A spend cap or token allowance is reached (the message names which one), or too many requests at once. |
| `external_provider_not_allowed`, `assistant_off`, `no_provider` | The primary admin has not allowed the external provider, the assistant is off, or no provider is set up. |
| `provider_key_unreadable` | The saved API key of the provider in use can't be decrypted (`APP_ENCRYPTION_KEY` changed); enter it again in Admin → Agent. |
| `network`, `internal` | Kite could not reach the provider, or something failed in Kite itself. |

- **In the app.** The summary card, the Write with Kite panel and the assistant chat show the sentence with a **Details** disclosure: the code, the feature, the model, the provider, the provider's HTTP status when there was one, and the time. **Try again** appears where trying again can help (not for a setting that has to change first), and the primary admin gets a link to [Admin → Agent](/agent) for a setting that needs fixing. Activity and the assistant's job list show a failed automatic job as its code in words, such as "The AI model did not answer because it took too long (timeout)".
- **Logs.** Every failure is logged once as `ai.failed` with the code, the feature, the model, the provider, the HTTP status, the duration, the token counts and the finish reason, never the prompt or the answer. A cut-off answer from automatic reading, a one-line summary or an agent draft also records its budget: the output cap with the parts added for thinking and module extensions, how thinking was set (off, on at an effort, or left to the provider), whether Kite had already retried, and the output and thinking tokens the provider counted.
- **Recent AI errors.** [Admin → Agent](/agent) lists the last 20 failures with the same fields and the person and mailbox they belong to, so the primary admin can see what failed without server access. They are kept as `ai.error` rows in the audit log (the newest 200; no migration), which no other list shows. Only provider and model failures are kept: a refusal before any provider call (`spend_cap`, `rate_limited`, `external_provider_not_allowed`, `assistant_off`, `no_provider`, `provider_key_unreadable`) still gets its message in the app but is logged at most once a minute per person, code and feature and never kept, so a button pressed over and over cannot push real failures out of the list.
- **Why?** When AI requests failed in the last 24 hours, the primary admin sees "N AI requests failed in the last 24 hours" under **Needs attention** on the [Admin overview](/admin) and in the mailbox's command center. **Why?** next to it groups those failures by code without asking any model (`GET /api/admin/agent/errors/report`, the same `ai.error` rows): for each group the count, first and last time, the features, the providers and models, the HTTP statuses, Kite's sentence for the newest failure, the likely cause and the fix, with a link to the setting that fixes it (the provider in Admin → Agent, automatic reading's opt-in and spend cap, or [AI usage](/ai-usage)). It never shows who or which mailbox, and nothing from the mail. For `cut_off` the cause and fix use what Kite knows: the feature's output cap, the recorded budget (cap, thinking setting, tokens used, retry) or, for failures recorded before budgets were kept, whether the model thinks by default, and then the setting to change, such as clearing the model's reasoning effort or choosing another triage model.
- **Ask AI.** In that dialog, **Ask AI** opens the assistant in a new chat with a written summary of the groups in its input (counts, codes, features, providers, models, statuses, Kite's sentences, its diagnosis and fix, the facts above such as caps and thinking settings, and a note on what each feature asks the model for; never a person, a mailbox or mail), for the admin to read and send. Sending it is an ordinary assistant chat, so the provider, the spend caps and the token allowance apply as usual. From the Admin overview it opens the mailbox first. Ask AI is replaced by the reason and a link to the fix when the assistant could not answer: it is turned off, no provider is set up, the saved key can't be decrypted, the provider is external and not allowed to read mail, or the assistant's own provider is the one failing (a refused key, or its default model missing, with no successful request to that provider since).

## Kill switches

- **Install-wide.** The primary admin can turn automatic reading off for every mailbox with one switch, and can turn external providers off again at any time.
- **Per mailbox.** Set the level to Off, or use **Pause for 24 hours**. While a mailbox is paused, the settings show the end time and a **Resume** button.
- **Assistant off.** Turning the email assistant off stops all of it.

When each switch takes effect differs. Kite checks the automatic-reading switch, a mailbox's Off level and pause, and the daily limit when a queued job starts. A job that has not started yet is skipped. A job that is already running may still finish its remaining model calls, such as a repair, a fallback or a reply draft. The external-provider opt-in is checked again before every model request, so turning it off also stops those remaining calls to an external provider.

## Why Kite skipped a message

**Activity** (assistant panel) lists what Kite did and recent skipped messages with the reason in plain words:

- Automatic reading is turned off for this install, for this mailbox, or the email assistant is off.
- Kite is paused for this mailbox.
- The external AI provider is not allowed to read mail automatically.
- Daily limit reached, daily spend cap reached, or rate limited.
- The message was moved or deleted first.
- The reviewer can no longer read this mailbox.
- A module the step needs is turned off, for example "Calendar is turned off". Kite records this with the reason code `module_disabled` and the module, skips only that step and still runs the others.

When the model is refused (the external provider is not allowed, the rate limit or a spend cap is reached), Kite still runs the module steps that need no model, such as calendar invitations and subscriptions, without the model's answer, keeps their suggestions and lists the message with the reason. The same happens when the model keeps failing on the job's last attempt ("The AI model did not answer; the message was checked without it"), or at once when Kite asked the model only because a module wanted help (that request is never retried). Only when no module step ran is the whole message skipped.

Mail a program sent (`Auto-Submitted`) is normally not read at all. When a module step opts in to such mail and is on for the reviewer and the mailbox, Kite reads it in a steps-only pass: only those steps run, no model is asked, and no summary or reply is suggested. These messages count toward the daily limit.

A module kind can be private to the reviewer: its cards, row badges and For you counts appear only for the mailbox's reviewer, and only the reviewer can accept or dismiss them. Other users with full access see nothing of it.

## Activity and Undo

Every action Kite records, and every action you accept from a suggestion, is written to the action log before it takes effect, with who started it, the status and the reason. Activity shows the log for the mailbox.

Changes you approve in the assistant chat (marking emails read or unread, moving them, creating a folder or filing mail into one, see [Email assistant and MCP](email-assistant-and-mcp.md)) are recorded the same way, with the number of emails and the folder. Undoing one puts back only the emails still where the action left them and says how many went back. Moving mail to or out of Spam also trains the spam filter, and undo takes that training back with the move, using the receipt that very move left (a newer report on the mail keeps it, and the undo is refused until that one is undone) (see [Undoing a report](spam-protection.md#undoing-a-report)); the same holds for **Mark as spam** on a phishing warning, which asks for confirmation first. Before the database update that adds the receipts is applied, undo moves the mail back but cannot untrain it.

Actions can be undone from Activity, from the toast or from the chat card for 7 days. Undo needs the same permission as the action, and undoing a sent reply or RSVP step is limited to the person who made it. An undo is itself logged as a new row.

## Phishing warnings

A message with phishing signs gets a red warning in the reader that lists them in plain words: a link that opens a different address than it shows, failed sender checks, an attached web page that asks for a password, an attached program, a request to whitelist the sender, a match on URLhaus or ThreatFox when the operator turned [those lookups](spam-protection.md#urlhaus-and-threatfox-lookups-optional) on, and what the model found. The model can add reasons but never removes one Kite found itself. The warning offers **Mark as spam**, which moves the message to Spam and can be undone, **Report phishing**, which also blocks the sender and trains the spam filter harder (see [Report phishing](spam-protection.md#report-phishing)), and **Not phishing**. Reporting a message from its **More actions** menu closes its warning too.

The model's suspicion alone does not show a warning. It needs a sign in the message itself: one of the signs above, or a weaker one such as a link through a URL shortener. The model is told the authentication results, whether the sender is on one of your domains and where the links go, so an authenticated password reset or sign-in code from a service you use is normal mail to it. When the model is suspicious and the message shows no sign, Kite still writes no reply draft for it and Activity records `model_flag_unconfirmed`.

Kite also trusts some senders more. For a known contact or a sender you marked **Not phishing** whose mail passed sender authentication, or mail from one of the install's own domains that passed DMARC without copying a contact's name, the model's suspicion is not enough even with a weak sign (Activity records `model_flag_trusted_sender`). Signs Kite found itself, such as a misleading link or a failed check, always warn, whoever the sender is.

**Not phishing** closes the warning and adds the sender to the mailbox's trusted senders. The toast offers Undo, which opens the warning again and removes the sender.

The mailbox's **Trusted senders** are listed in the assistant settings under **Automatic reading**, for people with full access to the mailbox. **Remove** takes a sender off the list and **Add** puts an address on it, up to 500 per mailbox. Each change is saved at once, apart from **Save automatic reading**, and only for that one address, so a change made elsewhere in the meantime is kept. Trust still needs mail that passes sender checks. **Muted senders** sits below it and works the same way.

## Calendar invites

When a message carries an invitation (ICS), the reader card shows the event and offers **Accept**, **Decline** and **Propose new time**. Kite checks your calendar for conflicts and can suggest free slots over the next 7 days.

- Replies go to the organizer named in the invitation only, never to other attendees. If the invitation names no organizer, Kite does not offer a reply.
- Accepting adds the event to your calendar and sends the RSVP. An updated invitation offers **Update event**, and a cancellation offers **Remove from calendar**.
- If Kite cannot confirm who sent the invitation (no passing DKIM or DMARC result), the card shows an **Unverified sender** warning. It also warns when the organizer's address differs from the sender's. Check both before you reply.
- Invitation handling is part of the Calendar module (see [Modules](modules.md)). A mailbox's calendar capability switch turns it off for automatic reading in that mailbox only. When the owner turns Calendar off, or restricts it for you, Kite skips the invitation step with `module_disabled`, hides invitation suggestions and their counts, and refuses to accept them or to undo an invitation action until Calendar is back on. Nothing is deleted. Proposed times use the working hours of your first enabled booking page when Booking is on, and Monday to Friday, 09:00 to 17:00 in your time zone otherwise.

## Subscriptions (Money Watch)

Money Watch is a module (see [Modules](modules.md)). It reads receipts, invoices, renewal and trial notices, refunds and failed-payment mail, including mail a program sent (`Auto-Submitted`), bulk and no-reply senders, and offers one **subscription** card per message, for example "Netflix $17.99/month, renews 1 Nov. Track it?". The card shows the amount, cycle and renewal date, the document the message is (an invoice, payment, credit note or refund), the attachment that holds it and, when the message has an `https` `List-Unsubscribe` header, the host of its cancel link.

- **Track** starts tracking the subscription, or updates the tracked one from a later invoice (a new renewal date, and "now $19.99/month, up from $17.99" when the price changed), and records the invoice or payment.
- **Record it** appears for a credit note or refund from a vendor you already track. It records the document, which lowers your paid total, and never changes the price or renewal date.
- **Mark urgent** appears when a payment for a tracked subscription failed. It flags the subscription under Needs attention and in the sidebar count.

Nothing is tracked or recorded until you click, every choice shows a toast with Undo, and undo opens the card again. Cards are private to the mailbox's reviewer: other users with full access to the mailbox do not see them, and tracked subscriptions belong to the reviewer alone. A sender without passing authentication gets the **Unverified sender** warning, and phishing or spam mail gets no card.

Each recorded document is one entry in the subscription's history on the Subscriptions page (`/finance`): its type, date, the period it covers when stated, the amount, a link to its conversation and **Open document** for the attachment. The entry points to the attachment in the message; Kite never copies it. You can also track a subscription or add a document from any message through the reader's **More actions** menu, even with automatic reading off.

Detection is deterministic first: subject, sender and body phrases, amounts, cycles and dates, the attached invoice (including the text of a plain PDF), and earlier mail from the same sender. Kite sends a message to the model for Money Watch only when it looks like a receipt and the detector left the amount, the cycle or the date empty. That request is the normal triage request with a few extra fields, under every limit above: the external-provider opt-in, the daily and rate limits and both spend caps. The model's values only fill empty fields, never override what Kite read itself and never supply the cancel link. A card marks the values the assistant read, and says "Check the amount before tracking" when the model read a different amount or currency. The cancel link comes only from the `List-Unsubscribe` header and only opens in your browser when you click **Cancel before …**; Kite never fetches it.

Each mailbox has a **Subscriptions in receipts (Money Watch)** switch in its automatic reading settings, on by default. Turning it off stops Money Watch reading that mailbox and asking the model for it.

## Assistant chat and modules

Chat offers the core email tools plus the tools of the modules that are on for you. With Money Watch on, `list_subscriptions` lists your tracked subscriptions, their renewals and the totals paid in the last 12 months, in chat and over MCP with the `mcp:finance-read` scope. The calendar tools (`get_schedule`, `search_events`, `get_event`, `create_event`, `update_events`, `delete_events`, `find_free_time`, `get_calendars`) and the calendar part of the instructions belong to the Calendar module. They follow only the Calendar module and your own module access, not a mailbox's calendar capability switch. With Calendar off for you, chat has no calendar tools.

In chat, `create_event` saves at once, but `update_events` and `delete_events` never act on their own: the tool returns a proposal card listing each event by title and start time with what would change (or that every occurrence of a series would be deleted), and nothing changes until you choose **Approve changes** or **Approve deletion** under it. The approval runs the Calendar module's own tool as you, so it still checks that the events are yours and that Calendar is on for you. This holds for any module tool that changes, deletes or sends (`needsChatApproval` in `src/lib/modules/capability-utils.ts`); a module names a preview service (`approval.preview`) for the card's lines. An email that asks the assistant to cancel or move a meeting therefore cannot do so without your click. If an event was edited after the proposal (its preview `version` no longer matches), the approval is refused and the card stays as it was, so you ask again and see the current event. A new description is quoted on the card like a new title. Approved calendar changes have no Undo.

The `open_page` tool gives you a link to a page in Kite, such as the inbox, Settings or a date in Calendar. The model can only pick from the pages that are on for you, and Kite builds the link itself, so it always points inside Kite. Nothing opens until you click the link. `open_page` exists only in chat. Automatic reading never gets tools.

## Evaluating a model

`node scripts/agent/injection-eval.mjs` runs a corpus of hostile messages through the real triage and draft pipeline against a model you choose and exits non-zero on a policy breach. `node scripts/agent/fake-model-server.mjs` starts a local fake model for manual checks, which needs `AI_ALLOW_INSECURE_LOOPBACK` outside production. With that flag, `AI_TEST_TIMEOUT_MS` shortens the Summarize timeout (the e2e server sets 5 seconds), so a spec can show the timeout message; it is ignored in production. Neither runs in CI against a real provider.
