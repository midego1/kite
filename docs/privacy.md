# Privacy and data handling

This page describes what a Kite deployment stores, for how long, and how data leaves or is removed. Each claim names the source file it was checked against. See [PII handling](pii-handling.md) for how to treat evidence and backups.

## Controller

In a self-hosted deployment the operator is the data controller. The Kite project receives no data from your deployment except pseudonymous usage statistics, which are on by default, explained at setup and easy to turn off at setup, in Admin → General or with `KITE_TELEMETRY=0` (see [Usage statistics](#usage-statistics)). There is no update check or licence check, and nothing is sent before setup is finished.

The processors depend on how you configure the deployment:

- Cloudflare: Workers, D1, R2, Queues, Email Routing and Email Sending, Analytics Engine, and Workers AI or Turnstile when you use them.
- Resend or Amazon SES, when a domain uses them for sending or receiving (`src/lib/email/outbound-provider.ts`, `src/lib/aws/`).
- Anthropic's Messages API or an OpenAI-compatible AI endpoint (Haimaker, OpenAI, OpenRouter, Groq or a custom base URL), when the assistant is configured to use one (`agent_*` columns of `app_settings` in `src/db/schema/index.ts`, `src/lib/agent/provider-constants.ts`).
- Gravatar (`gravatar.com`): when Kite creates a contact it requests that contact's avatar by the SHA-256 hash of the normalised address, so Gravatar sees the hash (`src/lib/contacts/gravatar.ts:7-24`, called from `src/lib/contacts/service.ts:50`). Hashing is not anonymisation for guessable addresses.
- abuse.ch URLhaus (`urlhaus-api.abuse.ch`) and ThreatFox (`threatfox-api.abuse.ch`), only when the operator sets `URLHAUS_AUTH_KEY` (or `ABUSE_CH_AUTH_KEY`) or the owner saves an Auth-Key under Admin → General: for incoming mail that already shows a phishing risk, from a sender who is neither a saved contact nor someone the user wrote to (unless authentication failed), Kite sends URLhaus up to five links exactly as they appear, ThreatFox up to five lookup terms derived from those links (host names, their registrable domains, or IPv4 addresses with the link's port as `host:port`, never paths or query strings), and both the SHA-256 hashes of up to three attachments, never file content (`src/lib/spam/providers/abuse-ch-utils.ts`, `src/lib/spam/providers/urlhaus-utils.ts`, `src/lib/spam/providers/threatfox-utils.ts`, `src/lib/spam/providers/abuse-ch.ts`, `src/lib/spam/engine.ts`). A link can carry a personal token that identifies the recipient. The owner's **Test key** in Admin → General, and the check before **Save key** stores a key, send only `example.com`. See [Spam protection](spam-protection.md#urlhaus-and-threatfox-lookups-optional).
- Cloudflare's public DNS-over-HTTPS resolver (`cloudflare-dns.com`): domain DNS auditing sends each audited hostname and record type there. This happens on Workers and on Node/Docker alike, even when no Cloudflare credentials are set (`src/lib/dns-query.ts:15-41`, `src/lib/domains/dns-audit.ts:40`).
- S3-compatible stores you add under Admin → Storage (Amazon S3, Backblaze B2, Wasabi, Hetzner, MinIO or another provider): the classes you route to a store (raw mail and attachments, Drive files, database backups) are written there, and with Drive routed there, browsers upload to and download from the store directly with short signed URLs, so the provider sees the user's IP address. Each such provider is a processor for that data.
- The Kite project's statistics collector at `kite-telemetry.midego.net`, unless the owner turned usage statistics off (at setup or under Admin → General) or the operator set `KITE_TELEMETRY=0`: one pseudonymous heartbeat a day with the fields listed in [Usage statistics](#usage-statistics). For that data Michiel de Gooijer (midego), who runs the collector, is the controller, not a processor of yours.
- Destinations you configure yourself: webhook URLs receive the events you subscribe them to, IMAP import connects to the server you enter, and the operational alert webhook (Slack, Discord, ntfy or another endpoint) receives the app name, rule ids and names, counts, links to Kite pages and the send time, with no addresses, ids or error text (`src/lib/alerts/webhook-utils.ts`; see [Operational alerts](operations.md#operational-alerts)).

Remote images in mail reach their hosts only after the reader allows them, with **Show images** on a message or **Always show remote images** under Settings → Inbox. On Workers the reader then loads them from `GET /api/remote-images` on Kite's own origin, and the Worker fetches the image: the image host sees a Cloudflare address and the `Kite-Remote-Images/1.0` user agent, never the reader's IP address, cookies or referrer, and it still learns that the message was opened. The Worker fetches only a URL that an `<img>` in a message the signed-in user can read names, over https on the default port and never to an IP address, a local or reserved name or Kite's own host; it accepts PNG, JPEG, GIF, WebP and AVIF up to 5 MiB, follows at most three redirects and keeps nothing (`src/app/api/remote-images/route.ts`, `src/lib/remote-images/fetch-utils.ts`). On Node/Docker this proxy is off, because that server could reach its own private network, and the browser loads remote images directly from their host as before.

The Node/Docker runtime keeps D1 and R2 equivalents as local files and uses no Cloudflare service for storage or queues. It still calls the Cloudflare API when you set Cloudflare credentials, and it always uses the DNS-over-HTTPS resolver above.

## Usage statistics

**On by default, and the owner is told before anything is sent.** Only the primary admin decides:

- **New installs.** The last step of the first-run setup has a **Usage statistics** section that says what is sent, how often, to whom and for how long, with a **Send usage statistics** switch that is on. Turning it off before **Create account** means no install id is ever made and nothing is sent. Nothing is recorded or sent before the account is created: the choice and, when it is on, the install id are stored only once setup is complete (`recordSetupTelemetryChoice` in `src/lib/telemetry/state.ts`, called from `POST /api/auth/register`). The first report follows at the next 02:00 UTC.
- **Installs that existed before this change** (and any install whose setup did not carry the switch, such as one created through the API). Kite does not start sending by itself. The first time the primary admin opens Kite after the upgrade, a one-time notice in the sidebar and above the Admin pages says *"Kite will start sending usage statistics on &lt;date&gt; unless you turn them off"*, with **Turn off** and **Keep on** buttons. The date is fixed when the notice is first shown: the UTC day after 14 full days, so the first report comes at least 14 days later. **Turn off** records the decision and nothing is ever sent; **Keep on** starts with the next daily report; closing the notice keeps the date. Until that day the install sends nothing and has no install id; on that day it gets one and the 02:00 UTC report goes out. An owner who never signs in is never told, so that install never starts.
- **An explicit off is final.** An owner who turned statistics off, before or after this change, stays off: no notice, no start date, nothing turns them on again except the owner's own switch. Migration 0074 records every choice made before it as such (`decision` in `telemetry_state`).

The primary admin can change it at any time under **Admin → General → Usage statistics** (`PUT /api/admin/telemetry`; every choice is recorded in the audit log as `telemetry.enabled` or `telemetry.disabled` and listed under Admin → Activity, including the one made at setup). The card lists exactly the fields below, the address they go to, the start date while one is pending, the install id with a **Copy ID** button and the UTC day of the last attempt (it is recorded before sending, so it does not prove the collector received it).

The statistics are **pseudonymous, not anonymous**: the random install id links one install's daily reports to each other, and the request that carries them can reveal more than the report (see **Where**).

**Who.** The collector at `kite-telemetry.midego.net` is run by **Michiel de Gooijer (midego)**, the Kite maintainer, who is the controller for the data it receives. The legal basis is legitimate interest (Art. 6(1)(f) GDPR): knowing how many installs run which version, runtime and modules, and roughly how large they are, to decide what to maintain and fix. The reports are limited to ranges and carry no names, addresses or content; owners are told before the first report (at setup, or by the notice 14 days ahead) and can object at any time, without giving a reason, by turning statistics off, which also erases what was sent (see **How to turn it off**). Cloudflare hosts the collector (Workers and D1) as processor. Questions, access, objection and erasure requests: **privacy@midego.net**, with the install id from the card. (Maintainer check: `midego.net` receives mail through Cloudflare Email Routing, so confirm that `privacy@midego.net` has a routing rule and that a test message arrives before this section is relied on, and again whenever the routing changes.)

**When.** Once a day, from the 02:00 UTC cron on Workers and the same hour on Node/Docker (`worker.ts`, `server/runtime/scheduler.ts`), at most one heartbeat per UTC day. A heartbeat that fails or takes longer than 5 seconds is not retried until the next day. There is no other report: nothing is sent at setup, at sign-in or when a setting changes. An install without a decision (setup not finished, or an existing install before its start date) makes no request from either cron path, and an install whose owner turned statistics off never does (`tests/telemetry-cron.test.mjs`, `tests/telemetry-decision.test.mjs`).

**What.** One JSON object, `telemetry_schema_version` 2, built only by the allowlist in `buildHeartbeatPayload` (`src/lib/telemetry/telemetry-utils.ts`, tested in `tests/telemetry.test.mjs`). Counts are never sent as numbers, only as the range they fall in:

| Field | Value |
| ----- | ----- |
| `telemetry_schema_version` | `2` |
| `install_id` | A random UUID (`crypto.randomUUID()`) made when statistics are turned on: when setup completes with the switch on, on **Keep on**, or on the notice's start date. Turning them off deletes it; turning them on again makes a new one. It is not derived from anything. |
| `version` | The Kite release, such as `2026.10.26.0`, or `unknown` |
| `runtime` | `workers` or `node` |
| `users_total` | Accounts that are not disabled |
| `users_active_1d`, `users_active_7d`, `users_active_30d` | Accounts that signed in (a new session) or made an audited action (reading, sending, deleting, a setting) in the last 1, 7 or 30 days |
| `mailboxes_total` | Mailboxes |
| `mailboxes_active_1d` | Mailboxes that received a message, or sent one successfully, in the last day |
| `inbound_1d` | Messages received in the last day, including spam and imported mail |
| `outbound_1d` | Messages written in the last day and sent successfully (status `sent`: not drafts, queued or failed sends) |
| `modules_enabled` | The ids of the modules that are on for the install, such as `calendar` or `drive` |

The account and mailbox fields are one of `0`, `1`, `2-5`, `6-20`, `21-100` or `100+` (more than 100); the message fields are one of `0`, `1-10`, `11-100`, `101-1000` or `1000+` (more than 1,000). The collector refuses any other value, and it refuses version 1 reports, which carried exact counts. A heartbeat never contains user, mailbox or message ids, names, email addresses, domains or host names, `APP_URL`, IP addresses, message content or error text (`src/lib/telemetry/heartbeat.ts`).

**Where.** An HTTPS `POST` to `https://kite-telemetry.midego.net/v1/heartbeat` (`DEFAULT_TELEMETRY_URL` in `src/lib/telemetry/telemetry-utils.ts`), and to no other address unless `KITE_TELEMETRY_URL` is set; redirects are never followed (`redirect: "error"`). The collector is `deploy/telemetry-collector/` in this repository. Set `KITE_TELEMETRY_URL` to send heartbeats to another https collector instead. An empty `KITE_TELEMETRY_URL`, a value that is not an https URL, or one naming a `.invalid` host means nothing is sent. The card shows the address in use.

The request can say more than the report, and Kite cannot change that:

- On **Cloudflare Workers**, Cloudflare adds a `CF-Worker` header to every outgoing request, naming the zone the Worker runs on: your domain, or your `workers.dev` subdomain. Kite cannot remove it. The request comes from a Cloudflare egress address.
- On **Node/Docker**, the request comes from your server's IP address.
- The collector does not read, log or store the `CF-Worker` header or the user agent, and never logs or stores the IP address; it has Workers Logs turned off. Only an erasure request (`DELETE /v1/installs/<id>`) uses the connecting address, as the key of its per-address rate limit, which Cloudflare keeps for about a minute. Cloudflare, which runs the collector's zone, still sees the connecting address to route the request, and Cloudflare's own zone analytics for `midego.net` may record a sample of requests with their IP addresses under Cloudflare's retention.

**What the collector keeps, and for how long.** One row per install and UTC day with the fields above, dated by the collector (no time of day). Those rows, the only place the install id is stored, are kept for **90 days**. A daily cleanup then counts them into totals per day (installs, and installs per version, runtime, module and range) without any install id, and deletes them; the totals are kept. Nothing about the request is stored.

**Public totals.** `https://kite-telemetry.midego.net/v1/summary` answers the totals to anyone: installs that reported in the last 30 days by version, runtime, module and range, and the number of reporting installs per day. It never contains an install id, so a reporting install visibly adds to it. Small groups are hidden: until at least 10 installs reported in the last 30 days it shows only that number, and after that any count below 5 is shown as `"<5"`. It is recomputed once a day (after the 90-day cleanup), so an erasure shows in it the next day.

**How to turn it off.** At setup, turn off **Send usage statistics** before **Create account**. On an existing install, press **Turn off** on the notice, or switch it off on the card under Admin → General. That deletes the install id at once and then, best effort, asks the collector to erase every report of that id (`DELETE /v1/installs/<id>`; knowing the random id is enough). The request is made only when a heartbeat was ever attempted with that id. If the collector cannot be reached or does not confirm, the opt-out still stands, Kite logs `telemetry.erase_failed`, and the card shows the id once with a **Copy ID** button so you can send it to privacy@midego.net. Operators can decide for the deployment: set `KITE_TELEMETRY=0` (also `false`, `off` or `no`) to keep statistics from being turned on or sent, whatever the owner chose. The setup switch is then off and locked, the notice never appears, a pending start date passes without effect, and the card's switch can still be turned off, which deletes the stored id and makes the erasure request above. No value of `KITE_TELEMETRY` turns statistics on. An empty `KITE_TELEMETRY_URL` sends nothing either (and shows no notice). Before migration 0071 is applied statistics stay off; before 0074 nothing starts by itself and the notice is not shown.

**A report in flight.** A heartbeat checks the choice again right before it posts, but an opt-out can land in the few milliseconds between that check and the collector storing the report, after the opt-out's own erasure request has arrived. So once the collector accepts a report, the heartbeat reads the choice once more and, if the id it sent is gone, sends the erasure request for it itself (`src/lib/telemetry/heartbeat.ts`). A report whose answer never arrives (a timeout) is not covered; send the id by email if that matters to you.

**Copies of the database.** The install id lives in the database, so a copy of it (the SQLite file on Node, a D1 Time Travel restore or a copied D1 database) carries the same id, and two deployments running from copies would report as one install. Kite's own JSON backups leave `telemetry_state` out. A restore never brings back a pending start date or a dismissed notice either. To give a copy its own id, turn statistics off and on again there: turning them off deletes the id and turning them on makes a new one (`setTelemetryEnabled` in `src/lib/telemetry/state.ts`).

## What is stored where

| Where                      | What                                                                                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 (SQLite on Node)        | Every table in `src/db/schema/index.ts`: accounts, mailboxes, message metadata and bodies, contacts, settings, sessions, API keys, audit logs. Grouped in `src/lib/backups/table-groups.ts`. |
| D1 (SQLite on Node)        | Money Watch (module `finance`, migration 0063), in `src/db/schema/finance.ts`. `finance_subscriptions`: per user, the vendor, plan, amount, currency, cycle, renewal and trial dates, status, reminder settings, the `https` cancel link from the sender's `List-Unsubscribe` header, and links to the source and latest message, the sender's contact, the mailbox and the calendar reminder event. `finance_charges` (the document ledger): per tracked subscription, one row per invoice, payment, credit note, refund or failed payment, with its type, amount, currency, document date, the period it covers when stated, its source message and the id of the attachment that is the document. The ledger stores attachment references only, never file content and never extracted PDF text; opening a document goes through the normal attachment route and its access check. No card numbers and no message excerpts are stored. Rows belong to one user (the mailbox's reviewer, or whoever added them by hand) and are shown only to that user: in the page, the API, search, refs, the `list_subscriptions` tool and webhooks to that user's own endpoints. Admins do not see them in the UI; they are in admin backups (`mail` group) like other user data. |
| D1 (SQLite on Node)        | Drive (module `drive`, migration 0064), in `src/db/schema/drive.ts`. `drive_items`: per owner, each file and folder with its name, parent folder, size, content type, the store and object key of its contents, when it was trashed, and for a file saved from mail the id of the source attachment; unfinished uploads keep the file's size and modification time (to resume it) and their parts in `drive_upload_parts`. `drive_shares`: who an item is shared with and whether they can view or edit. `drive_links`: per public link a SHA-256 hash of its token (the token itself only sealed with `APP_ENCRYPTION_KEY` when that key is set), a password hash when it has one, the expiry, when it was revoked, when it was last opened and how often its file was fetched; no visitor IP, address or user agent is stored. `drive_settings` and `drive_user_quotas` hold the admin defaults and per-account storage overrides. Files are visible only to their owner and the people they are shared with; admins do not see other users' files in the UI, but the metadata is in admin backups (`drive` group). |
| D1 (SQLite on Node)        | Object storage (migration 0065), in `src/db/schema/storage.ts`. `storage_stores`: each S3-compatible store's name, provider, endpoint, region, bucket and its access key pair, sealed with `APP_ENCRYPTION_KEY` (a store cannot be saved without it), plus the result of its last check. `storage_routes`: which store each kind of data (mail, Drive, backups) is written to and the previous one while data is moved. `storage_migrations`: progress of each move, with the admin who started it. No object content and no file names. When a kind of data is routed to a store, the objects listed below as R2 for it are kept in that bucket instead. |
| D1 (SQLite on Node)        | Assistant instructions (migration 0069). `mailbox_agent_settings` holds a mailbox's instructions for chat, drafting and summaries next to its general ones, readable by the mailbox's users and managed by those who can manage it. `user_ai_settings`, in `src/db/schema/agent-writing.ts`, holds each user's own instructions (general, chat, drafting, summaries) and the writing-style opt-in (off by default). Personal instructions are shown only to their user, admins included, and are sent to the AI provider only in that user's chat requests and in the reply drafts of mailboxes they review. Both are in admin backups (`assistant` group) **in plaintext**: anyone who can download a backup can read every user's personal instructions, even though the app never shows them to an admin. |
| D1 (SQLite on Node)        | Writing style profiles (migration 0070), in `src/db/schema/agent-writing.ts`. `writing_style_profiles`: per user and mailbox, only while that user has turned on **Learn my writing style from mail I send**, running statistics of the mail they sent from the composer (word, sentence and paragraph counts, how often they ask questions or use exclamation marks, emoji and lists, how often they greet and sign off, how formally they address people) and up to eight greeting, sign-off and language forms with their counts. A form is rebuilt only from a fixed list of greeting and sign-off phrases plus the placeholder `{name}` (`hi {name},`, `groet,`); a line with anything else on it (a sentence, a phone number, a company) gives no form, so no name, address, number or other text of a message is stored. `composer_sends`: one row per message sent from the composer with a session and without text Write with Kite inserted, holding only the message id, the sender, the mailbox and when. It is written whether or not the sender opted in, so that turning the profile on later can learn from earlier mail under the same rule; a send Kite helped write leaves no row, so nothing records that someone used Write with Kite. The rows stay after Reset and after turning the profile off, for the same reason (turning it on again can rebuild from them); they go with the message, the user or the mailbox. `ai_assisted_drafts`: the ids of drafts Write with Kite inserted text into, so a reopened draft is never learnt from; a row goes with its draft when it is sent or discarded. Profiles are shown only to their user, admins included; the rendered description goes to the AI provider only inside that user's own chat, Write with Kite and (as the mailbox's reviewer) automatic reply draft requests, which already send mail to the same provider. All three tables are in admin backups (`assistant` group) **in plaintext**: anyone who can download a backup can read every user's profile statistics and forms, even though the app never shows them to an admin. |
| D1 (SQLite on Node)        | Usage statistics (migration 0071), in `src/db/schema/telemetry.ts`. `telemetry_state`: whether the owner turned usage statistics on, the random install id while they are on, and the UTC day of the last heartbeat. Not in backups, so a restore into another deployment does not copy the install id. |
| D1 (SQLite on Node)        | AI summaries (migration 0072), in `src/db/schema/agent-summaries.ts`. `ai_summaries`: the summaries the reader's **Summarize** button made and their translations, and the one-line summaries of new mail shown in the message list where a mailbox turned them on (kind `line`, at most 140 characters, no user recorded), per mailbox and conversation (or message): the summary text (an overview and up to five points), its language, the model that wrote it, the user who asked, a digest of that user's personal summary instructions (empty without any) and a digest of the ids of the messages it covers. A summary repeats what its messages said and is shared with everyone who can read the mailbox, read-only users included; drafts, Spam, Trash and the Screener's held mail are never summarised. Rows are deleted with their messages: database triggers remove a conversation's summaries when one of its messages is deleted or moved to Spam or Trash, and a summary is saved only while every message it covers still exists. The table is derived data and is **not** in backups (`INTERNAL_TABLES` in `src/lib/backups/export.ts`). |
| R2 (files on Node)         | Raw inbound MIME at `inbound/<timestamp>-<id>.eml` (`src/lib/email/inbound.ts`, `src/lib/email/intake.ts`).                                                     |
| R2 (files on Node)         | Drive file contents at `drive/<itemId>` (`driveObjectKey` in `src/lib/drive/name-utils.ts`). A file saved from mail is a separate copy of the attachment. Anyone holding an active public link can download the file or the files in the linked folder until the link expires or is revoked. |
| R2                         | Raw MIME of drafts imported through JMAP at `drafts/<messageId>.eml` and pending JMAP uploads under `jmap-uploads/` (`src/lib/jmap/blobs.ts`). Drafts composed in the app keep their text and HTML bodies in D1 and have no raw MIME or body object in R2. Attachments uploaded to or forwarded onto a draft are stored in R2 like other attachments (`src/app/api/drafts/route.ts:64-89`, `src/app/api/drafts/[id]/attachments/route.ts:46-58`, `src/lib/email/attachments.ts:68-89`). |
| R2                         | Attachments at `attachments/<messageId>/<id>/<filename>` (`src/lib/email/attachments.ts`).                                                                      |
| R2                         | Database backups under the prefix `backups/database` (`BACKUP_PREFIX` in `src/lib/backups/utils.ts`).                                                           |
| R2                         | Avatars at `avatars/<userId>` and `mailbox-avatars/<mailboxId>`, the branding icon at `branding/app-icon`, and Gravatar copies of contact avatars at `contact-avatars/<userId>/<url-encoded contact address>` (the object key contains the contact's address; `src/lib/contacts/avatar.ts`, `src/lib/contacts/gravatar.ts`). Uploaded avatars get a small preview object at `<key>:preview` (`src/lib/avatar-images.ts:4-6`). Gravatar previews are best-effort. The branding icon is stored at `branding/app-icon` without a preview. |
| R2                         | Operational alert state at `system/alert-state.json`: the baseline time, last email and attempt times, and per rule a fingerprint and the time it last alerted (`src/lib/alerts/state.ts`). Fingerprints are operational values: the backup rule's lists the ids of failed backup rows, the webhook rule's is a timestamp, the others are the word `active`. No addresses, payloads or error text. |
| Realtime socket (Durable Object, or the Node stand-in `server/runtime/realtime.ts`) | New-message events for users who can access the mailbox (owner, domain owner, shared-mailbox delegates): the message id, mailbox id, sender address, sender display name, subject, and a one-time code the server detected in the subject or body with conservative heuristics (`src/lib/email/one-time-code-utils.ts`). The code is detected per delivery, sent only to those users, never stored in a database column, and never logged; the event is dropped for messages placed in Spam. The browser notification that carries it can be switched off per browser under Settings → Inbox → Browser notifications (`src/hooks/message-realtime-utils.ts`). |
| Workers Logs / stdout      | Two kinds of output. Structured JSON lines from `createLogger` (`src/lib/logger.mjs`) replace the value of any field whose key matches `authorization`, `cookie`, `password`, `secret`, `token`, `signature`, `body`, `headers`, `recipient`, `sender`, `forwardTo` or `email` (case-insensitive) with `[REDACTED]`, and log an `Error` as its type and a code-shaped `code` only. The redaction goes by key name, not by value: an address under a key such as `to` or `address` would not be redacted, and no current structured event uses one. Plain `console.*` calls do not go through the logger and are not redacted. Several of them include addresses or error objects: `src/lib/email/inbound.ts` logs the inbound recipient (`payload.to`) and, when forwarding, the forward destination; `src/lib/email/incoming.ts` logs the recipient or the forwarding source and destination when routing or forwarding fails; and failures passed as `console.error(..., error)` print the full error, which can contain its message. See [Mission readiness](mission-readiness.md) for the structured events. |
| Analytics Engine           | Labels and numbers only: event, service, route template, provider, queue or webhook event name, HTTP method, outcome, status class, status code, duration and attempt count. Labels are restricted to short strings of letters, digits and `_.:/[]{}-`, and anything else is stored as `other` (`safeLabel` in `src/lib/metrics.mjs`). Points from the main Worker carry the deployment version id (`CF_VERSION_METADATA.id`, `worker.ts:97`) when the `CF_VERSION_METADATA` binding exists. Relay points and points without that binding carry an empty version value. That id identifies a Worker deployment, an operational value shared by all users; signed-in users also receive it from `GET /api/version`, which the "Kite was updated" notice compares in the browser and nothing stores. The metric call sites pass no user, mailbox, message or database ids, addresses, URLs or error text. Node/Docker records no metrics (`METRICS` is a no-op in `server/runtime/env.ts:60`). |

Backups contain database records, including sensitive authentication and configuration tables, but not the R2 objects: Drive file contents, like attachments and raw mail, are not in a backup, only their names, folders, shares and links. Treat them as confidential.

## Retention

| Data                                                                       | Rule                                                                                                                                                                                              | Source                                                |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Trash and Spam messages                                                    | Per user setting `users.trash_retention_days`. Settings offers 7, 14, 30, 60 or 90 days; the API accepts any whole number from 1 to 365. Unset means never delete automatically. Runs on every cron trigger, at most 200 messages per run across all users. | `src/lib/email/trash-retention-utils.ts`              |
| Database backups                                                           | `backup_settings.retention_enabled` defaults to off. When on, completed or failed backups older than `retention_days` (default 30) are deleted, on runs where no new backup is due. ## Export

- `GET /api/export/messages`: a signed-in user exports their messages.
- `GET /api/backups/[id]/download`: the primary admin downloads a database backup.
- JMAP (`src/lib/jmap/`): clients with an API key that has the `jmap` scope read mail.
- `GET /api/v1/messages`: an API key with the `read` scope lists messages.
- The assistant's MCP endpoint exposes mail to a connected client; see [Email assistant and MCP](email-assistant-and-mcp.md).

Import goes the other way: `POST /api/import/messages`, `POST /api/import/imap` and `POST /api/import/jobs`.

## Deletion

- **Messages.** A message goes to Trash, then is deleted permanently: "Delete forever" through `POST /api/messages/bulk`, "Empty Trash" or "Empty Spam" through `POST /api/messages/empty`, or the trash retention rule above. Permanent deletion also removes the attachment and raw MIME objects from R2 (`src/lib/email/permanent-delete.ts`).
- **Mailboxes.** `DELETE /api/mailboxes/[id]` and `DELETE /api/v1/mailboxes/[id]` remove a mailbox, its messages and their stored objects through a background purge (`src/lib/mailboxes/delete.ts`).
- **Domains.** `DELETE /api/domains/[id]` removes the domain's mailboxes the same way, plus the Cloudflare routing and DNS configuration Kite created (`src/lib/domains/cloudflare-cleanup.ts`).
- **Money Watch.** The user removes a subscription (with all its documents) or a single document from the Subscriptions page (`DELETE /api/finance/subscriptions/[id]`, `DELETE /api/finance/documents/[id]`). Removal can be undone for 7 days, so the action log (`agent_actions`) keeps a snapshot of the removed rows until it is pruned after 180 days. Deleting a message permanently keeps the documents' type, amount and dates but drops their link to the message and with it the link to the attachment; deleting a mailbox clears the subscription's mailbox link. Turning Money Watch off keeps everything. The tables cascade from the user row, which is only disabled, never deleted (below).
- **Drive.** The owner moves a file or folder to the trash and deletes it forever from there (`DELETE /api/drive/items/[id]`), which removes the rows, shares, links and stored contents of the item and everything inside it; otherwise the retention rule above does it. Revoking a public link (`DELETE /api/drive/links/[id]`) ends it at once. Turning Drive off keeps everything, and a disabled account's public links stop working.
- **User accounts cannot be deleted. They can only be disabled** (`PATCH /api/accounts/[id]` and `PATCH /api/v1/accounts/[id]` with `disabled: true`). A disabled account cannot sign in, but its row, its audit entries and any mailboxes it owns remain until those mailboxes are deleted (audit entries are never deleted). The primary admin cannot be disabled. If you must erase a person's data, delete their mailboxes and messages as above and treat the remaining account row as retained.
- **Assistant instructions.** A user clears their own instructions by saving empty fields under **My instructions**; the row is deleted with the user (`ON DELETE cascade`) and a mailbox's instructions with the mailbox.
- **Writing style.** **Reset** next to a mailbox deletes that profile, and turning **Learn my writing style from mail I send** off deletes all of the user's profiles at once (after a confirmation). Profiles go with the user and with the mailbox (`ON DELETE cascade`); `composer_sends` rows go with their message, the user or the mailbox. There is no account export; the assistant settings show each profile's sample count and exactly the text Kite gives the AI.
- **AI summaries.** Deleting a message, or moving it to Spam or Trash, deletes the summaries of its conversation and of the message itself, with their translations; deleting the mailbox deletes all of its summaries (`ON DELETE cascade`). Summaries are not in backups, so a restore starts without any.
- **Backups.** Deleted data stays in existing backups until they expire or are deleted. After you restore a backup, reapply deletions you made since.
- **Logs and metrics.** Analytics Engine points are built from the fixed fields listed above and contain no addresses or message content. Logs can hold recipient and forwarding addresses from the `console.*` calls described above. Kite does not log message bodies on purpose, but it cannot guarantee that none appear: several handlers pass raw `Error` objects to `console.error` (for example `console.error(\`JMAP ${name} failed\`, error)` in `src/lib/jmap/processor.ts:152`), and a database error such as Drizzle's `DrizzleQueryError` from JMAP `Email/set` carries the failed SQL statement and its parameters, which can include message text. Structured `createLogger` events never log error messages. Both expire under Cloudflare's retention (see Retention); on Node, stdout retention is whatever your log collector keeps.
