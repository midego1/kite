# Quality checks and existing debt

`npm run check:mission` runs app and relay typechecking, lint and unit tests; scoped coverage; quality debt checks; documentation freshness; the Worker build and bundle budgets; local relay integration; and Chromium e2e. Every command must pass. Its timing wrapper preserves command output and records status and elapsed milliseconds in `test-results/quality/timings.json`, including a failed step. It never deploys or uses remote bindings.

CI splits the work across three kinds of job. "Mission validation" runs `npm ci`, then `npm run check:mission` with `MISSION_SKIP_TASKS=build:node,test:e2e` set on that step only. It runs on a Boat `boat-large` runner only for pushes to `main` and pull requests labelled `boat-ci` by an allowed user (`midego1`, listed once in the job's `runs-on`; a pull request must also be that user's own, and a rerun must be by the same user). Boat runs jobs of a public repository only for its allowed GitHub users and refuses bots, so bot merges to `main` (auto-merge), `release/next` dispatches and everything else run on GitHub-hosted `ubuntu-latest`, which also keeps `main` validated when Boat is down; CI does not run when a label is added (a run for a label would skip the required checks, which GitHub counts as passing), so `boat-ci` takes effect on the next push, or close and reopen the pull request. A parallel "Node build" job runs `npm run quality:timings -- build:node`, so the type-checked Node/Docker build still runs on every pull request and push to `main`. Ten parallel "E2E (shard N of 10)" jobs each run `npm run quality:timings -- test:e2e:shard` with `E2E_SHARD=N/10`; every shard starts its own dev server and database and runs a slice of the specs. `scripts/quality/e2e-shard.mjs` plans the slices: it lists the suite with `playwright test --list`, groups it (a file is one unit because the suite runs one test at a time, unless it declares `test.describe.configure({ mode: "parallel" })`, as `e2e/23-auto-agent.spec.ts` does; a file that depends on test order must not), weighs each group by the durations recorded in `e2e/timings.json` (a test missing from it counts as the median), assigns the longest groups first to the least-loaded shard, writes the slice to `test-results/e2e-shard-list.txt`, checks that the list selects exactly the planned tests and runs it with `playwright test --test-list`. Playwright's own `--shard` splits by test count, which left one shard twice as long as another. When the slices drift apart, download the E2E artifacts of a green run and refresh the durations with `npm run e2e:timings -- <dir>/*/test-results/playwright-results.json`; `E2E_SHARD=1/10 npm run test:e2e:shard -- --plan` prints the split without running anything. The whole suite on one runner took about 20 minutes, ten shards about two minutes of tests each plus a minute of server start. Every job restores one `node_modules` cache keyed by `package-lock.json` (saved straight after a clean `npm ci`) instead of installing, and the E2E jobs cache the Chromium headless shell. Verify the exact job names before making any of them a required check. `MISSION_SKIP_TASKS` accepts only `build:node` and `test:e2e` (any other value fails before a task starts), is recorded in `timings.json` as `{ "skipped": true, "reason": "MISSION_SKIP_TASKS" }`, and is ignored when tasks are listed explicitly. Locally, `npm run check:mission` runs everything, and `E2E_SHARD=2/10 npm run test:e2e:shard` runs one slice.

Every job appends `node scripts/quality/ci-summary.mjs` to the GitHub step summary (task timings, Playwright totals with flaky tests, coverage). In CI Playwright also writes `test-results/playwright-results.json`. Run the script locally after `check:mission` to preview it.

The coverage thresholds (lines 80, branches 90, functions 95) were measured on macOS (lines 83.3, branches 93.6, functions 98.9). Check the first Linux CI run, and if the runner measures differently, lower the thresholds in `scripts/quality/coverage-config.json` in a reviewed change. Do not loosen them locally.

Without a split, CI can run `npm ci`, install Playwright Chromium, then `npm run check:mission`. Upload `test-results/quality/**` even on failure, alongside Playwright reports. For split jobs, run `npm run check`, `npm run test:coverage`, `npm run quality:check`, `npm run docs:check`, `npm run build`, `npm run quality:report`, `npm run test:relay:integration`, and `npm run test:e2e`. `npm run quality:timings -- build test` times selected commands without changing their exit status.

## Formatting

Prettier uses tabs and a 120-column print width. There is no formatting baseline: `npm run format:check` fails when any file Prettier does not ignore is unformatted, and `quality:check` runs the same check. `npm run format` formats everything; prefer `npx prettier --write path/to/changed/file.ts` during focused work. The optional pre-commit hook and `npm run precommit:check` check only staged files, reading the staged copy rather than the working tree. `.prettierignore` excludes generated output, the migration bundle and SQL/meta migrations, lockfiles, `wrangler.jsonc` and its example, `public/`, screenshots and all Markdown.

## Complexity, size, unused code and duplication

ESLint warns for cyclomatic complexity above 20, source files above 500 nonblank/noncomment lines, and unused variables. `quality:check` rejects increases above each recorded finding, so an existing large function cannot grow its complexity and an existing large file cannot add counted lines. Existing warnings remain visible in `npm run lint` and `test-results/quality/lint.json`.

The Knip wrapper disables experimental raw-transfer parsing to avoid a large scratch-buffer allocation in small development VMs; analysis still uses Knip's supported standard parser.

Knip analyzes root app/server/Worker entries, route conventions, tests and scripts, plus the relay as its own workspace. Its findings include unused files, dependencies, exports and unlisted imports. `npm run quality:dead-code` emits the full raw report and exits nonzero for existing findings. `quality:check` compares individual issue identities with the baseline and rejects new findings. Framework runtime imports and dynamic registration can cause false positives; inspect a finding before deleting code. The baseline records those findings rather than declaring the repository debt-free.

jscpd scans app, server, Worker and relay source with a minimum 100 tokens and 10 lines, ignoring comment tokens and declarations. `npm run quality:duplicates` uses its native fingerprints to reject new duplicated blocks. The full clone report remains in `test-results/quality/duplicates/`. Tests are excluded from clone scanning so repeated fixture setup does not dominate application duplication debt.

## Boundaries and dependency consistency

The TypeScript AST import graph checks runtime imports reachable from every `use client` entry, including static re-exports, literal dynamic imports and literal require calls. Browser code must not import Node builtins, database modules, server runtime, Worker/relay entrypoints or server-only mail packages. `use server` modules form intentional server-action boundaries and type-only imports are excluded. The independent relay must not import app/server source, with an explicit allowance for the portable shared logger and trace helpers. Existing violations, if any, are listed in the same transparent baseline; new edges fail. Computed imports and TypeScript aliases beyond the repository's `@/` convention are not analyzed.

Root and relay shared dependencies must declare identical version ranges. Existing range differences are recorded individually; a new or changed mismatch fails. The relay is an npm workspace in the root lockfile: root `npm ci` pins and installs dependencies for both packages. `VERSION` has four numeric segments, and the root package version must be its first three without leading zeros (`2026.10.09.0` → `2026.10.9`; see [Releasing](releasing.md)). The relay keeps an independent application version.

## Coverage and performance scope

`npm run test:coverage` runs the app gate (`npm run test:coverage:app`, `scripts/quality/coverage.mjs`) and the relay coverage. The app gate runs each `tests/*.test.mjs` file in its own `node --test --experimental-test-coverage --enable-source-maps` process (in parallel) with the lcov reporter, and concatenates the results into `test-results/coverage/app.lcov`. One run per file matters: a single `node --test` run merges every child's coverage for a source path into one record in an order-dependent way, so a module that one test bundles without calling could erase another test's hits. Every esbuild bundle in the tests sets `sourcemap: "inline"` (stdin builds also set `absWorkingDir`) and lives under `test-results/bundles/`, not `node_modules` (Node skips coverage there), so lcov points at real `src/` files. `parseLcov` merges the records for one source file by line (`DA`) and by function name (`FNDA`), keeping the highest hit count, so the result does not depend on record order; branches, whose indices differ per record, use the record with the largest denominator.

`scripts/quality/coverage-config.json` classifies every `src/lib/**/*-utils.ts` as `gated` or `ungated` (each ungated entry needs a reason). A utils file in neither list, in both, or listed but missing fails the gate, so a new utils file must be classified in the same change. Gated files (plus `logger`, `trace` and `worker-utils.ts`) are checked per file (branches >= 70%, functions >= 80%; `logger` and `trace` override that with lines 90%, functions 90%, branches 80%) and in aggregate (lines >= 80%, branches >= 90%, functions >= 95%). Thresholds are the measured value minus about 3 (aggregate measured lines 83.3%, branches 93.6%, functions 98.9%); line coverage is depressed by esbuild mapping, so branches and functions carry the gate. The gate writes `test-results/coverage/summary.json` (`aggregate`, per-file `files[]` with measured values, thresholds, `passed` and `failures`). Gate coverage claims cover only gated files, not whole-app coverage; the relay handler keeps 90% lines, 90% functions and 80% branches. Normal app/relay unit tests and e2e remain required independently.

`npm run quality:report` requires built JavaScript output in both `dist/client` and `dist/server` and records raw/gzip totals and the 15 largest chunks in `test-results/quality/bundle.json`. Gzip totals are summed per chunk, not a route's initial transfer size, and server raw/gzip bytes are not a Cloudflare deployment-limit measurement. It enforces two things from `scripts/quality/bundle-budgets.json` (logic in `scripts/quality/bundle-budget-utils.mjs`, tested by `tests/bundle-budget.test.mjs`):

- **A growth limit per pull request (the gate that matters).** The report builds the pull request's base commit in a scratch copy under `test-results/quality/` (`git archive`, about 25 seconds, cached by commit and lockfile) and fails when this change grows a total by more than `growth`: client 60,000 raw / 15,000 gzip bytes, Worker 160,000 / 40,000. The limits come from the history of budget raises (the largest single pull request so far added 73,000 raw / 23,000 gzip bytes to the client and 110,000 / 22,000 to the Worker, most added a few thousand). The scratch copy reuses the checkout's `node_modules`, unless `package-lock.json` differs between the base and the change: then it runs `npm ci` for the base's own dependencies, so growth that comes from a dependency shows up and a lockfile change cannot break the base build. The `growth` limits are read from the base commit's `bundle-budgets.json`, so a pull request cannot raise its own limit and a raise only takes effect once it has merged.
  - **The base.** On a pull request it is the first parent of GitHub's merge commit, the `main` the change merges onto, with no stored numbers to keep in step. **On a pull request a base that cannot be found or built fails the job**, because a silent skip would let any change through. A push to `main` has no base and only the ceiling applies. Locally the base is `git merge-base HEAD origin/main`, and a missing one prints a `::warning::`; `BUNDLE_BASE=<ref>` or `--base <ref>` picks another commit, and `BUNDLE_BASE=none` skips the comparison on purpose (a local escape hatch; CI never sets it).
  - **Noise.** The scratch build and the checkout can measure a few hundred raw bytes apart for identical code (about 200 bytes on the client, for instance, where the checkout's generated bundles such as the changelog differ), which is why the limits are generous.
- **An absolute ceiling.** The top-level `client` and `worker` numbers are a safety net about 10% above the build at the time (client 3,150,000 raw / 1,015,000 gzip, Worker 8,140,000 / 2,290,000; the Worker's set on 2026-10-31 when `main` reached 7,399,562 / 2,078,181, the client's lowered later that day to keep the bundle trim of #289 when `main` was at 2,859,410 / 919,277), so ordinary pull requests never edit the file. When a build reaches it, review the largest chunks and raise it in a pull request of its own (the ceilings are read from the checkout, so that pull request passes).

A pull request that legitimately needs more adds `bundle-growth.d/<slug>.json`, a new file per pull request, so it never conflicts (the same idea as `changelog.d`). The numbers are extra growth on top of the default limit, for this pull request only; every key is optional but one number must be given, and the reason is mandatory:

```json
{
	"reason": "The rich-text editor ships its own parser for pasted tables.",
	"client": { "bytes": 40000, "gzipBytes": 12000 }
}
```

Only files the pull request adds count (those already in the base are ignored), and an invalid file fails the report. `npm run release:prepare` deletes them with the changelog fragments. Keep the allowance close to the measured growth and explain it in the pull request; raising the ceiling is a separate decision. Timings are measurements rather than flaky machine-dependent pass/fail thresholds.

## TODO policy

`quality:check` scans every tracked or unignored file for the case-sensitive words TODO, FIXME and HACK (whole words, so `TODOS` and `Todo` do not match). A marker must carry an issue link in the form `TODO(#123)`; the same form works for FIXME and HACK. An unlinked marker fails the check and is printed as `file:line`. There is no baseline. `package-lock.json`, `cloudflare-env.d.ts`, binary files (a NUL byte or an image, font, archive or wasm extension) and `scripts/quality/todo-utils.mjs` (which builds the words from pieces) are not scanned, and neither is this page, which has to spell the words out. Linked markers are listed under `linked` (and unlinked under `unlinked`) in `test-results/quality/todos.json`. The issue number is not checked against GitHub.

## PR report

`.github/workflows/pr-report.yml` runs on `pull_request` only and builds an advisory report with `node scripts/review/pr-report.mjs --base <ref> --inputs test-results`. It is not a required check and never blocks a merge. The `report` job has a read-only token (`contents: read`): it runs Semgrep with the `security.yml` rules, `npm audit --omit=dev` for the head and for the base (from the base `package.json` and lockfiles), `quality:check`, `quality:duplicates` (its pass or fail is recorded separately, so a duplicate-only failure still shows) and `test:coverage`, then writes the report to the job's step summary and to the `pr-report` artifact. A separate `comment` job holds `pull-requests: write`, never checks out PR code, skips pull requests from forks, uses `continue-on-error`, and creates or updates one comment marked `<!-- kite-pr-report -->`. A scan whose output is an error or unreadable renders as failed instead of clean, and R1 matches backup-list entries exactly. If GitHub refuses the write (for example on Dependabot runs), the step summary still has the report.

Sections: Security (Semgrep findings as `file:line` with findings in changed files marked, npm audit counts and advisories that are new compared with the base), Quality (new debt against the baseline, linked and unlinked TODO markers), Coverage (aggregate and gated files against their thresholds) and Repo rules. The rules only warn: R1 a migration that creates, drops or renames a table without a backup list change (`AGENTS.md`), R2 UI changes under `src/app` or `src/components` without an `e2e/` change, R3 a changed or removed Cloudflare resource name in `wrangler.jsonc` or the relay's `wrangler.jsonc`. Added bindings pass. A section whose input is missing says "not run". The report never contains source snippets, audit `via` details or environment values, and is truncated below GitHub's 65,536 character comment limit. Run it locally after `npm run quality:check` and `npm run test:coverage`.

## Comparing the reviewers

CodeRabbit (`.coderabbit.yaml`) and Greptile (`greptile.json`) both review every non-draft pull request against `main`, on open and on every push, with the same path rules, the same ignored generated files and the same context files. Greptile reads `greptile.json` from the pull request's own branch, so a branch created before the file landed on `main` is reviewed with the dashboard settings. Keep the two files in step: a rule added to one and not the other skews the comparison.

`.github/workflows/coderabbit-adopt.yml` handles both reviewers' inline comments the same way, and its verdicts are the measurement: Droid adopts a finding that holds up in a commit whose body says `Addresses <reviewer> review comment <id>`, and replies `Adopted in <sha>.`, `Already addressed ...`, `Valid, not adopted: ...` (correct, but the fix did not pass validation) or the reason the finding is wrong. When both reviewers flag the same problem, one commit addresses both comments, so each gets the credit; a finding that arrives later and is answered `Already addressed in <sha>` with a commit the workflow adopted for the other reviewer is credited to that commit too. The prompt tells Droid to judge the finding only, never the reviewer.

Before anything is pushed, the adopt job runs `scripts/review/adopt-gate.mjs` on Droid's commits: `npm run check`, `npm run test:coverage`, `npm run quality:check` and `npm run docs:check`. A check that fails with the commits but passes on the pull request head without them drops every adoption of that run, and their comments are answered `Valid, not adopted: ...` instead. A check that already failed before the run is noted in the step summary and does not block. Commits that change a file under `.github/workflows/` (and commits that no longer apply without them) are left out first and answered `Valid, not adopted`: pushing a workflow change needs the `workflows` permission, which neither token gets, so an AI-written change to CI never runs with the repository's secrets. Droid gets 35 minutes per run; when it runs out, the commits it made are still checked and published, and the comments it did not reach stay unanswered for the next run (a new review, or Actions → Review adopt → Run workflow). The publish job then resolves every thread it settled: adopted, already addressed and incorrect findings. A `Valid, not adopted` thread stays open for a person. If GitHub refuses a resolution, the answers are still posted and the job fails, so the open threads are noticed.

A push made with the workflow's own token never starts other workflows, so without more setup CI does not run on the adopted commits (push an empty commit or rerun CI by hand). To have it run, create a GitHub App once and let the workflow push with it:

1. GitHub → Settings → Developer settings → GitHub Apps → New GitHub App. Any name and homepage URL, webhook off, repository permissions **Contents: Read and write** and **Pull requests: Read and write**, installable only on this account.
2. Generate a private key, then install the App on this repository only.
3. In the repository, Settings → Secrets and variables → Actions: the variable `REVIEW_ADOPT_APP_CLIENT_ID` (the App's Client ID) and the secret `REVIEW_ADOPT_APP_PRIVATE_KEY` (the whole `.pem` file).

With the variable set, the publish job mints a short-lived App token for the push and the thread resolution; replies still come from `github-actions[bot]`, the login the collector checks to skip answered threads. Delete the variable to go back to the workflow token.

`GH_TOKEN=$(gh auth token) npm run review:scoreboard -- --limit 30` tallies the most recently updated pull requests per reviewer: findings, adopted, shared (adopted by the same commit as a finding of the other reviewer), already addressed, valid but not adopted, declined, open (not answered yet, or outdated before a run reached it) and the valid rate (adopted plus valid but not adopted, out of every answered finding). To decide, also look at what neither number shows: real problems one reviewer found that the other missed (adopted minus shared), and how much of each review is summary and noise. Findings that CodeRabbit puts only in its review body (nitpicks, comments outside the diff) are not inline comments, so neither the workflow nor the scoreboard sees them.

To keep one reviewer, uninstall the other's GitHub app, delete its configuration file and its login from `REVIEWERS` in `scripts/review/coderabbit-comments-utils.mjs` and the workflow's actor check, and update `CONTRIBUTING.md`, `SECURITY.md` and this section.

## Reviewing a baseline change

`npm run quality:baseline` explicitly regenerates the recorded findings and duplicate fingerprints. Never run it automatically in CI or to dismiss a failure. Review every added finding and explain accepted debt in the PR. Decreasing findings pass; remove stale baseline entries as debt is retired. Baseline generation errors or scanner failures still fail the command. Report files are under the existing ignored `test-results/` tree; baseline files and budget configuration are committed and reviewable.

## Pre-commit and release notes

The pre-commit hook in `.githooks/` is opt-in: `npm ci`/`npm install` never changes Git configuration. `npm run hooks:install` sets `core.hooksPath` to `.githooks`. When `extensions.worktreeConfig` is enabled it writes the setting with `git config --worktree`, so it applies to the current worktree only; otherwise it uses `git config --local`, which every worktree of the clone shares, and prints how to switch (`git config extensions.worktreeConfig true`, then rerun). The script never enables that extension itself. Existing custom hooks paths and custom hooks in the default hooks directory are preserved; use `npm run precommit:check` manually in that case. Remove the hook with `git config --local --unset core.hooksPath` (or `--worktree`). Hooks never install packages or contact a service while committing. They complement CI and can be bypassed locally, so CI remains the required validation.

`npm run release:notes -- <base-ref>` generates grouped notes from committed Git subjects and VERSION. It defaults to `origin/main`, validates the comparison ref, writes only to stdout, and requires human review before any publication. Pull requests add a changelog fragment in `changelog.d/` instead of a release; `npm run release:check -- <base-ref>` (the CI "Release version" job on pull requests) fails without one unless the pull request is labelled `no-changelog`, and `npm run release:prepare`, run by the release pull request workflow, folds the fragments into the next calendar version; [Releasing](releasing.md) describes the whole sequence, including the release published automatically after each production deploy.

Browser artifacts use `test-results/playwright`, separate from `test-results/quality` and the synthetic auth state. Playwright can clean its own outputs without deleting earlier quality or timing evidence.
