## Architecture

Next.js App Router APIs running on Cloudflare Workers via vinext. Drizzle ORM over D1, R2 for raw MIME, attachments, and record backups, Queues for async mail processing, a Durable Object for realtime, and a cron trigger for scheduled backups.

### worker.ts is the entrypoint

`worker.ts` wraps `vinext/server/fetch-handler` and adds handlers Next.js cannot express:

- **`fetch`** — intercepts `/api/realtime` for the WebSocket upgrade (authenticates the session cookie, then routes to `env.REALTIME.getByName(user.id)`), delegating everything else to vinext.
- **`email`** — the Cloudflare Email Routing handler. Resolves domain routing rules first (`resolveIncomingMail` in `src/lib/email/incoming.ts`) because `message.setReject()` and `message.forward()` only exist here, then applies optional account-level forwarding (loop-guarded by `X-Kite-Forwarded`; `wasForwardedByKite` also honours the pre-rename `X-Mailflare-Forwarded`), writes raw MIME to R2, and enqueues to `INBOUND_QUEUE`. It never parses mail inline.
- **`queue`** — a single consumer for every queue; `isInboundQueueMessage` and `isWebhookRetryMessage` in `worker-utils.ts` discriminate inbound mail, webhook retries, and outbound payloads, and agent jobs go through `processAgentQueueMessage`. Message kinds a module declares (today `import.imap` on the agent queue) are dispatched through the registry by `dispatchModuleQueueMessage` (`src/lib/modules/background.ts`), which acks and skips a message whose module is off. Failures retry with a delay (`queueRetryDelaySeconds`).
- **`scheduled`** — the `*/5 * * * *` and `0 2 * * *` cron triggers: backups, pruning, the opt-in usage heartbeat (daily), stale-backup recovery, alerts, agent maintenance and trash retention, then module cron tasks through the registry (`runModuleCronTasks`, for example the stalled-import safety net). `server/runtime/scheduler.ts` runs the same module tasks on Node.

It also re-exports `RealtimeHub`, which must remain exported from the Worker entrypoint.

### Mail pipeline

Inbound: `email` handler → R2 → queue → `processInboundMessage` (`src/lib/email/inbound.ts`) → `resolveInboundAddress` routing decision (deliver / reject / forward) → `parseRawMime` (postal-mime, then `sanitizeStoredEmailHtml` from `stored-html-utils.ts` on the HTML body) → insert message + attachments → upsert contacts → `dispatchWebhooks` → `notifyUsersOfNewMessage` over the Durable Object.

The Screener (`src/lib/screener/`, migration 0068, user docs in `docs/screener.md`) sits after the spam filter and mailbox rules: `applyScreener` sees only mail they would still deliver as `received` and, for an enabled mailbox and an undecided sender, stores it as `status = "screening"` (held, keeping its `folderId`) or leaves it `received` in Inbox mode, where list rows get `screenerPending`. Either way delivery skips the notification, auto-reply and `scheduleAgentWork`; webhooks still fire. `screening` is a status of its own, and every Inbox, folder, search, count, conversation, JMAP, `/api/v1` and MCP query either filters on explicit statuses or excludes `SCREENING_STATUS`; a new query over inbound mail must leave it out too. Approving sets it back to `received` and schedules automatic reading (`service.ts`); sending approves recipients (`approveSentRecipients` in `release.ts`, which must not import the agent schedule because that would close an import cycle through `send.ts`). Denying reuses `blockContact`. Reads fall back when the tables are missing and writes throw `ScreenerUnavailableError` (503 `SCREENER_UNAVAILABLE`).

Outbound: `src/lib/email/send.ts` / `sender.ts`, sending structured messages (no MIME library) through the `EMAIL` send_email binding, with `outbound_jobs` rows tracking queued sends. `to`, `cc` and `bcc` accept a header string or an array; `toAddr`/`ccAddr`/`bccAddr` on `messages` store the full comma-joined lists (use `splitEmailAddressList` from `src/lib/email/address.ts`, not `getEmailAddress`, when a value may be a list).

Composer: `src/components/compose/rich-text-editor.tsx` is a contentEditable HTML editor; the body is one HTML string and the text/plain part is derived with `htmlToPlainText` (`rich-text-utils.ts`). Quoted/forwarded content is wrapped by `wrapQuotedHtml` and folded by both the composer and the reader (`splitQuotedHtml`). Forward copies the source's attachments onto the draft (`copyMessageAttachments`); `/api/send` with `draftId` sends them.

Threading: `resolveThreadId` in `src/lib/email/threading.ts` files an inbound or imported message under the thread of the stored message its `In-Reply-To`/`References` name (matched against `providerMessageId` in the same mailbox); otherwise its own Message-ID seeds a new thread. Outbound replies carry `inReplyTo`/`references`/`threadId` from the draft, and a fresh send is keyed by the Message-ID Cloudflare returns. `/api/messages/[id]/thread` returns the conversation. Lists pass `group=thread` (the "conversation view" toggle, `use-conversation-view.ts`) to get one row per thread plus `threadMessageIds`, which row actions and bulk actions expand to.

### Spam analysis lives in `src/lib/spam/`

`analyzeSpam` (`engine.ts`) scores each stored inbound message from local analyzers (`analyzers/`: authentication, URLs including links inside attached web pages, structure, attachments, safelist pressure), the sender's contact, mailbox reputation and the Bayesian classifier; its signals are stored in `messages.spam_signals` and feed the phishing facts of automatic reading. Authentication signals come only from `authenticationResults` on the inbound queue payload, which the intake hop sets (`src/lib/spam/authentication-results-utils.ts`): the Worker `email` handler and the relay route (only with a valid `X-Kite-Headers-Signature`) pass the topmost Cloudflare `Authentication-Results`; SES passes its receipt verdicts (`sesAuthenticationResults`) only when the SNS signature verifies (`src/lib/aws/sns-signature.ts`); the SMTP listener and Resend pass none, and the message's own headers never count. `authPassed` needs DMARC (which outweighs a failed SPF check), or a DKIM pass aligned with the From domain (`dkim_passed` `metadata.aligned`, via `registrableDomain` and its shared-suffix list) and no failure. A blocked sender returns before anything else. The only outside call is the optional `SpamIntelligenceProvider`: `spamIntelligenceProvider(env)` (`providers/abuse-ch.ts`) is `AbuseChIntelligenceProvider` when `abuseChAuthKey` finds `URLHAUS_AUTH_KEY` (or its alias `ABUSE_CH_AUTH_KEY`) and a no-op otherwise; inbound mail uses `configuredSpamIntelligenceProvider` (`abuse-ch-key.ts`), which falls back to the owner's sealed `app_settings.abuse_ch_auth_key` (migration 0068), read only when a message would be looked up. A secret always wins, and `PUT`/`DELETE /api/admin/threat-lookups/key` (owner only) refuse while one is set; `PUT` saves only after `testAbuseChKey` passes or abuse.ch is unreachable. `ABUSE_CH_TEST_ORIGIN` (dev only) points both APIs at the e2e fake. It runs URLhaus (links and attachment hashes, `urlhaus-utils.ts`) and ThreatFox (link hosts and the same hashes, `threatfox-utils.ts`) in parallel; `planThreatLookups` (`abuse-ch-utils.ts`) sends nothing unless the local signals already show a risk, `lookupSignals` caps a match on both lists, and a refused key is logged as `spam.threat_lookup_key_rejected`. `POST /api/admin/threat-lookups/test` (owner only) is the **Test key** button. Known correspondents are not looked up unless authentication failed. Report phishing (`phishing-report.ts`, bulk action `phishing`) trains like a spam report with extra fingerprint weight, blocks the sender except trusted contacts and own domains, and closes open phishing suggestions. Every report asks first (`confirmReportSpam` / `confirmReportPhishing` in `src/components/messages/`, always through `ConfirmDialog`, with no way to skip it) and offers Undo: `applySpamFeedbackWithReceipt` (`feedback.ts`) saves a `spam_report_receipts` row (migration 0073, internal to backups, pruned after 7 days) with the earlier classification, the token and reputation rows the report created, the earlier place and the phishing extras (a block only if the report placed it, the warnings it closed), and `undoSpamReceipt` (`report-receipts.ts`) subtracts exactly the training `trainingStatements` (`training.ts`) added in one atomic batch whose first statement is a `json()` guard (receipt not yet undone, no newer trained receipt for the message, feedback row unchanged), so a second or concurrent undo is a no-op and a receipt a newer report stands on answers `superseded` untouched; approved chat moves record each message receipt id in their saved state (`receipts`, via `AgentToolContext.onReceipt`) and "Mark as spam" in its `after`, and undo exactly that one. The receipt write never fails a report: without the table the bulk response sets `trainingUndoUnavailable` and Undo only moves the place back. User-facing behaviour is in `docs/spam-protection.md`.

### Sending and receiving providers are per domain

`domains.sending_provider` (`none | cloudflare | resend | ses`) and `domains.receiving_provider` (`none | cloudflare | resend | ses`, default `cloudflare`) are chosen independently on the Domains page; DNS stays on Cloudflare either way. They record intent: switching a provider never touches DNS, each provider's own Setup does, and a **Clean up** button removes the config of an unselected provider.

- **Sending** goes through `sendThroughProvider` (`src/lib/email/outbound-provider.ts`), which `deliverEmail` and `sendSystemEmail` call after `getOutboundProviderConfig(env, from)` resolves the provider from the From domain (`none` throws). Cloudflare keeps its 5 MiB link fallback; Resend and SES take attachments directly. Resend and SES return different Message-IDs than we send, so `providerMessageId` stores the one replies will carry (`<id@email.amazonses.com>` or `<id@region.amazonses.com>` for SES).
- **Receiving** from a non-Cloudflare provider enters through `intakeProviderMail` (`src/lib/email/provider-intake.ts`) and then the same `intakeIncomingMail` as everything else, once per recipient on a known domain. Providers cannot be rejected to after accepting, so reject and size limits drop the message, and `forward` is unavailable. Inbound endpoints are public and authenticate themselves: `/api/inbound/resend` verifies the Svix signature (`svix.ts`) with the secret Resend returned when `ensureWebhook` created the hook (`app_settings.resend_webhook_secret`), then fetches the raw MIME from `raw.download_url`; `/api/inbound/ses` is an SNS HTTPS endpoint guarded by a secret token in its URL, the topic ARN and reading the object from our own bucket.
- **Only one MX owner per domain.** `publishMx` (`receiving-dns.ts`) refuses with `MxConflictError` (HTTP 409 `MX_CONFLICT`) when other MX records exist; the UI confirms and retries with `replaceMx`. Cloudflare Worker routes (`ensureMailboxDomainRouting`) are created only for domains whose receiving provider is `cloudflare`.
- **Resend** keeps one key (`app_settings.resend_api_key`, or `RESEND_API_KEY`) and one Resend domain per hostname carrying both capabilities, so sending cleanup disables only `sending` when the domain still receives through Resend and vice versa. Apex MX values matching `inbound-smtp.*.amazonaws.com` are receiving records; everything else is sending.
- **AWS** (`src/lib/aws/`) is a hand-rolled SigV4 client (`sigv4.ts`, verified against AWS's published vectors in `tests/provider-aws-resend.test.mjs`) so it runs on Workers and Node without the SDK. Credentials live in `app_settings.aws_config` (or `AWS_*` env vars) and are validated before saving by `validateAwsConfig`, which proves identity with STS then probes SES, SNS and S3, reporting each missing permission with the IAM policy that grants it. SES sending uses SESv2 (`ses.ts`); receipt rules exist only in SES v1 (Query protocol), so receiving uses `awsQuery`. `setupSesReceiving` creates the S3 bucket and policy, SNS topic, policy and HTTPS subscription, then a per-domain receipt rule in the account's active rule set (creating `mailflare-inbound` only when none is active), and the MX. State is in `app_settings.ses_receiving`. SES inbound exists only in some regions (`SES_RECEIVING_REGIONS`) and needs a public HTTPS `APP_URL`.
- **Skip DNS setup** (`addSkippedDomainForUser`, `skipDns` on add and first-run register) stores the `"manual"` zone, providers `none` and `domains.dns_skipped`, without any Cloudflare call. `adoptCloudflareZone` (`src/lib/domains/adopt-zone.ts`) swaps in the real zone at the first DNS setup, Cloudflare sending enable or Cloudflare receiving setup, and only for a skipped domain with Cloudflare credentials: a self-hosted manual zone stays manual. `PATCH /api/domains/[id]` clears the flag behind the dashboard's `DnsSkippedBanner`. Whole-row `domains` reads go through `selectRow`/`selectRows` (`src/lib/db/pending-columns.ts`) so they keep working before the column's migration is applied.

### Routing rules have two scopes

`routing_rules.scope` splits two genuinely different mechanisms, and mixing them up is the easy mistake:

- **`domain`** — evaluated by `resolveInboundAddress` (`src/lib/email/routing.ts`) *while resolving the address*, in three phases: `reject` rules first (so a sender can be blocked even when the recipient is a real mailbox), then exact mailbox and alias lookup, then `forward`/`store` catch-all fallbacks. Ordered by descending `priority`, then oldest first. This phase split is what stops a `*` catch-all from shadowing real mailboxes — preserve it.
- **`mailbox`** — evaluated by `resolveInboxRuleDestination` *after* delivery, to pick a folder or move to spam/trash.

Both queries filter on `scope`, so any new rule must set it explicitly. `forward` and `reject` are actioned in `worker.ts`, never in the queue consumer.

### Webhook retries and manual backups ride the outbound queue

`src/lib/email/webhooks.ts` records every attempt (status, error snippet, duration, `nextRetryAt`) on `webhook_deliveries` and re-enqueues failures onto `OUTBOUND_QUEUE` with a `delaySeconds` backoff rather than adding a third queue binding. `env.d.ts` widens `OUTBOUND_QUEUE` to the union of every payload type accordingly. `runDelivery` is shared by the retry queue and the manual retry endpoint.

`POST /api/backups` records a `queued` row and sends `{ kind: "backup.run", backupId }` (`src/lib/backups/queue-utils.ts`) on `OUTBOUND_QUEUE`; the consumer's `runDatabaseBackup` exports the database, so a large backup never runs inside the admin request (it used to outlive the response timeout and leave the row running forever). `runDatabaseBackup` no-ops on a completed or deleted row, so a retried message cannot export twice. `failStaleBackups` (`src/lib/backups/service.ts`) marks a queued or running backup older than `STALE_BACKUP_AFTER_MS` as failed with `STALE_BACKUP_ERROR`, from the `*/5` cron and from `GET /api/backups`, and `deleteBackup` allows removing an interrupted row.

### Cloudflare is a live dependency, not just a host

Domain and mailbox management call the Cloudflare API at runtime (`src/lib/cloudflare-api.ts`, `src/lib/domains/`). Adding a domain enables Email Routing DNS and sending subdomains on the zone; creating a mailbox creates a Cloudflare Email Routing rule targeting the Worker named by `getEmailWorkerName()` (`src/lib/cloudflare-api-utils.ts`, `kite`); removing a domain cleans those up (`src/lib/domains/cloudflare-cleanup.ts`).

Consequence: `getEmailWorkerName()`, the deployed Worker `name`, and `services[].service` for `WORKER_SELF_REFERENCE` in `wrangler.jsonc` must all agree. Rules that still point at a pre-rename Worker (`LEGACY_EMAIL_WORKER_NAMES`) are re-pointed instead of duplicated. Cloudflare service bindings need a literal name and cannot reference the top-level `name`.

Auth is `CF_TOKEN` (preferred) or the legacy `CF_EMAIL` + `CF_API_KEY` pair.

### Schema and the dual-migration gotcha

Schema lives in `src/db/schema/index.ts`, plus `src/db/schema/agent-auto-read.ts` for the automatic-reading tables (suggestions, the agent action log, sender policies), `src/db/schema/agent-writing.ts` for each user's own AI settings (`user_ai_settings`, migration 0069) and the writing style profile (`writing_style_profiles`, `composer_sends`, migration 0070; logic in `src/lib/agent/writing-style.ts` and the pure `writing-style-utils.ts`), `src/db/schema/modules.ts` for module state (`module_settings`, `user_module_access`) and `booking_appointments`, `src/db/schema/finance.ts` for Money Watch (`finance_subscriptions`, `finance_charges`, migration 0063) `src/db/schema/drive.ts` for Drive (the `drive_*` tables, migration 0064) and `src/db/schema/storage.ts` for object storage (`storage_stores`, `storage_routes`, `storage_migrations`, migration 0065), and `src/db/schema/telemetry.ts` for `telemetry_state` (migration 0071, internal: not backed up). Each imports the core tables they reference and are merged into the Drizzle `schema` object in `src/db/index.ts`. Migrations are generated into `drizzle/migrations/`. Note that `drizzle-kit generate` currently prompts interactively about a snapshot rename conflict, so recent migrations were hand-written to match the generated style.

`npm run db:bundle` packages the SQL files for the Worker, and `npm run changelog:bundle` packages `CHANGELOG.md`, with the pending `changelog.d` fragments under "Unreleased", for the "What's new" dialog; `npm run bundles` runs both, and the build, deploy, preview and development scripts call it before loading application code. `/api/setup/prepare` and the admin migration endpoint use the shared runner in `src/lib/migrations/service.ts`; migration files remain the only schema history to maintain.

The setup path only ever initializes an empty database — it refuses to touch one that already has tables.

Deploys never apply migrations, so the deployed code can run a release ahead of the schema. `src/lib/migrations/pending.ts` answers that question for everyone (`GET /api/migrations/pending`, `{ pending }`), and `src/components/migrations-banner.tsx` shows it in the mailbox: the primary admin can apply the updates from there through the existing admin route. With `AUTO_APPLY_MIGRATIONS=1` (an env var, so it can be read before its own migration exists), `src/lib/migrations/auto-apply.ts` applies pending migrations once per isolate from that status check and from the start of queue processing, with the same safety backup as the admin route. Keep both paths working on a database whose schema is behind: read `d1_migrations` and `sqlite_master`, never a new column.

### Two runtimes, one code path

The Node build aliases `cloudflare:workers` to `server/runtime/cloudflare-workers.ts`, allowing the shared helper to use its existing `getNodeEnv()` fallback. That alias only applies when `KITE_RUNTIME=node`; vinext uses the native Workers module. Next outputs to `.next-node` so its generated types do not collide with vinext's `.next/types`.

The app reaches every platform service through `getEnv()` (`src/lib/cloudflare.ts`). On Workers that is the native `cloudflare:workers` env. In the self-hosted runtime, `server/index.ts` builds an object with the same shape (`server/runtime/env.ts`: a D1-compatible wrapper over better-sqlite3, an R2-compatible file bucket, `EMAIL` over nodemailer or the Cloudflare Sending REST API, in-process queues, a WebSocket hub standing in for the Durable Object, a fixed-window rate limiter) and publishes it as `globalThis.__kiteNodeEnv` before Next starts; `getNodeEnv()` in `src/lib/runtime.ts` returns it. Application code must not care which one it got. The few places that must differ check `isNodeRuntime(env)`: setup requirement checks and domain provisioning, which without Cloudflare credentials records the zone as `"manual"` (`src/lib/domains/provision.ts`) so every Cloudflare call is a no-op and the DNS page lists records to set by hand. Inbound mail off Workers goes through `intakeIncomingMail` (`src/lib/email/intake.ts`) from either the SMTP listener (`server/runtime/smtp.ts`) or the signed `/api/inbound` webhook the relay Worker in `deploy/cloudflare-email-relay` calls. `npm run build:node` builds Next in Node mode and bundles the server with esbuild to `dist/server.mjs`; the Dockerfile runs that. Migrations are applied from `drizzle/migrations` at start (`server/runtime/migrate.ts`), so the bootstrap schema in `src/lib/setup/migration.ts` is not used there.

### JMAP lives in `src/lib/jmap/`

`handleJmapRequest` (`src/lib/jmap/handler.ts`) owns `/jmap/*` and `/.well-known/jmap`; the Next routes under `src/app/jmap/[[...segments]]` and `src/app/.well-known/jmap` only delegate to it, and it is framework-free so it could be mounted from `worker.ts` too. Auth is an API key with the `jmap` scope via `authenticateApiRequest` (`src/lib/api/key-auth.ts`, the Next-free core that `src/lib/api/auth.ts` now wraps). JMAP Mailbox ids encode `mailboxId`, `mailboxId~role` or `mailboxId~f~folderId` (`ids.ts`); `email-query.ts` maps filters onto `messages` columns, `email-objects.ts` builds Email objects from stored rows (no MIME parsing), and states are digests of counts (`state.ts`), which is why every `/changes` method answers `cannotCalculateChanges`.

`Email/set` create and `Email/import` share one insert (`insertDraft` in `emails.ts`) and one target rule (`resolveDraftsMailbox` in `email-import-utils.ts`): a new message goes into exactly one Drafts mailbox, never Inbox or a folder, because delivered mail is the inbound pipeline's job. `Email/import` parses the uploaded blob with `parseRawMime`, stores the `Message-ID` in `providerMessageId` with its angle brackets (as inbound rows do) and keeps the uploaded bytes at `drafts/<messageId>.eml` in `rawR2Key`, so `readBlob` serves the client's own MIME back instead of the rebuilt minimal message; the `jmap-uploads/` object is deleted once claimed. `Email/copy` and `Email/parse` are still `emailUnsupported`.

D1 refuses a statement with more than 100 bound parameters, and a key without a mailbox restriction reaches every mailbox its user can read. So `scope()` in `emails.ts` binds the accessible mailbox ids as one JSON parameter (`inJsonArray` in `src/db/chunk-utils.ts`), and client-supplied id lists and per-mailbox lookups go through `queryInChunks`, which also drops repeated ids so a row is never returned twice across chunks. `serverFail` answers a fixed description, because a Drizzle error message carries the SQL and its bound values; the detail is only logged.

`email-query.ts` answers the `header` filter from columns — `Message-ID` from `providerMessageId` (compared with and without angle brackets, since inbound rows store them and outbound rows do not), `In-Reply-To` from `inReplyTo`, `References` by a padded `LIKE` on the space-joined chain. Any other header name throws `unsupportedFilter` (RFC 8620 §5.5). Filter conditions must never be silently dropped: a client that de-duplicates with `header` would otherwise match every message in the mailbox.

### Automatic reading lives in `src/lib/agent/auto-read/`

User-facing behaviour is in `docs/assistant.md`. The pipeline: delivery calls `scheduleAgentWork` (`schedule.ts`), which, when the mailbox autonomy is not `off` and `triageMessageGate` passes, inserts an `agent_jobs` row of kind `triage` and sends an `agent.triage` message on `AGENT_QUEUE`; with autonomy `off` it falls back to the legacy auto-draft job. The queue consumer (`src/lib/agent/queue.ts`) leases the job and runs `processAgentTriageJob` (`process.ts`), which reads the install and mailbox settings again when the job starts, so the kill switch, pause and the daily limit skip jobs already queued but not started (a running job may finish its remaining model calls); only the external-provider opt-in is re-checked on every model request. A refused job is skipped with a reason code (`kill_switch`, `external_provider_not_allowed`, `daily_limit`, `rate_limited`, ...) that Activity shows in plain words (`reasonText`).

- **Deterministic first.** `facts-utils.ts` computes facts (auth, bulk, no-reply, known contact, phishing signals, invite attachments); `needsModel` decides whether a model call is needed at all (or a module's `wantsModel` hint asks for it, below), and `policy-utils.ts` (`planSuggestions`) turns facts plus the optional model answer into suggestions. Everything is validated in code, never trusted from the model.
- **Tool-less model call.** `triage-model.ts` makes one structured request with no tools, no SDK retries (the job retries) and the message wrapped in a nonce-delimited untrusted block (`triage-utils.ts`). `auto-read-model.ts` re-checks the provider and the external opt-in on every request. Prompts and responses are not persisted; only `ai_usage` rows. The output cap is 400 tokens (`model-call-utils.ts`), raised by active module model extensions by at most `MODULE_EXTENSION_MAX_OUTPUT_TOKENS` (200) in total.
- **Module steps.** After the model, `runModuleTriageSteps` (`module-steps.ts`) runs the `triage_step` descriptors of modules on for the reviewer and whose per-mailbox switch (`capabilities.modules.<key>`, from `triage.capability`) is on. `triage.automatic` steps also get `Auto-Submitted` mail in a steps-only pass (no core kinds but phishing, counted toward the daily limit). When the model is refused (`external_provider_not_allowed`, `rate_limited`, `spend_cap`) or fails (at once for a hint-only request, which is never retried; on the last attempt otherwise, `model_failed`), the steps still run with `model: null`, so Calendar invites and Money Watch cards are still found.
- **Model extensions and hints.** A step's `triage.model` (`{ jsonSchema, instructions, maxOutputTokens, wantsModel? }`, rules checked by `tests/module-registry.test.mjs`) is merged into the one triage request only while active (`activeModelExtensions`, `model-extension-utils.ts`): the schema under `properties.modules.properties.<id>`, the instructions appended to the system prompt outside the untrusted block, `modules` parsed leniently (active keys, ≤ 2 KB each, never a repair). Each step receives only its own `model.modules.<id>`, unvalidated; the module validates it. A `wantsModel` service hint can request the model for mail `needsModel` skips (never for muted senders or `spam`); core then plans its own kinds as if the model had not run. Without an active extension the request is byte-for-byte unchanged.
- **Spend.** `triage-run.ts` reserves the estimated cost in `ai_usage` before the call and settles it afterwards (`spend.ts`, `spend-utils.ts`), against the mailbox cap and the install cap (default $2 per day, 2,000,000 micros); the cap stops new calls but is not a guaranteed billing ceiling. Without model rates it counts input tokens against two install allowances (`app_settings.agent_auto_read_token_cap` and `agent_chat_token_cap`, migration 0069, default `UNKNOWN_RATES_INPUT_TOKEN_CAP` = 2,000,000 each), split by `ai_usage.source` (`INTERACTIVE_SPEND_SOURCES` in `spend-utils.ts`); chat reserves each step the same way (`src/lib/agent/chat-spend.ts`). `quota.ts` holds the per-mailbox daily limit (default 200) and rate limit.
- **Suggestions.** `agent_suggestions` (`src/db/schema/agent-auto-read.ts`) holds kinds `calendar_invite` (declared by Calendar), `reply`, `summary`, `phishing` (more are reserved) and module-owned kinds such as Money Watch's `subscription`, expiring after 14 days. A module kind is stored once a `suggestion_kind` descriptor declares it, its payload is validated by that descriptor's input schema, and its UI text comes from the client data's `suggestionKindMeta`. They are listed only to users with full access to the mailbox (`/api/agent/suggestions` answers 404 otherwise), and a kind with `audience: "reviewer"` (Money Watch's) only to the reviewer, and surface as a row badge, a reader card and the For you page (`src/app/(dashboard)/for-you`). Reply suggestions create a draft private to the reviewer, guarded by `draft-guard-utils.ts`.
- **`agent_actions` is write-before-effect.** `execute.ts` inserts a `pending` row first, performs the effect, then marks it `applied` or `failed`; stale pending rows are recovered. An undo is a new row (`variant` `undo:<id>`, `undoOf`) inside `DEFAULT_UNDO_WINDOW_MS` (7 days), with the permission rules in `actions-utils.ts`. Organize proposals approved in chat (`confirmAgentAction` in `src/lib/agent/actions.ts`) run through the same executor as `move`, `mark_read`, `set_folder` or `create_folder` rows, saving every message's earlier place in `before`; `mark_read` needs only read access (`canSeeAction`). Only autonomy `off` and `suggest` can be saved (`autonomyError`); `act` and `auto` exist in the schema but are rejected.
- **Calendar invites.** `parseIcsInvite` (`src/lib/calendar/ics-parse-utils.ts`) parses the attached ICS; `invite.ts` checks availability against the reviewer's events and proposes slots; `invite-actions.ts` accepts, declines, proposes, updates or removes. RSVP and proposals go to the ICS organizer only and are refused when none is named; `authPassed` drives the unverified-sender warning.
- **Write with Kite.** `POST /api/agent/compose` (`src/lib/agent/compose.ts`, prompt in `compose-prompt-utils.ts`, output checks in `compose-output-utils.ts`) writes or rewrites composer text with no tools: `selectInteractiveModel` (`interactive-model.ts`) re-checks the assistant switch, the provider and the external opt-in on every request, the spend is reserved like a chat step (source `compose`, chat's token allowance), the email being answered is loaded by the server from the reply's `In-Reply-To`/thread, and only `ai_usage` is stored. The client panel (`src/components/compose/write-with-kite*.tsx`) is loaded lazily from the toolbar button and keeps the quote and the signature block untouched.
- **Summaries.** `GET`/`POST /api/messages/[messageId]/summary` (`src/lib/agent/summaries/`: `service.ts`, SQL in `store.ts`, prompt and eligibility in `summary-prompt-utils.ts`, output checks, languages and digests in `summary-utils.ts`; user docs in `docs/assistant.md`) is the reader's Summarize button: `canRead` is enough (read-only users too), the model goes through `selectInteractiveModel`, each request reserves spend (source `summary` or `summary_translation`, chat's token allowance) and the answer is checked by code. Summaries are cached in `ai_summaries` (`src/db/schema/agent-summaries.ts`, migration 0072) per mailbox, scope, conversation (`coalesce(thread_id, id)`) and the requesting user's personal-instructions digest, with a digest of the covered message ids that marks them out of date. Only `received`, `sent` and `archived` mail not judged spam is ever summarised. Triggers in 0072 delete a conversation's summaries when one of its messages is deleted or leaves those statuses, `saveSummary` writes only while every covered message is still eligible (one conditional `INSERT … SELECT`), translations are rows with `translation_of`, and the table is in `INTERNAL_TABLES` (not backed up). The 0072 `list_summaries*` columns on `mailbox_agent_settings` are reserved for one-line list summaries and not read yet.
- **Testing.** `AI_ALLOW_INSECURE_LOOPBACK` (`src/lib/agent/provider-url-utils.ts`) lets a plain-http loopback provider work outside production, which is how the fake model (`scripts/agent/fake-model-server.mjs`, `e2e/support/fake-model.ts`) runs. `scripts/agent/injection-eval.mjs` runs the hostile corpus in `tests/fixtures/agent-injection/` through the real prompts, guard and policy against a real model; it is not part of CI.
- **Backups.** The new tables are in `BACKUP_TABLES` in `src/lib/backups/export.ts`.

### Modules live in `src/lib/modules/`

Calendar, Booking (depends on Calendar), Email templates, Mail import, Money Watch (id `finance`, subscriptions and their document ledger at `/finance`) and Drive (files at `/drive`, public links at `/d/<token>`) are the six builtin modules the primary admin can turn off for the install (`/modules`, `GET`/`PUT /api/admin/modules`) or per user (`PUT /api/admin/accounts/[id]/modules`). User-facing behaviour and the step-by-step guide to adding one are in `docs/modules.md`; the design is `docs/specs/module-platform.md`.

- **Manifest versus descriptors.** `src/lib/modules/<id>/manifest.ts` is client-safe data (pages, API prefixes, nav, UI commands, composer slots, record kinds, webhook events, scopes, queue message types, cron tasks, labels) listed in `MODULE_MANIFESTS` (`registry.ts`); it imports no `@/db`, zod, React or server code, and browser code reads the smaller `src/lib/modules/client-data/` slice instead. `capabilities.ts` holds JSON-only `CapabilityDescriptor`s generated from the zod schemas in `schemas.ts` (`describeCapability`), indexed in `capability-registry.ts`; `server.ts` holds the handlers, imported only by `server-registry.ts`, which only `invoke.ts` imports. Module implementation code lives in `src/lib/<module>/`, not in the module directory.
- **`invokeCapability(moduleId, name, input, ctx)` is the only path into module code.** Input, the call context (`buildCallContext`) and the result are plain JSON; it checks module state, grants and `mailboxBound` mailboxes, validates input and output, applies `timeoutMs` and never throws (`{ ok: false, error: { code } }` with `module_disabled`, `forbidden`, `invalid_input`, ...). Core never passes `env`, `db`, bindings, a `Request` or functions to a handler; handlers may call `getEnv()` for their own tables.
- **`ModuleHost`** (`host.ts`, `host-services.ts`) is how modules reach core: send through the normal send path and send limits, read messages and attachments, import messages, emit webhooks, resolve refs, invoke another module's `service`, check another user's access, read and decide the module's own suggestions, run its own actions through the executor as the viewer (`actions.execute`), look up the viewer's contacts and a sender's earlier mail, send realtime notices (`notify`) and write audit rows. `suggestions` and `actions` are bound by `src/lib/agent/auto-read/module-host-services.ts`, which `invoke.ts` loads for that side effect. Core code that emits or resolves through it imports `@/lib/modules/invoke` so the host bindings are registered.
- **Import rules, enforced by `tests/module-imports.test.mjs`.** Core surface files (`worker.ts`, `worker-utils.ts`, `server/index.ts`, `server/runtime/scheduler.ts`, the assistant, MCP, webhooks, search, JMAP, automatic reading, For you, the palette, the composer, Settings nav and others) never import `@/lib/modules/<id>`, `@/lib/calendar`, `@/lib/booking`, `@/lib/import`, `@/lib/finance` or `@/components/modules/<id>`; core client code reaches module client code only through `src/components/modules/client-registry.ts`, whose lazy `import()` calls each carry an inline `typeof window` check so the chunk stays out of the server bundle; module directories never import `@/lib/email/send` or `@/lib/email/webhooks` and never use `import()`. `tests/module-registry.test.mjs` checks the manifests and descriptors.
- **State and guards.** `state.ts` reads `module_settings` (no row means `defaultEnabled`) and `user_module_access` (no row means allowed; the primary admin is always allowed), applies `dependsOn`, and treats a missing table (before migration 0062) as every module on. Answers are cached per request and per isolate for 30 seconds; writes clear the isolate cache. Pages are gated with `requireModulePage(id)` in the outermost layout of the module's own route group (`(calendar)`, `(booking)`, `(import)`, `(finance)`, `(drive)`), above any shell, and with `requirePublicModulePage`; both render `src/app/not-found.tsx` (HTTP 404). `AuthGuard` renders nothing on the server, so under `next build` a not-found thrown inside a shell arrives after streaming starts and answers 200. Every method of every route under a module's API prefix is wrapped in `withModule(id, handler)` (`route-guard.ts`): install-level off answers 404 before authentication, per-user off answers 404 after the handler calls `checkUser` (`tests/module-route-guard.test.mjs` scans for both).
- **Record refs.** `{ kind, id }` with kinds `<namespace>:<type>`; `resolveRecordRefs` (`record-refs.ts`) resolves core kinds itself and module kinds through each module's `resolveRefs` capability (resolvers in `src/lib/<module>/refs.ts`), turning anything off, missing or hidden into a neutral unavailable label. Every `href` must pass `isSameOriginPath`. Webhooks, search, For you, Activity, audit rows and chat tool results use them.
- **Scopes stay registry-wide.** `MCP_SCOPES` and the REST key scopes include every module's scopes whether or not it is on, so turning a module off and on never invalidates a key; only tool listing, key creation (400 `MODULE_DISABLED`) and webhook subscriptions follow module state.
- **Data hooks.** A `lifecycle` descriptor with `dataHook: true` (Calendar's `user.time_zone_changed`, which freezes legacy recurring series) runs whatever the module state; other hooks (Booking's `user.created`) run only when on, and a failing hook never rolls back the core write.
- **Composer slots.** The composer's send menu renders `ComposerSlot` (`src/components/compose/composer-slot.tsx`) for the `send-menu` declarations of enabled modules and loads each module's client chunk the first time the menu opens; Templates fills it. The reader's overflow menu does the same for `message-menu` slots (`messageSlots`) through the shared loader `src/components/modules/use-slot-entries.ts`; core draws the entry and the module's `Overlay` gets only `{ messageId, mailboxId }`. Module-owned message statuses (`template`) are never listed, and `?status=template` returns rows only while the owning module is on.
- **Attachment slots.** A message attachment's menu (`src/components/message-attachment-menu.tsx`, opened from `MessageAttachmentCard`) lists the `attachment-menu` slots of enabled modules (`attachmentSlots` in the client data) and loads the module's `Overlay` from its client chunk; the overlay gets only `{ messageId, mailboxId, attachmentId }`. Drive's **Save to Drive** fills it (`src/components/modules/drive/`).
- **Background work.** Manifest `queueMessageTypes` and `cronTasks` are dispatched by `dispatchModuleQueueMessage` and `runModuleCronTasks` (`background.ts`) on both runtimes; a disabled module's messages are acked and skipped with `module_disabled`, so paused import jobs keep their row and resume from the cron task when the module is back on. Mailbox export (`/settings/export`, `GET /api/export/messages`) is core and never gated.
- **Backups.** `module_settings` is in the `system` group, `user_module_access` and `booking_appointments` in `accounts`, `finance_subscriptions` and `finance_charges` in `mail`, the Drive tables in their own `drive` group (`drive_upload_parts` is internal) (after `booking_appointments` in `BACKUP_TABLES`; the ledger stores attachment ids, never file content), and `calendar_events_fts%` is skipped like `messages_fts%`.

### Drive lives in `src/lib/drive/`

User-facing behaviour is in `docs/drive.md`; the design is `docs/specs/drive-storage.md`. Pages are under `src/app/(drive)` and `src/app/d/[token]`, components in `src/components/drive/`, and the API under `/api/drive` and `/api/public/drive`, every method wrapped in `withModule("drive", …)`.

- **Storage.** File bytes go through `getStorage(env)` (`src/lib/storage/`), the store the Drive class is routed to (the default store over `BUCKET` unless Admin → Storage says otherwise); each row records its `store_id` and the object key `drive/<itemId>`. Uploads are multipart, through the Worker in 32 MiB parts (`DRIVE_PROXIED_PART_BYTES`), each part a raw `PUT /api/drive/uploads/[id]/parts/[n]` body streamed to `uploadPart`, or, for an S3 store in direct mode, in 64 MiB parts (`DRIVE_DIRECT_PART_BYTES`) the browser `PUT`s to presigned URLs from `/api/drive/uploads/[id]/part-urls` and confirms with their ETags; on Node the file bucket implements multipart too. Downloads of `DRIVE_PRESIGNED_DOWNLOAD_BYTES` (8 MiB) or more from an S3 store redirect to a five-minute presigned URL; public links always stream through Kite. `reserveDriveFile` (`quota.ts`) reserves the quota and inserts the row in one statement, so concurrent uploads cannot overshoot it, and an owner can have 20 uploads in progress.
- **Access.** `getDriveRole` (`access.ts`) resolves owner, edit or view with one recursive CTE over the ancestor chain (depth at most `DRIVE_MAX_DEPTH`, 64); a share on a folder covers its subtree and a trashed ancestor hides its descendants. Only the owner deletes forever, restores or creates links; edit shares are given and removed by the owner only (403). An item the caller cannot reach answers 404, so ids do not leak.
- **Public links.** `public.ts` resolves a token by its SHA-256 hash (the token is sealed with `APP_ENCRYPTION_KEY` only when the key is set), checks expiry, revocation and the owner being active, and limits folder links to their subtree; the routes and the `/d/[token]` layout also check that Drive is on for the owner. Responses never read or set `ep_session` and carry `no-store`, `no-referrer` and `noindex`. Passwords unlock per link with an HMAC cookie for an hour. `DRIVE_LINK_RATE_LIMIT` (namespace `1005`, previews `1105`) limits visits per IP, `LOGIN_RATE_LIMIT` unlock attempts per IP and link.
- **Background.** The `purgeDrive` cron task (02:00 UTC) deletes items trashed longer than `drive_settings.trash_retention_days` and aborts uploads past their resume window (three days).
- **Before migration 0064.** `answerDrive` (`errors.ts`) turns a missing table into `{ …whenPending, migrationPending: true }` for reads and 409 `MIGRATION_PENDING` for writes.
- **Backups.** Rows only, never file contents; `drive_upload_parts` is in `INTERNAL_TABLES`.

### Object storage lives in `src/lib/storage/`

User-facing behaviour is in `docs/deployment.md#object-storage-optional` and `docs/operations.md#object-storage`; the design is `docs/specs/drive-storage.md`. `getEnv()`, `worker.ts` and the Node env wrap the platform env in `withStorage` (`router.ts`), so `env.BUCKET` is a router that sends each key to the store of its object class (`object-classes-utils.ts`: Mail, Drive, Backups); application code keeps calling `env.BUCKET`. `rawEnvOf` returns the unwrapped env for the default store.

- **Stores and routes.** `storage_stores` (credentials sealed with `APP_ENCRYPTION_KEY`) and `storage_routes` (`src/db/schema/storage.ts`, migration 0065). `loadStorageConfig` (`config.ts`) caches them per isolate for `CONFIG_TTL_MS` (30 s) and falls back to the last known config or the default store when the read fails. Optional `STORAGE_S3_*` env vars bootstrap one store without the UI.
- **S3 client.** `s3-bucket.ts` implements the bucket interface over the SigV4 signer in `src/lib/aws/` (no SDK): streamed bodies, multipart, presigned URLs. Bodies of unknown length are buffered up to `MAX_BUFFERED_BYTES` (32 MiB).
- **SSRF.** `assertStoreEndpoint` checks the endpoint on save and on every config load; private and loopback addresses are refused, except private hosts on Node with `STORAGE_ALLOW_PRIVATE_ENDPOINTS` (MinIO on the LAN) and `http` or loopback with `STORAGE_ALLOW_INSECURE_ENDPOINT` outside production (the e2e fake S3). A blocked store is skipped with `storage.store_blocked`.
- **Validation.** `validate.ts` writes, reads, lists and deletes a probe object (and checks CORS for direct mode) before a store can be saved or routed to.
- **Route switch and migration.** `route-switch.ts` changes a class's active store and keeps the previous one for reads while `migration.ts` copies objects in batches (`storage.migrate` messages on `OUTBOUND_QUEUE`, cursor leased per job); the five-minute cron runs `runStorageMigrationMaintenance`. Purge deletes the old copies only after the job finished.
- **API.** `/api/admin/storage/*` is primary-admin only (`requireSessionAdmin(env, request, isPrimaryAdmin)` plus `hasValidSessionMutationOrigin`) and writes `storage.*` audit events. Secrets and presigned URLs are never returned or logged.
- **Backups.** `storage_stores` and `storage_routes` are in the `system` group; `storage_migrations` is internal. A restore keeps the target's stores and routes when it already has any.

### Usage statistics live in `src/lib/telemetry/`

Opt-in, off by default, pseudonymous, documented field by field in `docs/privacy.md#usage-statistics-opt-in`. `telemetry_state` (one row, migration 0071) holds the owner's choice, a random install id (`crypto.randomUUID()`, made on opt-in and deleted on opt-out) and the UTC day of the last heartbeat; it is in `INTERNAL_TABLES`, so a restore never clones the id. `GET`/`PUT /api/admin/telemetry` (primary admin, origin-checked, audit `telemetry.enabled`/`telemetry.disabled`) back the card in `src/app/(admin)/general/telemetry-card.tsx`. `runTelemetryHeartbeat` (`heartbeat.ts`) runs from the `0 2 * * *` cron and `server/runtime/scheduler.ts`: it claims the day first (`claimTelemetryDay`, so a failure is not retried until tomorrow), counts with one SQL statement, builds the body only through the allowlist `buildHeartbeatPayload` (`telemetry-utils.ts`, schema version 2), which replaces every count by its range (`accountBucket`, `messageBucket`), re-reads the state right before posting (an opt-out or a new id during counting wins) and posts it with a 5 s timeout and `redirect: "error"`, never reading the response; when the id it sent is gone after the collector accepted it (an opt-out in flight), it sends the erasure itself. It never throws and logs a fixed event. Turning statistics off (allowed also under `KITE_TELEMETRY=0`) deletes the id, then `eraseAfterOptOut` (`erase.ts`) calls `DELETE <collector>/v1/installs/<id>` best effort when a heartbeat was ever attempted; a failure is logged as `telemetry.erase_failed`, never undoes the opt-out, and the `PUT` answer's `erasure` lets the card show the id to send to privacy@midego.net. `KITE_TELEMETRY=0`/`false`/`off`/`no` keeps it from being turned on or sent; `KITE_TELEMETRY_URL` overrides the collector, https only, and set but empty means nothing is sent (the Node env passes it through unnormalised for that reason). `DEFAULT_TELEMETRY_URL` is `https://kite-telemetry.midego.net/v1/heartbeat`, the collector Michiel de Gooijer (midego) runs on Cloudflare; `telemetryUrl` treats a non-https override or a `.invalid` host as no endpoint, so the e2e server (`KITE_TELEMETRY_URL` in `playwright.config.ts`, passed through `vite.config.ts`) never posts, and unit tests inject a fetcher; `tests/telemetry-cron.test.mjs` runs both cron paths for a default install with a recording global `fetch`. A missing table reads as off. Adding a field means changing `HeartbeatPayload`, the builder, `TELEMETRY_FIELDS`, the collector's validator and schema (`deploy/telemetry-collector/`, a standalone Worker outside the build, deployed by hand with the steps in its README; `src/index.ts` must export only `default` and D1 allows at most five compound SELECT terms, tested by `tests/telemetry-collector.test.mjs`; it keeps daily rows 90 days, then rolls them up into id-free `aggregates`, and serves the public `GET /v1/summary` from a copy the cron stores, with counts below 5 as `"<5"` and only `installs_30d` below 10 installs; `DELETE /v1/installs/<id>` checks the id before its per-`CF-Connecting-IP` rate limit) and the privacy page, and bumping `telemetry_schema_version`. Raw SQL here uses plain `?` parameters: better-sqlite3 rejects numbered ones.

### Password reset and MFA

`reset_email` on `users` is the destination for reset links (`src/lib/auth/password-reset.ts`); links are hashed, single-use, 30 minutes, and redeeming one revokes every session. Reset mail is sent by `sendSystemEmail` (`src/lib/email/system-mail.ts`), which writes straight to the send binding from the first admin mailbox on a sending-enabled domain, so nothing lands in Sent and no webhooks fire. If no domain can send, the request still returns 200 and a warning is logged. TOTP lives in `src/lib/auth/totp.ts` (RFC 6238 over Web Crypto, no dependency); the secret is stored on `users` at enrolment but only counts once `totp_enabled` is set by a verified code. A login with MFA returns `{ mfaRequired, challengeToken }` (`login_challenges`, 5 minutes) instead of a session, and `/api/auth/mfa/verify` finishes it with a TOTP or recovery code. Password changes and admin resets call `deleteUserSessions`.

### Search is an FTS5 index kept by triggers

`messages_fts` (migration 0030) is an external-content FTS5 table over `messages`; three triggers in the same migration keep it in sync on insert, update and delete, so no application code touches the index. `buildSearchConditions` in `src/lib/search/conditions.ts` turns the Gmail-style grammar (`src/lib/search/query-utils.ts`) into a `rowid IN (SELECT rowid FROM messages_fts WHERE messages_fts MATCH ?)` predicate plus plain column filters. Two consequences: the bootstrap SQL in `src/lib/setup/migration.ts` is split with `splitSqlStatements`, which keeps trigger bodies whole; and the backup coverage check skips `messages_fts%`, since the shadow tables are derived and repopulate on restore. `wrangler d1 export` does not work on databases with virtual tables; the app's own JSON backup is unaffected.

### Access control

Two independent auth surfaces:

- **Session cookie** (`ep_session`) — `getCurrentUser` / `requireUser` in `src/lib/auth/cookies.ts`, backed by `src/lib/auth/session.ts`. Used by dashboard/admin API routes. `requireUser` *throws*, which Next surfaces as a 500, so route files under `src/app/api` must not import it (`tests/route-auth.test.mjs` fails if one does). Use `requireSessionUser` from `src/lib/api/auth.ts`, which returns a 401 response, or `requireSessionAdmin(env, request, allow?)`, which returns 401 without a session and 403 when `allow` (default `isAdmin`; pass `isPrimaryAdmin` for owner-only routes) rejects the user.
- **API key bearer token** — `authenticateApiKey` + `requireScope` in `src/lib/api/auth.ts`, used by the public `/api/v1/*` surface.

Mailbox authorization is separate from user role and goes through `src/lib/mailboxes/access.ts` (`getMailboxAccessLevel`, `listAccessibleMailboxes`, `listAccessibleMailboxIds`), which accounts for ownership, the `mailbox_access` sharing table, and admin role. Message queries scope by accessible mailbox IDs, not by `userId` — see `src/app/api/messages/route.ts` for the canonical pattern.

### The inbox is resizable panels, and one file owns the hotkeys

`SidebarFrame` (`src/components/sidebar-frame.tsx`) puts the dashboard's sidebar and page into `SidebarPanels` (`sidebar-panels.tsx`, react-resizable-panels) from `md` up, and on phones renders the sidebar as a modal `Sheet` through `SidebarAside`. `MessageSplitLayout` (`src/components/messages/message-split-layout.tsx`) does the same for the message list and the reader in the right/below reading layouts. Panel sizes are pixels stored in the existing column-width preferences (`column-width-preferences.ts`, `kite-sidebar-minimal`); `useSyncedPanel` (`src/components/ui/use-synced-panel.ts`) moves a panel when a stored preference changes elsewhere (loaded after mount, a toggle button), and sizes are read from `onLayoutChanged`'s layout with `layoutPixels`, because a panel reports its new pixel size a frame later. The Settings, Admin and Calendar shells keep their CSS grid sidebar.

`useHotkeys` (`src/components/shortcuts/use-hotkeys.ts`) is the only key listener logic and decides where bare keys never fire: inputs, textareas, contentEditable, comboboxes (the Select trigger), and anything inside a dialog, alertdialog, modal, menu, listbox or a `data-shortcuts-off` element such as the composer form. App-wide bindings (`c`, `/`, `?`, Cmd+K, `g` sequences) are `CORE_SHORTCUTS` in `src/lib/modules/core-commands.ts`, bound by `ShortcutsProvider`; the folder list's keys are `listShortcuts` (`messages/message-list-keyboard-utils.ts`, bound by `useMessageListKeyboard` only while no message is open); the reader's are `messageShortcuts` (`message-actions/message-shortcuts.ts`) and `readerNavigationShortcuts` (`messages/message-detail-navigation-utils.ts`). The `?` sheet lists those builders through `shortcuts/mail-key-hints-utils.ts`, so a new key belongs in a builder, not in a hand-kept list.

### Folders are mostly virtual

`messages.status` is a free-text column driving the folder views: `received` (inbox), `sent`, `draft`, `spam`, `trash`, `archived`. Orthogonal to that are `starred`, `snoozedUntil`, and `folderId` (user-created folders in the `folders` table). A "folder" route under `src/app/(dashboard)/` is usually a status filter, not a table.

### All mailboxes is a scope, not a mailbox

`MailboxProvider` keeps `selectedMailbox` (the mailbox chosen last, which Settings and Compose start from) next to `allMailboxes`, the filter's `hiddenMailboxIds` (both browser preferences through `useStoredState`, keys in `mailbox-provider-utils.ts`) and the derived `viewMailboxes` and `mailboxScope`. Mail views pass `mailboxScope` to `useMessages`/`useMessageCounts`/navigation: one id, several ids joined by commas, or null for every accessible mailbox, which `setMailboxScopeParam` (`src/hooks/utils.ts`) sends as `mailboxId` or `mailboxIds`. On the server `resolveMailboxScope` (`src/lib/mailboxes/scope-utils.ts`) checks every requested id against `listAccessibleMailboxes` (404 otherwise) and `mailboxScopeCondition` binds several as one JSON parameter. Conversation grouping keys on thread and mailbox (`conversationKey`, `src/lib/messages/conversation-key.ts`), so a thread never spans mailboxes. Per-message access in the UI comes from `useMessageAccess` (read-only mail is never moved or deleted; the bulk route enforces the same and files mail only into a folder of its own mailbox). `setSelectedMailbox` does not leave the combined view; the switchers call `setAllMailboxes(false)`. In the combined view the composer keeps its From mailbox locally (`use-compose-mailbox.ts`).

### No licensing, no self-update

Every feature is available without a key; access is governed only by roles and per-user permissions (admin, primary admin, `canManage*`, mailbox sharing). Migration 0056 dropped the old `license_settings` table; `RETIRED_BACKUP_TABLES` in `src/lib/backups/utils.ts` strips it from older backup documents on restore and skips it in the coverage check for databases that have not applied 0056 yet. Add a table there when a future migration drops one.

The app never checks for or pulls updates. New versions arrive by a push to the connected Cloudflare Git integration or `npm run deploy`; the database card on the admin overview (`src/components/admin-update-card.tsx`, `/api/admin/migrations`) reports and applies pending D1 migrations through the Worker binding. `UpdateAvailableHost` (`src/components/update-available-host.tsx`, mounted in `providers.tsx`) polls `GET /api/version` for signed-in tabs and shows a "Kite was updated" toast with Reload once the version differs from the one the tab first saw; the version is the server's own (`getDeploymentVersion` in `src/lib/deployment-version.ts`: `CF_VERSION_METADATA.id`, else the build identity), never anything fetched from outside. The sidebar footer links to the source repository (`SOURCE_CODE_URL` in `src/lib/source-code.ts`), which AGPL-3.0 section 13 requires for network users.

## Conventions

- Tabs for indentation. `@/*` maps to `src/*`.
- Types and pure helpers are split out of components and modules into sibling `*-types.d.ts` and `*-utils.ts` files (41 and 27 of them respectively). Follow this when adding anything non-trivial.
- Server code reaches bindings through `getEnv()` / `getEnvAsync()` in `src/lib/cloudflare.ts`, then `getDb(env)` from `src/db`. Keep binding access centralized here.
- API routes return `NextResponse.json({ error: "..." }, { status })` for failures; there is no shared error envelope helper.
- UI is Tailwind v4 + shadcn/Radix primitives in `src/components/ui/`. `Select` and `Checkbox` keep the native API (`<option>` children, `onChange(event)` with `event.target.value` / `event.target.checked`) but render Radix controls, so e2e specs pick options with `chooseOption` and read values with `expectSelectValue` (`e2e/support/select.ts`), never Playwright's `selectOption`. `DialogContent` sets no max height, so a tall dialog overflows the viewport with an unreachable submit button — add `max-h-[calc(100vh-4rem)] overflow-y-auto` on any dialog with more than a few fields.
- `cloudflare-env.d.ts` is generated (500KB) — regenerate with `cf-typegen`, never hand-edit.
