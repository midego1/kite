# Modules

Kite's core is mail: mailboxes, domains, contacts, accounts, settings, backups, search, the assistant, MCP, the API, JMAP, webhooks and mailbox export. Core is always on. Around it sit **modules**, feature areas the owner (the primary admin) can turn off for everyone or for some users. The design is in the [module platform spec](specs/module-platform.md).

## The six modules

| Module | What it is | Depends on |
| --- | --- | --- |
| **Calendar** | The personal calendar at `/calendar`, its API under `/api/calendar`, the read-only subscription feed under `/api/public/calendar` (see [Subscribing from another calendar app](api.md#subscribing-from-another-calendar-app)), the calendar tools in assistant chat and MCP, calendar invitations in automatic reading, the Events section of the search dropdown and the `calendar.event.created`, `calendar.event.updated` and `calendar.event.deleted` webhook events. | nothing |
| **Booking** | Booking pages: the settings page at `/booking`, the public pages at `/book/...` and `/c/...`, the APIs under `/api/booking` and `/api/public/booking`, and the `booking.appointment.created` webhook event. Booked appointments land in the host's calendar. | Calendar |
| **Email templates** | The **Template** entry in the composer's send menu (insert a template, save a new one) and its API under `/api/templates`. There is no templates page. | nothing |
| **Mail import** | Settings → Import (`/settings/import`): IMAP imports, mbox and eml uploads and background IMAP jobs, with the API under `/api/import`. | nothing |
| **Money Watch** | Subscription tracking: the Subscriptions page at `/finance` and its sidebar item with a count, the API under `/api/finance`, subscription cards in automatic reading (found in receipts, invoices, renewal, trial, refund and failed-payment mail), the **Track as subscription** and **Add to a tracked subscription** entries in the reader's menu, renewal reminders (a notice, the sidebar count and, when Calendar is on, a calendar event), the `list_subscriptions` and `list_payments` tools in assistant chat and MCP, the `track_subscription` chat tool (a card you approve, see [Adding a subscription in chat](assistant.md#adding-a-subscription-in-chat)), the Subscriptions and Payments sections of the search dropdown, the `finance:subscription` and `finance:payment` record kinds and the `finance.subscription.detected`, `finance.subscription.renewal_due` and `finance.payment.recorded` webhook events (the last for payments found in new mail, queued and never for the 90-day scan). It also records payments that arrive by mail (one-off receipts, invoices, refunds and credit notes) without a card on the **Payments** tab at `/finance?tab=payments`, with month totals per currency, an optional category (set by code only where obvious, editable by hand), **Export CSV** of the filtered rows and **Scan last 90 days** for mail already there. **Keep receipts** (the gear button on either tab, on by default) files a tracked subscription's, a document's or a payment's mail into the owner's Drive under `Money Watch/Receipts/<year>/`: the raw mail as `.eml`, a self-contained sanitized HTML copy and, where it can be built reliably, a PDF, plus the receipt attachment (not copied separately when Drive flags it, and rows from a No-AI mailbox are not filed at all); **Save receipts for existing payments** backfills rows recorded before it ran while their mail still exists. Deleting a row that already has a Drive copy asks first; the copy is never deleted with it. Its data is four tables: tracked subscriptions, their document ledger (invoices, payments, credit notes, refunds and failed payments, each linked to its message and attachment), the payments found in mail (fields and a message link only) and the Keep receipts ledger (which rows are filed, to which Drive files). | nothing (calendar reminders need Calendar; Keep receipts needs Drive) |
| **Drive** | Files and folders: the pages under `/drive` (My Drive, Recent, Shared with me, All attachments, Trash) and their sidebar and mailbox-menu items, Admin → Drive at `/drive/settings`, the API under `/api/drive`, public links at `/d/<token>` with their API under `/api/public/drive`, **Save to Drive** in a message attachment's menu, the **Open Drive** palette command and the daily task that empties the trash. It also offers a `fileReceipt` service other modules reach through `moduleHost.invoke`, which Money Watch's Keep receipts uses; with Drive off, Keep receipts cannot file anything and says so in its setting. Its data is the `drive_*` tables and the file contents in object storage, including Money Watch's filed copies, which count toward the owner's Drive quota like any other file. See [Drive](drive.md). | nothing |

Every module starts on. A new install and an upgraded one behave exactly as before until the owner turns something off.

## Turning a module off

Open **Admin → Modules** (`/modules`). Only the owner sees this page; other admins do not, and the API answers them with 403. Each module shows its name, what it does, what it depends on and a switch. The page also lists the core areas that have no switch.

Booking needs Calendar. Turning Calendar off also turns Booking off: the page asks first and then shows Booking as "Off because Calendar is off". Turning Calendar on again restores Booking as it was. Turning Booking on while Calendar is off is refused.

### What off does

A module that is off is absent, not broken:

- Its links, tabs, Settings entries and command palette commands disappear.
- Its pages show the "Page not found" page, with HTTP status 404. Its API routes answer 404 for everyone, signed in or not, before any sign-in check. Booking's public pages and the public booking API answer 404 too.
- Assistant chat loses the module's tools, and the `open_page` tool no longer offers the module's pages. MCP stops listing its tools.
- Its webhook events are no longer sent, and a webhook cannot newly subscribe to them (the API answers 400 `MODULE_DISABLED`). New API keys and MCP keys cannot ask for its scopes, for the same reason.
- Search drops the module's section. With Calendar off, the Events section is gone from the search dropdown.
- Automatic reading skips the calendar step and Activity says "Calendar is turned off". Invitation suggestions and their counts are hidden, and accepting one or undoing an invitation action is refused until Calendar is back on. The other steps (reply, summary, phishing) still run.
- With Email templates off, the composer's send menu shows only the schedule options and loads no template code, and the message API returns no template rows.
- With Mail import off, its queued work is skipped: see paused imports below.
- With Drive off, the Drive sidebar and mailbox-menu items, Admin → Drive, the palette command and **Save to Drive** disappear, `/drive` and `/d/<token>` show the not-found page, and `/api/drive` and `/api/public/drive` answer 404, so every public link stops working. For a restricted user, their own public links answer 404 while other users' links keep working. The daily trash clean-up does not run while Drive is off for the install. Money Watch's Keep receipts files nothing while Drive is off for the install or for the owner; its setting says so instead of offering the switch, and unfiled rows are filed once Drive is back on.
- With Calendar off, the Today card in the empty reading pane disappears.
- With Money Watch off, the Payments tab, the recording of payments and the 90-day scan stop (a running scan waits and resumes when it is back on), and the Subscriptions sidebar item and its count, the reader's menu entries, its card in the empty reading pane and its palette commands disappear, `/finance` and `/api/finance` answer 404, and automatic reading skips its step (Activity says "Money Watch is turned off") and does not add its part to the model request. Existing subscription cards are hidden, and accepting one or undoing a Money Watch action is refused. The reminder task sends no notice, webhook or calendar event, and leaves the rows untouched, so a reminder still inside its window fires once Money Watch is back on. Calendar reminder events it already created stay in the calendar. Keep receipts stops too (its cron tasks are module-owned, like the reminder task); files already saved in Drive stay there, since Money Watch never deletes them.

### What off does not do

- **Nothing is deleted.** Events, booking pages, appointments, templates, import jobs, subscriptions and their documents, and Drive files, shares and links stay in the database and in backups. Turn the module on again and everything is back.
- **Mailbox export always works.** Settings → Export (`/settings/export`) and the export API are core. Turning Mail import off never hides them, and the old Import and export links send you to Export instead.
- **Old keys keep working.** An API key or MCP key that already has a module's scope keeps authenticating. It only gets 404 or no tools from that module while the module is off.
- **Existing webhook subscriptions keep their events.** They just receive nothing while the module is off.
- **Integrity hooks still run.** When a user changes their time zone, Calendar still freezes their legacy recurring series, so the calendar is correct when it comes back.

### Importing a whole account

Settings → Import → **IMAP** → **Whole account** copies every folder of an account in one background job. **Show folders** signs in, lists the account's folders and proposes where each one goes, in a table with the number of messages and the size of each folder (see [Sizes before you start](#sizes-before-you-start)). Under **Sign in with**, choose one of your [connected accounts](external-accounts.md) instead of typing the server and password: the job then keeps no password of its own and asks core for the account's login on every run (`moduleHost.accounts.sourceLogin`), so removing the account stops the import at its next run with "The account was removed". **Import mail** on Settings → Connected accounts opens this page with the account chosen (`/settings/import?account=<id>`), and the import starts in the mailbox that account's mail goes to: choosing the account selects that mailbox in the sidebar (only when you have full access to it), and the line under **Sign in with** names it.

| Source folder | Goes to | Ticked |
| --- | --- | --- |
| Inbox | Inbox | yes |
| Sent | Sent | yes |
| Archive | Archive | yes |
| Your own folders | A Kite folder of the same name, created if missing; nested folders become `Parent / Child`, since Kite folders are flat | yes |
| Junk or Spam | Spam | no |
| Trash | Trash (emptied by trash retention) | no |

Drafts and virtual folders (Flagged, Important) are not offered. Each row can be unticked or sent elsewhere. Kite recognises the standard folders by the special-use attributes the server announces, or by their usual names where it announces none. Folders are copied one after another in the order of the table, so the provider sees a single connection; a message filed in two folders lands once, in the first. A folder the server refuses to open (it no longer exists or cannot be selected) is marked failed and the others go on; the finished import then says how many folders could not be imported. When the server is only busy, throttling or limiting connections, the import waits and tries again instead.

**Gmail** shows labels as folders, so the same message appears in several of them. On Gmail Kite copies **All Mail** once and files each message by its labels: Inbox, else Sent, else its first label (alphabetically) as a Kite folder, else Archive. A message with several labels goes to the folder of the first, and the jobs list says how many did. Gmail's Spam and Trash are offered separately, switched off; drafts are skipped.

**One folder** is the earlier form: one source folder into one place, optionally only its newest messages.

The jobs list below the form shows each folder's progress. **Pause** stops an import once the messages it is copying at that moment are saved (a slow source server can make that take a few minutes): it keeps its saved password and its place in every folder, and **Resume** continues from there. Resuming while that batch is still running never starts a second copy beside it: the running batch simply carries on. If the worker running it died, Resume restarts the job about three minutes after that worker's last sign of life, and at most one five-minute check later. A job paused for more than seven days is cancelled and its password erased; start it again and the mail already imported is skipped. If the source server rebuilds a folder (a new UIDVALIDITY), Kite reads that folder again from the start and skips what it already has.

#### Sizes before you start

Below the table the page always shows the totals of the ticked folders: the messages, the size at the source, what the import adds to mail storage and what it adds to the database (with the database's size now), plus a warning from 70% of the database limit (and **Import anyway** above 90%, see [Operations](operations.md#database-size)). Sizes are a preview: they never block **Import account** and never make it fail.

- **Where a folder's size comes from.** A server that offers `STATUS=SIZE` (RFC 8438) gives each folder's total in the same answer as its message count, so the table shows it at once. Gmail does not; there Kite measures the ticked folders one after another with `UID FETCH n:m (UID RFC822.SIZE)`, which returns about 40 bytes per message and no message bodies.
- **Measuring in steps.** The page asks `POST /api/import/account/sizes` for one step at a time (`src/lib/import/folder-sizes.ts`): `FETCH n:m (UID RFC822.SIZE)` over the next window of 10,000 messages by sequence number, newest first. Sequence numbers are dense, so a folder takes one request per 10,000 messages however sparse its UIDs are (100,000 messages: ten requests; at most 100 per folder, and the page gives up on a folder after its message count divided by 10,000 plus three). The answer carries the step's messages, bytes, how many came without a size, the folder's `UIDVALIDITY` and the cursor for the next call; the page adds them up, so no request holds more than one step in memory (about 10,000 answer lines) and nothing is stored between steps. A changed `UIDVALIDITY` starts that folder again, and a message deleted at the source between two steps can shift the numbers by one, so the sum is a preview. Each request opens its own short IMAP connection (the password is sent with every request, never kept); a step that is no longer wanted closes its connection at once (the request is aborted). Closing the page or switching to One folder stops measuring; ticking another folder adds it.
- **Estimate or exact.** While a folder is being measured the table shows "≈ size · measuring 40%", the average weight of the messages counted so far times the folder's message count, and the totals say "estimate". Once every ticked folder is finished the sizes are exact. A message that came without a size makes the folder an estimate (scaled from the others), and a server that sent no sizes at all leaves it unknown. A folder the server cannot measure (it names no message count) is "unavailable" and one whose steps failed (after two retries) is "failed" and is tried again when you tick it again or read the folders again; either shows "—", keeps the size at "Not known yet" and is named under the totals. The warning and the start check both use exact sizes only, so an estimate never shows less than the server decides.
- **Upper bound.** A message in several folders, or already in Kite, is copied once (matched by Message-ID), so the totals are an upper bound; Gmail's All Mail already holds one copy of every message, which Kite copies once.
- **What the import adds.** Mail storage grows by at least the raw size of the messages (`MAIL_STORE_FACTOR` is 1.0, a lower bound): since [attachments are stored once](specs/attachments-once.md) an imported attachment is a range of the stored raw message and has no decoded copy. With `ATTACHMENT_RAW_INDEX=off` every attachment is stored again and the factor is 1.51 (the measured figure of that spec, assuming attachments are 70% of the bytes). Two things add to that and are not counted, because they depend on the mail: attachments the MIME index cannot verify (stored decoded, as before) and HTML bodies over 16 KB that are offloaded (see [Large imported messages](#large-imported-messages)). The database grows by about the install's average D1 bytes per message (40 KB until it holds 1,000 messages, at most 128 KB), but never more than a message weighs and never less than 2 KB (its row and index entries); with the measured sizes the cap is the real average weight. The folder's measured size is also sent with the job and kept as its folder total.

Whole-account imports need database migration 0076. Until it is applied from the admin overview, starting one answers "Apply the database update to import a whole account", while **One folder** imports keep working.

### What an import keeps

- **Read and starred.** An IMAP import keeps the source's state: mail marked read there (`\Seen`) is read in Kite, and flagged mail (`\Flagged`) is starred. Answered marks and keywords are not kept. Imported sent mail and drafts are always read. Uploaded `.eml` and `.mbox` files carry no flags, so Kite reads the state from the message's own headers (below); a message that says nothing arrives unread and not starred, as before.
- **Headers of uploaded files.** An `.eml` or `.mbox` upload reads these headers, only from the first 64 KiB of each message, and ignores anything it cannot make sense of. `Status` and `X-Status` (the mbox convention, flag letters only) containing `R` mean read, and without it unread; `X-Status` containing `F` stars the message. A Gmail Takeout `X-Gmail-Labels` header (only the first one in the message is read) gives the same, from positive signs only: the `Unread` label means unread, and the `Opened` label, or Gmail's own labels such as `Inbox` or `Important` without `Unread`, mean read. A list of other names (a localized export) or one that may be cut short says nothing, so the mail stays unread. The `Starred` label stars the message. Mail labelled `Spam` is filed in Spam, and mail labelled `Trash` in Trash (Trash wins when both are present). `X-Spam-Flag: YES` files mail in Spam only when the message has no `X-Gmail-Labels` header: Gmail's labels are the sole authority on placement where they exist, so Inbox mail a filter flagged stays in Inbox. Imported spam and trash have the status `spam` or `trash` like any other and are never held by the [Screener](screener.md) (imports are not screened); the sender of imported spam is not added to your contacts. Spam and Trash retention counts from the import date. The headers only refine an upload to **Inbox**, the default: pick any other destination (Archive, Spam, Trash, Sent or one of your folders) and every message goes exactly there, though it still keeps its read and starred state. Labels such as `Sent` and `Drafts` are not used to file uploads; upload those exports to Sent or Drafts yourself. Importing an export again skips mail already in the mailbox, so it does not reclassify, mark read or move rows imported earlier. IMAP imports ignore these headers and keep using the server's flags and folders.
- **Dates.** A message keeps the date in its `Date` header. When it has none (or one that cannot be read), an IMAP import uses the date the source server received it (`INTERNALDATE`) instead of the time of the import. A date more than a day in the future is not believed: the import uses the next date that is, and otherwise the time of the import.
- **No duplicates.** A message already in the target mailbox is skipped, by its Message-ID, whether it was stored with angle brackets (received mail) or without (mail Kite sent). So importing the provider's Sent folder does not add copies of mail you sent from Kite, and running the same import again only adds what is missing. A message without a Message-ID is recognised by a SHA-256 hash of its bytes, across re-runs and folders. Messages imported without a Message-ID before this change were keyed by file name and size, so a re-run can add those once more.
- **Conversations.** Imports run newest first, so a reply often arrives before the message it answers. An imported message whose parent is not stored yet joins the conversation of the first message its `References` header names, so the replies and the original meet in one conversation whatever order they arrive in. Received mail is grouped as before.

### Failed sign-ins and oversized messages

- **Limit on failed sign-ins.** Every import route that signs in to a server you name is limited per user, counting **failed** sign-ins only: `POST /api/import/imap`, `/api/import/imap/folders`, `/api/import/account/plan`, `/api/import/account/sizes` and the runs of an import job (`POST /api/import/jobs` itself only saves the job; its first run signs in). Ten failures in ten minutes, or five at the same server (host and port), and the next sign-in is refused with HTTP 429, `code: "RATE_LIMITED"`, a plain message and a `Retry-After` header (seconds until the oldest failure that counts leaves the window); nothing connects meanwhile. A sign-in that works is never counted, so measuring a 100,000-message folder (ten steps, each its own sign-in, plus a retry or two) or planning an account again and again is never limited. Connecting a connected account and **Test connection** have their own limit of 10 attempts in 10 minutes ([Connected accounts](external-accounts.md#security)).
- **How it counts** (`src/lib/import/sign-in-limit.ts`, counting rules in `sign-in-limit-utils.ts`). Each sign-in writes an `import.sign_in_attempt` audit row, then counts the user's rows in the window, its own included, so parallel requests cannot all see room; a refused attempt removes its row, and so does a sign-in that works, which leaves failures and attempts still in flight. It needs no rate-limit binding and no `wrangler.jsonc` change, and behaves the same on Workers and Node. When the row cannot be written or counted, the sign-in is refused instead of allowed unchecked. A request cancelled by the page (an aborted size step) is not a failure, but its row stays, marked, and cancelled sign-ins have limits of their own (15 in 10 minutes per user, 8 per server, refused with a message that does not mention the password), because the password may already have been sent when the page cancelled.
- **Jobs.** A job whose password is wrong still fails at once ("Sign-in failed"). A run the limit refuses is not the job's fault: it keeps its attempts and its password, releases its lease and is queued again once the limit has room (`Retry-After` plus a second; without a queue the five-minute cron picks it up), with the message in its last error. So creating job after job cannot be used to try passwords without end, and a refused job never fails because of the wait.
- **Oversized messages are skipped.** Before fetching, an import asks the server for the `RFC822.SIZE` of the next UIDs (`UID FETCH … (UID RFC822.SIZE)`, no bodies) and leaves out each message above the connection's message limit (36 MB on Workers, 64 MB on the self-hosted server). It counts as skipped and the job's problems name it ("INBOX: skipped message 42, 80 MB is over the 36 MB limit"; the direct import route returns the same lines in `errors`), so one huge message no longer fails the batch and, after five attempts, the job. A server that leaves out the size is planned at the message limit, so its messages are fetched one at a time and never prefetched beside another (the connection's own limits are the backstop).
- **Memory is bounded by segments** (`src/lib/import/capped-fetch-utils.ts`). The UIDs of a run are cut, in order, into segments of at most 25 messages and 16 MB (a message up to the limit that does not fit with the others is a segment of its own). An import job writes each message of a segment as soon as it is read (`streamMessages` in `src/lib/imap/connection.ts`, `ImportWriter` in `src/lib/import/job-run.ts`): messages go to the module host in groups of at most 4 MB (a bigger message alone), one group written while the next is read, and a group's raw bytes are let go before its call, so only its encoded copies are alive while the host decodes them. The rest of the FETCH answer waits in the socket meanwhile, and the time spent writing does not count toward the command's deadline. Only once a segment is read, written and recorded in the job does the next segment's FETCH start, so the cursor never passes a message that was not written. So a run holds at most two groups and the message being read, not a segment and the next one: a Workers isolate (128 MB) never holds a chunk of big messages together (25 messages of 15 MB are written one at a time, not 375 MB). Within a segment messages are written in the order the server answers (usually oldest first), and segments run newest first. The direct import route (`POST /api/import/imap`) stops fetching further segments once it holds 32 MB of messages, so one request holds at most 32 MB plus one segment (16 MB, or one message up to the limit): when a page of up to 100 messages is bigger, it answers with the newest ones and a `nextOffset` that continues with the rest.

### Large imported messages

Imported mail whose HTML body is larger than 16 KB keeps that HTML in the Mail store (the store routed for Mail under **Admin → Storage**, the default R2 bucket otherwise), at `bodies/<message id>.html`, instead of in the database (migration 0074). This keeps a whole-account import from filling D1 with newsletter markup. Nothing changes for the reader: the message, its conversation, replies and forwards, search, the assistant, JMAP, the REST API and the mbox export show the same message as before. The database keeps the message's text part for search, snippets and automatic reading; a message without a text part keeps the readable text of its HTML, so search still finds it by its words. Words that appear only in the HTML part of a message that also has a text part are not searchable, as the two parts normally say the same. Until migration 0074 is applied, imports keep the HTML in the database as before. Mail Kite receives itself is not offloaded.

### IMAP connections

IMAP imports connect only over an encrypted connection: TLS on port 993, or STARTTLS on port 143 (the import form's **Encryption** choice). Kite checks the server's certificate and never sends a password in plain text, so a server that offers neither is refused, and so are ports other than 993 and 143 and private or local addresses. The same client runs on Cloudflare and on the Node runtime; on Node, Kite resolves the server's name itself, refuses it when any address is private, and connects only to the addresses it checked. Creating an import job resolves the name too (after the mailbox checks), so a server whose name points at a private address, or that does not resolve, is refused when you start the job, not at its first run; every run checks it again when it connects. A refused lookup counts as a failed sign-in toward the limit below, so starting jobs cannot be used to map which names resolve where. `EXTERNAL_ACCOUNTS_ALLOW_PRIVATE_HOSTS=1` lets a self-hosted install import from a mail server on its LAN, and `EXTERNAL_ACCOUNTS_EXTRA_PORTS` adds ports for a bridge such as DavMail (see [Self-hosting](self-hosting.md)). The client also limits what a server can send and how long it may take, so a broken or hostile server cannot fill memory or hold an import:

- A message may be at most 36 MB on Cloudflare (enough for a message at Gmail's 25 MB attachment limit; a Worker has 128 MB of memory) and 64 MB on the Node runtime, and one batch of messages 48 MB or 96 MB. A message above the limit fails its batch: the job retries a few times and then fails with the reason. It is not skipped yet.
- A response line may be at most 8 MB, and the lines answering one command 32 MB or 200,000 lines, sign-in included. A folder that may be too large for one search line (more than about 700,000 messages) is listed in ranges of UIDs instead, up to 64 ranges; a folder whose UIDs are too sparse for that is still asked once and stops at the line limit. One search lists at most 1 million messages on Cloudflare and 4 million on the Node runtime, across all its ranges, and starts no new range after the run's four-minute budget; past either, the job retries a few times and then fails with the reason.
- A command gets three minutes. Data that keeps arriving at 64 KB/s or more extends that, up to ten minutes, so a large batch on a slow link finishes while a server that sends a byte at a time does not.

### Paused imports

Turning Mail import off pauses background IMAP jobs. They are not failed or cancelled:

- A job keeps its status, its progress and its saved source credentials. No attempt is counted.
- A batch that is already running finishes. Its next batch is skipped instead of running.
- The safety net that restarts stalled jobs does not run while the module is off.
- Within about five minutes of turning Mail import on again, every paused job continues from where it stopped, on Cloudflare and on the Node runtime.

A job can also pause itself when the database is nearly full: at 90% of its size limit it stops with the status **Paused** and keeps its saved credentials until you press **Resume** (which asks for confirmation while the database is still above 90%) or cancel it. A job paused for more than 7 days is cancelled and its credentials erased. See [Database size](operations.md#database-size).

Cancelling a job needs Mail import to be on, because the cancel button and its API belong to the module. The Modules page reminds you that paused jobs keep their saved credentials.

## Per-user access

The owner can also restrict a module for one user under **Accounts → (user) → Permissions → Modules**. A restricted user sees exactly what everyone sees when the module is off: no links, not-found pages and 404 from the API. For Booking that includes the user's own public booking pages. For Mail import it includes the user's background jobs, which pause as above.

The owner is never restricted. Every change to a module switch or to someone's access is written to the audit log.

## When a change takes effect

The browser tab and server that handled a change see it at once. Other open sessions, and other server instances, pick it up within 30 seconds, because Kite keeps the module state in memory for up to 30 seconds. The Modules page says so.

## Before the database update

The switches live in tables that migration 0062 adds. Until an admin applies it, every module is on for everyone, and the Modules page says "Apply the pending database update to manage modules" with the switches disabled. Calendar search returns no events until then.

Money Watch keeps its data in two tables that migration 0063 adds. Until it is applied, `/finance` shows an empty page that points to the database update, its read API answers with an empty list and `migrationPending: true`, every write answers 409 `MIGRATION_PENDING`, automatic reading skips its step and the reminder task does nothing. Payments by mail add `finance_payments` and the scan's `finance_payment_scans` in migration 0094; until it is applied the Payments tab says so, `GET /api/finance/payments` answers `{ truncated: false, payments: [], months: [], scan: null, migrationPending: true }`, its writes answer 409 `MIGRATION_PENDING`, and the payment step and the scan do nothing. Migration 0109 adds the nullable `category` column to `finance_payments`; until it is applied payments are still recorded (without a category), rows and exports show no category, and changing a category answers 409 `MIGRATION_PENDING`. Keep receipts adds `finance_receipts`, `finance_receipt_settings` and the backfill's `finance_receipt_backfills` in migration 0102; until it is applied its setting and backfill routes answer 409 `MIGRATION_PENDING`, and the Keep receipts cron tasks do nothing.

Drive keeps its data in the tables that migration 0064 adds. Until it is applied, Drive pages say the update is pending, its read API answers with an empty list and `migrationPending: true`, every write answers 409 `MIGRATION_PENDING`, public links answer 404 and the trash task does nothing.

## Adding a builtin module

Modules are compiled into Kite. They run the same way on Cloudflare and on the Node runtime, from a static registry, with no code loaded at runtime. A module is two halves: a client-safe **manifest** (plain data) and a list of **capability descriptors** (JSON) with zod schemas and handlers on the server. Core only ever calls a module through `invokeCapability(moduleId, name, input, ctx)` with JSON input, a JSON call context and a JSON result. Tests in `tests/module-*.test.mjs` enforce the rules below.

1. **Id.** Add the id to `ModuleId` in `src/lib/modules/module-types.d.ts` and to `MODULE_IDS` in `src/lib/modules/client-data/module-ids.ts`, in the same position as in the registry.
2. **Client data.** Create `src/lib/modules/client-data/<id>.ts` with what browser code needs: the name, navigation items (`nav`, placed in `mailbox-selector`, `account-menu`, `module-tabs` or `settings-nav`), UI commands, composer slots, message menu slots, reading pane cards, suggestion kinds with their `suggestionKindMeta` (the For you heading, the "Why?" text per reason code, an optional row chip rank, label and icon) and key scope labels. Add it to `CLIENT_MODULES` in `src/lib/modules/client-data/index.ts`. Client components read this slice, never the manifest.
3. **Manifest.** Create `src/lib/modules/<id>/manifest.ts` exporting a `ModuleManifest`: description, `dependsOn`, `defaultEnabled`, page prefixes and API prefixes (mark public ones), record kinds, webhook events, grants, MCP and API key scopes, search sections, owned message statuses, queue message types, cron tasks, Activity labels, reason texts and admin notes. Add it to `MODULE_MANIFESTS` in `src/lib/modules/registry.ts`. The manifest must not import `@/db`, zod, React or server code.
4. **Schemas.** Create `src/lib/modules/<id>/schemas.ts` with a zod input schema (and usually an output schema) for every capability. Use `resolveRefsSchemas` from `src/lib/modules/shared-schemas.ts` for record resolution.
5. **Descriptors.** Create `src/lib/modules/<id>/capabilities.ts` with the module's `promptFragment` (or `null`) and one descriptor per capability, built with `describeCapability`, which generates the JSON Schema from the zod schema. A descriptor names its surfaces (`assistant_tool`, `mcp_tool`, `search`, `resolve_refs`, `suggestion_kind`, `triage_step`, `action`, `webhook_event`, `lifecycle`, `cron`, `queue`, `jmap_capability`, `jmap_method`, `service`), the grants it needs, its effect and, where it applies, `mailboxBound` and `timeoutMs`. A `suggestion_kind` descriptor's input schema validates the kind's payload when triage stores it; a `suggestion_kind` with `audience: "reviewer"` is shown to and decided by the mailbox's reviewer only. A `triage_step` may give each suggestion a `title` (core strips control and bidi characters and keeps 120 characters, otherwise the kind's `label` is used). Its input (`triageStepSchemas` in `src/lib/modules/shared-schemas.ts`) carries the sender name, at most 8 KB of body text, the automatic, no-reply, list and spam facts and the `List-Unsubscribe`, `List-Unsubscribe-Post` and `List-Id` headers; a step validating against `baseTriageStepSchemas` gets them stripped. `triage.automatic: true` lets `Auto-Submitted` mail reach the step through a steps-only pass, and `triage.capability` names the step's per-mailbox switch in `capabilities.modules` (on by default); list the same key with its label in the client data's `triageSwitches` so the automatic-reading settings show it. A step also runs, with `model: null`, when the model is refused or fails. A step that needs a few fields from the model declares a model extension in `triage.model`: a small JSON Schema (`additionalProperties: false`, at most 2 KB, scalar, nullable and enum properties only), a one-line `instructions` string of at most 600 characters, a `maxOutputTokens` allowance of 1 to 200 and, optionally, `wantsModel`, the name of one of the module's own `service` capabilities. Core merges the schema under `modules.<id>` in the triage request, appends the instructions to the system prompt outside the untrusted message block and raises the output cap (all extensions together add at most 200 tokens), but only while the module is on for the reviewer and the step's mailbox switch is on. Core asks the model for mail it would otherwise skip only when the `wantsModel` hint answers `{ wantsModel: true }`, under every existing gate and spend cap. The step receives only its own object as `model.modules.<id>`, unvalidated: validate it field by field in the module with your own zod schema, treat anything invalid as absent, and never let it override a value the step found itself or supply links, addresses or owners (Money Watch's `src/lib/finance/model-utils.ts` is the example). An `assistant_tool` that writes is proposed in chat instead of run when its effect is `update`, `delete` or `send` or its descriptor has `approval`: `approval.preview` names one of the module's own `service` capabilities, called with `{ tool, input }`, which answers the card's lines (`items`) and optionally a `version` core checks again on approval, an `input` that replaces the model's (validated against the tool's input schema again, so the card shows and runs exactly that) and `details` for the module's own card, or `{ refused: { error } }`, which the assistant gets as the tool's error. `approval.editable` lists the input keys the user may change on the card; core merges only those into the input on approval and the tool validates the result. A tool that answers `{ refused: { error } }` on approval leaves the card waiting with that error, and one whose answer carries `result.actionId` of an action it ran through `moduleHost.actions.execute` gets **Undo** on the chat card (Money Watch's `track_subscription` is the example). An `action` descriptor with `reopensSuggestion: true` makes core reopen the suggestion after an undo once no live action of the module remains on it, and an action's result may carry a `ref` to one of the module's own records, which Activity links. Add the list to `MODULE_CAPABILITIES` in `src/lib/modules/capability-registry.ts`.
6. **Handlers.** Create `src/lib/modules/<id>/server.ts` exporting one handler per invokable descriptor, and add it to `SERVER_MODULES` in `src/lib/modules/server-registry.ts`, which only `invoke.ts` imports. A handler gets parsed JSON and the call context, never `env`, a database handle, a binding, a `Request` or a function. It may call `getEnv()` for its own tables. Keep the module directory to these four files and put the implementation under `src/lib/<id>/`. Module directories may not use `import()`.
7. **Core services.** Reach core through `moduleHost` (`src/lib/modules/host.ts`): `mail.send` (the normal send path, counted against the acting user's send limits), `mail.getMessage` (optionally with a body excerpt and the list headers), `mail.recentFromSender` (up to 5 earlier messages from one sender in a mailbox the call is bound to), `mail.readAttachment`, `mail.importMessages`, `emitWebhook`, `resolveRefs`, `invoke` (another module's `service`), `modules.isEnabledFor`, `users.getProfile`, `contacts.find` (the viewer's own contact), `suggestions.get` and `suggestions.decide` (the module's own suggestion kinds, for viewers who may decide them), `actions.execute` (the module's own action capabilities through the executor, as the viewer), `notify` (a realtime notice with a same-origin link to users who have the module on) and `audit`. Never import `@/lib/email/send` or `@/lib/email/webhooks` from a module directory.
8. **Record kinds.** Add each `<id>:<type>` kind to `RecordKind` and to the manifest's `recordKinds`, with the neutral label shown when a record is unavailable. Declare a `resolveRefs` capability and put the resolver in `src/lib/<id>/refs.ts`. A resolver returns a same-origin `href` (or `null`) and a label, and must not reveal records the viewer cannot see.
9. **UI commands and client code.** Commands go in the client data with an effect (`navigate`, `read`, `fill`, `create`, `update`, `delete`) and either a route target (an href template filled from `params`) or a client target naming a handler. Client pieces (command handlers, suggestion cards, composer and message menu slots, and `proposalCards`, the body of a chat approval card for one of the module's tools by tool name, with its approve label and approved text) go in `src/components/modules/<id>/client.ts`, registered in `MODULE_CLIENTS` in `src/components/modules/client-registry.ts` with the inline `typeof window` check at the `import()`, so the chunk stays out of the server bundle and loads only when a module that is on needs it.
10. **Composer slots.** Declare a `send-menu` slot in the client data and the manifest, and export `composerSlots[<slot id>]` with a `MenuItem` (and optionally an `Overlay`) from the client chunk. The composer loads the chunk only when its send menu is first opened and only for modules that are on. A `message-menu` slot (`messageSlots` in the client data and the manifest) works the same way in the reader's overflow menu: core draws the entry from the declared `label` and `icon`, and the chunk's `messageSlots[<slot id>].Overlay` receives only `{ messageId, mailboxId }` plus its open state. A `reading-pane` slot (`readingPaneSlots`, `{ id, slot: "reading-pane", order }` in the client data and the manifest) adds a card to the empty reading pane's command center, after the core cards. Its component comes from a separate pane chunk, `src/components/modules/<id>/pane.ts` exporting `readingPaneSlots[<slot id>].Card`, registered in `MODULE_PANE_CLIENTS` in `client-registry.ts` with the same inline `typeof window` check; keep that chunk to the card so the pane loads nothing else of the module. The pane requests it after it has rendered and only for modules that are on. The card receives only `{ mailboxId }` (null for all mailboxes), draws the whole card with `CommandCenterCard` from `src/components/command-center/command-center-card.tsx` (with its `icon`, and `CommandCenterEmpty` for a day or a week with nothing in it), fetches its data through the module's own guarded API and renders nothing while that is loading, failing or answering `migrationPending`; core leaves out a card that throws. Calendar's **Today** and Money Watch's renewals card are the examples.
11. **Queue and cron.** Declare queue message kinds in `queueMessageTypes` (kind, queue, capability, metric class) with a matching `queue` descriptor, and scheduled work in `cronTasks` with a matching `cron` descriptor; a cron handler receives `{ scheduledTime }` (the tick time, ISO), so its input schema must allow or strip it. `dispatchModuleQueueMessage` and `runModuleCronTasks` in `src/lib/modules/background.ts` route them on both runtimes. A message for a module that is off is acked and skipped with `module_disabled`. Never add per-module code to `worker.ts`, `worker-utils.ts`, `server/index.ts` or `server/runtime/scheduler.ts`.
12. **Guards.** Give the module's pages their own route group and gate them with `requireModulePage(id)` in that group's outermost layout, which then renders the shell (see `src/app/(booking)/layout.tsx`). A guard in a layout nested inside a shell still shows the not-found page, but the Node build answers it with HTTP 200, and `tests/module-route-guard.test.mjs` refuses it. Gate each public page with `requirePublicModulePage(id, host)`. Wrap every exported method of every route under the module's API prefixes in `withModule(id, handler)` from `src/lib/modules/route-guard.ts`, and call `checkUser(user)` (or `checkHost` on a public route) right after authenticating. After adding routes, run `npm run docs:generate` and commit the result.
13. **Tests.** The unit tests in `tests/module-registry.test.mjs`, `tests/module-imports.test.mjs`, `tests/module-route-guard.test.mjs` and `tests/module-capabilities.test.mjs` check the new module automatically: manifests are data, descriptors round-trip through JSON, every descriptor has a handler, schemas match, routes are wrapped and core does not import module code. Add unit tests for your handlers, and add the module to the `e2e/27-modules-*.spec.ts` files (the gate in `27-modules-gating`, the off-then-on flow in `27-modules-surfaces`; shared helpers are in `e2e/support/module-spec.ts`): off hides its navigation, makes its pages not-found and its API 404, and on restores everything. Restore every module in `finally`.
14. **Data and backups.** Put the module's tables in their own schema file under `src/db/schema/`, write the migration by hand in the generated style, and add every new table to the backup lists in the same change (`BACKUP_TABLES` and `INTERNAL_TABLES` in `src/lib/backups/export.ts`, `BACKUP_TABLE_GROUPS` in `src/lib/backups/table-groups.ts`, `DatabaseBackupTable` in `src/lib/backups/types.d.ts`). A missing table must read as "nothing yet", so the module keeps working on a database that has not applied the migration.

Sandboxed apps (signed bundles that run inside your own Kite, using the same descriptors and the same call contract) are designed in the spec but not built.
